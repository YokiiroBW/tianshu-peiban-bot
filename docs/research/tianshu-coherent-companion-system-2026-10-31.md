## 2. 研究给出的结论与限制

### 2.1 好感度的收益来自什么

关系有连续性，会让用户感到“这段相处有历史”：称呼合适、记得共同经历、知道何时接话、了解对方边界、对未完成的事情有后续。这是值得做的产品能力。

陪伴研究中，感到被倾听与短期孤独感缓解有关；长期人机关系研究也强调自我披露、回应和关系演变。但这些研究**没有证明可见分数、签到涨分或离线扣分是必要机制**。[AI Companions Reduce Loneliness](https://doi.org/10.1093/jcr/ucaf040)、[Skjuve 等的纵向研究](https://doi.org/10.1016/j.ijhcs.2022.102903)。

量化反馈可能让成长更容易理解，也能提供游戏目标；一般任务研究中，积分可以提高任务产出，而量化可能降低活动本身的乐趣。这些是跨场景证据，不能直接当作陪伴产品的因果实验。[Etkin，2016](https://doi.org/10.1093/jcr/ucv095)、[Mekler 等，2017](https://doi.org/10.1016/j.chb.2015.08.048)。

因此，天枢可以展示共同经历与关系变化，但应把“更懂彼此”作为目标。若以后明确增加养成游戏模式，分数只做该模式的展示投影，不能重新成为所有陪伴逻辑的底座。当前默认方案直接删除旧自动涨跌分与阶段解锁规则。

### 2.2 主要风险对应具体设计

| 可能出现的问题 | 对天枢的具体设计含义 |
|---|---|
| 用户为了维持分数而刷消息、迎合角色 | 消息数量、付费、签到不直接增加亲密；同一次经历重复描述不增加独立证据 |
| 未回应、忙碌或离线被解释为关系变差 | 回应率只调整联系频率和时机，不扣关系、不产生惩罚性情绪 |
| AI 为了让用户满意而强化错误判断 | 用户偏好影响表达，不改写事实；角色可以温和持不同看法，关系成长不等于赞同一切 |
| 排他、内疚、挽留提高停留时间 | 不使用“离开就受伤”“只有我理解你”等手段；结束对话不触发情感挽留任务 |
| 模型升级使角色突然像另一个人 | 人格版本、共同经历和相处偏好独立于模型；模型替换按相同人物案例检查连续性 |
| 关系记忆把私聊内容带进群聊 | 共同经历仍继承原来源范围；亲密关系不扩大披露或设备操作权限 |

研究支持重视这些问题，但风险大小不能从小样本、论坛材料或使用相关性推成全体用户发生率。四周聊天实验中的高使用量关联不是随机分配“多用”的因果结论；有关迎合的实验也不能推出所有共情都不利。[Fang 等，2025](https://arxiv.org/abs/2503.17473)、[Cheng 等，Science 2026](https://doi.org/10.1126/science.aec8352)、[Emotional Manipulation by AI Companions](https://arxiv.org/abs/2508.19258)。

### 2.3 记忆、计划和学习要分别有正确结构

- **CoALA** 提供工作记忆、情景记忆、语义认识和行动决策的组织方式。适合用来确定职责，不是买一套框架就能得到人格的证明。[TMLR 2024](https://arxiv.org/html/2309.02427v3)
- **Generative Agents** 展示观察、检索、反思与计划组合能改善模拟角色的可信表现；不能把短期模拟的可信度当成人类长期幸福度。[UIST 2023](https://arxiv.org/abs/2304.03442)
- **Hindsight、Graphiti** 值得借鉴事实/经历/认识的区分、来源关联、时间版本和多路召回；天枢不需要因此同时安装几个记忆服务。[Hindsight](https://aclanthology.org/2026.acl-demo.27/)、[Zep 论文](https://arxiv.org/abs/2501.13956)
- **PM-Bench** 表明未来意图的跨日、更新与触发执行是独立难题；增加 heartbeat 或多代理并不稳定解决它。承诺必须是可取消、可改期的结构化状态。[COLM 2026](https://arxiv.org/html/2607.12385v1)
- **LongMemEval、EverMemBench** 提醒我们分别测记得住、找得到、归属正确、理解更新、会承认不知道。不能只测向量召回率。[LongMemEval](https://arxiv.org/abs/2410.10813)、[EverMemBench](https://arxiv.org/html/2602.01313v3)

这里还有一个值得保留的核对结果：EverMemBench 摘要的部分表述与正文 oracle 表格不一致。正文 Table 5 的多跳结果并不是普遍 26%。本方案只采用它的任务分类及“把检索和推理分开评估”的方法，不复述那个容易误导的数字。

## 3. 确定的目标架构

推荐 **一个模块化天枢应用、一套领域模型、一套 PostgreSQL 真相来源、一套持久工作调度和行动回执**。

闭环为：

> 消息、观察与真实动作结果 → 带来源的事件 → 事实与持续事项 → 用户认识、角色认识和关系 → 本轮上下文与注意分配 → 对话、日程和能力行动 → 真实结果 → 新经历与增量整理。

这是共享语义，不是把所有东西塞进一张万能表，也不是让所有功能每次都调用完整链路。明确命令仍可直接执行；普通聊天不等后台整理；没有新变化时不调用规划模型。

最终模块归属如下，名称为目标目录，尚未创建：

| 模块 | 唯一拥有的规则 | 主要输出 |
|---|---|---|
| `identity` | 账号—人物—角色、受众、场景、权限与授权版本 | 可信调用上下文 |
| `sources` | 来源定位、内容版本、覆盖、撤回/遗忘传播、外部档案适配 | 可核验的证据片段 |
| `memory` | 事实/观点、情景经历、来源依赖、检索与增量整理 | 记忆包、当前认识 |
| `people` | 用户画像、群主题画像、角色—人物关系的投影规则 | 相处背景与适用条件 |
| `companion` | 稳定人格、对话工作状态、短期情绪、兴趣使用、表达 | 回复、行动提案、简短决策理由 |
| `life` | 持续目标、承诺、活动、日程、关注点、主动联系的业务状态 | 下一次有理由的行动 |
| `capabilities` | 技能目录、可用性、参数、执行与回执、媒体和设备适配 | 实际结果与消费覆盖 |
| `models` | 原生协议、模型配置、供应商准入、公平调度与真实 usage | 一次有身份的模型调用 |
| `runtime` | 事务内派工、后台作业、超时取消、恢复、诊断 | 可恢复执行，不拥有业务含义 |
| `web` / `channels` | 普通用户界面与 QQ/TG 等接入/发送 | 配置和可读状态，不复制领域规则 |

`people` 是 Memory 领域内的投影子模块，不再形成独立数据库或模型抽取管道。`life` 的当前承诺与活动状态由它自己维护，Memory 只存历史证据及查询投影；不让两个模块各自判断一个提醒是否已经取消。

## 4. 统一语义：什么发生了、谁知道、现在还成立吗

### 4.1 必须分开的几个对象

| 对象 | 回答的问题 | 例子 |
|---|---|---|
| Source / Evidence | 原话或实际结果在哪里 | 私聊消息的某一段、阅读到第 3 章的回执 |
| Episode | 发生过什么 | 用户和角色一起讨论过某本书 |
| Claim | 目前有依据认为怎样 | 用户不喜欢突发惊吓；角色喜欢该作品的谜题 |
| Matter | 哪一件事正在延续 | 这次考试安排、一次共同阅读、设备维修 |
| Commitment / Action | 系统答应做什么、执行到哪 | 周六 8 点提醒；本次提醒尚未提交渠道 |
| Projection | 为当前使用压缩出的认识 | 画像、关系概况、近期自传、群主题 |
| Reflection / Opinion | 角色如何理解或感受一件事 | 对一次讨论的遗憾、对看过作品的观点；不能证明对方的内心 |
| Working state | 这一轮临时在想什么 | 当前问题、候选行动、短期情绪、正在读的位置 |

“用户说要去考试”是证据支持的用户意图；“角色已经替用户安排提醒”必须另有承诺写入结果；“提醒已送达”必须有渠道回执。三者不能通过一段模型总结合并成一个成功状态。

### 4.2 每条认识有足够的语义边界

至少保留：

- `owner`：谁的记忆视角；`subject`：说的是谁；`speaker`：谁说的；`participants`：谁参与。
- `world`：现实、角色设定、明确虚构剧情；`epistemic_kind`：直接陈述、亲历、转述、推断、主观看法。
- `occurred_at`：实际发生时间；`valid_from/to`：该认识适用的时间；`recorded_at`：系统何时得知。
- `scope/audience`：允许在哪些场景使用；`evidence_refs`：确切片段与版本。
- `conditions/negations`：条件与否定；`supersedes/disputes`：更新、矛盾或撤回关系。

不要再让“scope 中的 person”自动成为所有句子的说话者。比如甲说“乙周五考试”，它是甲对乙的转述。乙后来在私聊说“改到周六”，也不能无条件把私聊细节搬到甲所在群。

输入还应明确 `origin_kind`：人类来话、外部观察、工具回执、计时器、系统通知、角色产物或归档重放。它由接入代码确定，不能由正文自报。身份用稳定 ID 保存，昵称用于显示；禁止把历史原文里的“他”批量改成某个关系称呼。系统进度通知、角色手记和助手复述不增加用户自述证据。

更新采用“同主体、同事项、同语义槽、同适用范围”的有依据修订。后来收到的旧截图不能覆盖更早收到的新安排；两个人的互相矛盾陈述可以同时保存为不同主张，不能依靠最后写入获胜。

### 4.3 持续事项是最重要的连接点

为考试、共同阅读、创作、健康关心、下载订阅、维修等持续主题分配 `matter_id`。事项关联参与者、证据、事实槽、承诺、活动和产物。

这不是把所有聊天强行归档到某个项目。普通闲聊可以只有 episode；只有存在后续状态、目标或未解决问题才形成 matter。模糊相关只记 `related`，不自动合并。模型可以提议关联，强制合并必须有共同对象、明确指代或用户修正等依据。

事项状态由所属领域决定：用户报告“维修好了”是 memory 中的当前报告；天枢自己的“执行重启任务是否成功”由 capabilities 回执决定。统一事项索引引用两者，不抢走它们的写入权。

## 5. 画像、关系与情绪怎样相连

### 5.1 画像是一组可修正的认识

用户画像分为：明确稳定偏好、带条件的习惯、近期处境、系统推断、明确共享的公开偏好。每项显示依据、适用场景、最后确认时间；推断不会伪装成用户自述。

例：“工作日晚上不想被打扰”带工作日和晚间条件；“最近备考”有时间范围；“似乎喜欢短回复”是低确定性的观察，用户一句“今天详细讲”足以覆盖本轮使用。

现有 `profiles.py` 的显式共享发布语义继续有用，但需要与私人认识分开：角色可以记住私聊中的偏好，不意味着已经获准把它发布为共享画像。群画像描述群的话题和交流习惯，不把少数活跃者的偏好覆盖所有成员。

画像读取先选与当前任务相关的少量维度。询问书籍时不加载设备权限、身体状态等无关认识。完整画像仍能在管理界面查看和纠正。

### 5.2 关系模型的三部分

| 部分 | 内容 | 更新方式 |
|---|---|---|
| 明确约定 | 朋友/协作者/用户选择的角色关系、昵称、边界、联系偏好、冻结 | 明确设置或有指向的用户请求；不靠模型偷偷升级 |
| 共同历史 | 重要共同经历、一起完成的事情、支持、分歧和修复、纪念点 | 来自可核验 episode；保留原受众 |
| 当前相处认识 | 熟悉哪些话题、交流是否顺畅、哪些细节应照顾、未解决的分歧 | 从独立经历增量归纳；有证据和不确定性 |

需要数值的地方，只使用有明确用途的内部特征。例如熟悉度帮助决定解释背景的多少，联系回应统计决定打扰阈值。它们不再求和成“爱你多少”，不与管理员身份、秘密披露、工具能力或服务质量绑定。

**冻结继续保留用户控制语义**：冻结该角色—人物的自动关系演变，明确约定和已有关系不自动涨跌；新事件仍可留作事实记忆，短期情绪仍可变化，用户明确纠正仍生效。解冻从当前开始，不补算冻结期间的关系变化。

离线不会减少关系。很久没聊，只降低“我知道你最近在做什么”的新鲜度。回来时可以自然关心近况，不表现为惩罚、冷淡或要求补偿。

### 5.3 情绪、长期偏好、关系、联系意愿分别变化

- 一次争论可以使短期情绪不快，但不立即改写多年关系。
- 明确边界被反复触碰，可以形成“这个话题需要谨慎”的关系认识；不把用户忙、拒绝某次建议或观点不同当作扣分依据。
- 角色自己的长期兴趣来自她实际看过、读过、做过的经历，也允许独立于用户兴趣。
- 用户未回复，先视为不可用信息；联系调度减少打扰，关系不受损。
- 主动表达可以有个人看法和自然分歧。共情、事实准确与边界同时成立。

这比一个好感度数值更能表达连续性，也更容易定位错误：究竟是记错事实、误判联系时机，还是表达过度亲密。

### 5.4 人格与情绪采用有原因的动态结构

人格保留完整作者原文、价值动机、情境反应、解释和例子；增加“什么情境下为什么这样表现”的辅助结构，避免只有标签或随机对冲。角色设定经历与上线后的真实经历分别标记。

情绪继续沿现有 affect 领域演进，分为具体情绪事件、较慢的心境和活动精力；长期关系与稳定人格独立。使用 valence/arousal 连续状态、事件中的控制感和少量调节模式，允许混合感受、持续与恢复。收到澄清时重新评价同一事件，不重复累加。半衰期和阈值是工程参数，不是心理测量。

不新增每轮必经情绪模型调用；主对话/规划可顺带提出简短、带来源的状态建议，程序负责幂等、范围和时间更新。情绪影响表达和可选活动，不吞私聊、不取消已确认承诺、不因用户离线制造关系惩罚。理论、数据结构与填写示例见[动态人格详案](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/tianshu-model-concurrency-persona-design-2026-10-31.md)。

### 5.5 风格成长是有范围的表达变化

人格保留稳定基线；可学习部分是情境中的表达习惯和相处方式，例如“对这个人，解释困难问题时先给具体例子”“共同讨论这部作品后，更愿意表达对配乐的看法”。风格投影保存适用对象/场景、来源经历、原规则与新规则、形成原因、版本和最近复核水位。由 `companion` 拥有表达规则，Memory 提供依据和失效通知。

一次独立经历可以产生暂时观察；是否形成稳定习惯取决于后续独立支持和反例，不因同一段话在日记中重复出现就升级。明确的用户语体要求可立即作用于对应范围；普通风格更新使用 `expression_revision`，不重新授权、不使合法历史失效。没有新依据时保持原风格，记录“已复核，无变化”即可，不要求每五天编出一条成长。

私聊学到的相处细节保留原范围。全局表达习惯只能从允许用于该范围的材料生成，不能把私人事实换个说法放进全局人设。冲突或效果变差时可撤回对应规则；用户可查看和修正变化，不需要每次弹窗批准正常学习。

冻结某角色—人物关系时，该人物的自动相处风格更新也暂停，避免绕过冻结间接改变关系表达。角色通用表达能力、事实记忆和短期情绪仍可变化，用户明确纠正继续生效；解冻不追补冻结期的自动相处规则。

## 6. 记忆的写入、整理、检索和遗忘

### 6.1 写入尽量短，理解分层完成

1. 接入层完成身份、角色、受众与群策略判定，保存原消息或权威来源引用；明确停用的场景不继续加工正文。
2. 记录事件身份和业务结果。当前回复所需的近期内容直接可用，不等待长期抽取。
3. 对明确的提醒、取消、改期、纠正等操作，在本轮完成结构化落地；含糊且会影响实际执行的部分自然澄清，不能等夜间总结猜测。
4. 后台按脏事项/实体处理增量片段，提出 claims、episode 关联和画像更新。
5. 校验主体、范围、条件和来源，原子提交修订与后续派工。失败只影响这一项，不阻塞所有其他人物。

模型每次提案采用一个正式、可表达否定与条件的 schema。由同一份类型定义生成验证和提示词示例，删除当前 retention 依赖不可达 `negations` 字段的错位规则。

### 6.2 摘要是压缩，不是新增证据

对话压缩服务于当前工作记忆；长期整理才生成事实与认识。日记、总结、画像和兴趣概况都依赖原始证据，不能互相循环证明。

来源依赖精确到一条 claim 所需的片段，保留必要的否定、条件、时间和说话者。不能为省时间截掉这些语义，也不应把整轮 256 条来源全部绑定给其中一句话。

一个结论有两组独立充分证据时，明确记录替代支持组；其中一组撤回后可以依据另一组重新成立。多个片段共同才支持一个结论时，缺一个就必须重算，不能把“部分还有来源”当作完整有效。

### 6.3 一条有边界的检索路径

目标顺序：

> 确定角色/人物/受众与任务 → 读取相关进行中事项和明确偏好 → 在数据库内做有范围的候选检索 → 只加载候选正文与必要证据 → 融合排序 → 小集合重排 → 有上限的去重多样化 → 精确来源/范围核验 → 按真实 token 预算组装。

关键改变：

- 不再先装载所有授权组、所有文档、全部向量和证明材料，再做 top-k。
- 语义、中文关键词、实体/事项、时间是互补入口；时间不能只作为最后一个衰减乘子。
- 多人物问题先分解主体和事项。配额保障相关人物不会被刷屏者挤掉，不为群内每个人固定分配无关内容。
- MMR 缓存已选集合的最大相似度，选到所需 k 即停止；复杂度按候选数和 k 受控，不对全库反复重排。
- 神经重排不抹掉有效期、主体和事项语义。先排除失效/不适用材料，再组合相关性；不拿一个模型分数覆盖所有业务条件。
- “全部未完成承诺”走结构化查询和分页；不能以语义 top-k 冒充完整清单。
- 未召回、没记录、来源不可用、存在冲突分开表达。检索失败不证明事情从没发生。

起始候选预算可设每路 40、融合最多 120、重排最多 24、最终约 8–16 个语义单元；这些是实现起点，不是实验最优值。长问题按任务预算调整，完整语义单元不因硬截字失去否定和条件。

### 6.4 遗忘与更正是同一条闭环的反向更新

来源撤回/用户遗忘 → 直接依赖的 claims 失效或重算 → 画像/关系投影重建 → 上下文缓存失效 → 未执行行动重新判断。

保留最小删除标记和导入水位，使仍在外部档案、日记或旧队列里的内容不会重新学回来。删除用户私密认识不等于删除独立媒体原件或另一人的聊天。它们有各自的真实所有者。

过期通常意味着不再作为“当前事实”，并不自动抹去历史；用户明确要求忘记时才按所选范围删除内容和派生物。长期稳定偏好不靠重复聊天才能续命。

### 6.5 所有材料共用一份上下文预算

采用一个 `ContextAssembler`。人格、近期对话、关系、当前事项、召回片段、手记、工具说明、网页和视觉结果都是有类型的材料贡献者，不能各自在最终请求后面再追加一段提示词。总预算包含文本、工具 schema、图像/音频输入及预留输出；各提供者的字符/字节上限只用于运输防护，不能代替模型 token 预算。

按“当前输入与可信控制信息 → 完整有效人格 → 当前事项、明确偏好与必要工具结果 → 相关经历 → 可选手记和扩展背景”选材。完整人格不被静默截断；所选模型容不下必要输入时，使用明确允许且能容纳的路线，或清楚报告配置限制。不能为了塞更多旧日记删掉本轮问题、否定、条件或来源边界。

每个材料单元包含来源、适用范围、优先级、大小和必要依赖。整组条件和证据要共同入选；过大的低优先级单元可跳过，必要大单元可用已有带来源摘要或按问题获取更小原文。相关手记按事件和当前话题读取，不固定每轮灌六条心里话、两篇日记和整个风格档案。

稳定系统前缀与动态材料分开，所有数据按字面内容传递，不将记忆中的模板符号当成可执行提示模板。能准确计量时使用对应 tokenizer/提供者接口；无法准确计量的模态使用明确标记的保守估计与余量，保留实际 usage 对照，不能把估计冒充真实计费。缓存键包含角色、范围、内容及表达版本，不能跨人物复用私人材料。

这吸收插件预算和动态 context 的经验；上下文选材的重要性也得到 [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) 的任务实验支持，但具体预算仍由天枢实际模型与请求决定。

## 7. 日程、自主生活与主动陪伴

### 7.1 让计划拥有不同时间尺度

| 层次 | 内容 | 什么时候改变 |
|---|---|---|
| 长期方向 | 角色兴趣、想读的作品、持续创作、与用户共同目标 | 新经历、明确意图、阶段结果 |
| 当前事项 | 未完成承诺、正在读的书、需要关心的进展 | 状态更新、截止时间、取消或完成 |
| 当日安排 | 可用时间、作息、几个可执行活动、留白 | 起床/日期切换、重要变化；局部调整 |
| 下一步 | 一次阅读、一次提问、一次实际工具调用 | 执行结果或外部变化 |

日程提供节奏，不能把模型锁在机械时间表里。新消息只影响关联活动，不因任意资料版本变化重置整个剩余日程。日期切换不清掉长期兴趣，也不假定昨天未完成的工作已经完成。

### 7.2 一个待办必须有明确的唤醒条件

提醒和承诺保存 `due_at` 或事件条件、时区、对象、有效窗口、前提、改期/取消版本及原始依据。时间型由调度器唤醒；事件型由相应事件唤醒；没有条件也不能执行的项目进入明确的等待状态。

`waiting` 必须说明在等用户、来源、资源、某个事件还是下次时间。用户等待可以没有自动唤醒时间，但必须有可见原因与收到回应后的转移。删除无原因的 `paused + NULL` 黑洞。

错过时间的处理按意图确定：晨间叫醒过期不在下午补发；读书活动可顺延；重要明确提醒可按用户设置补报一次。重启不批量补发所有过时主动消息。

### 7.3 主动联系要回答三个问题

1. **为什么现在有话可说？** 新实际经历、共同事项进展、明确承诺、与用户相关且不重复的发现。
2. **为什么值得打扰这个人？** 用户联系偏好、当前会话、时段、上次联系、是否有回应；不是好感分达到阈值。
3. **现在这句话还成立吗？** 用户刚发新消息、事项已取消、内容重复、权限改变，都应撤销或改写未发送提案。

复用 R57 的显著性、双阈值、回应反馈与发送前检查，将它们收敛到一个 `AttentionPolicy`：生活分享、群参与、事项关心共享注意预算与重复判定，但各自保留原因和约束。用户明确发来的问题与约定提醒不需要靠“新奇度高”才被受理。

到期只意味着重新考虑，不能直接授权发送。参考可重规划的对话时间线，把尚未提交渠道的动作作为可撤销提案；已提交/未知结果的动作沿原回执核对。[Proactive AI，2026 预印本](https://arxiv.org/abs/2610.05159)。

群聊可旁听并形成之后有用的认识，也可选择沉默。只为制造活跃而插话不算成长。每条 contact 只有一个回应样本，晚到的回应修正该样本；不把一次对话里的十条消息算十次强化。

自拍与语音也受同一联系策略管理。活动/日程可以产生“想拍一张”“想给某人看看”的意图，生成前检查成本和用途，生成完成后再次判断现在是否合适发送。仅为相册创作、候选分享和用户明确交付分别记录；免打扰不必停止所有创作，已经生成也不意味着必须打扰。多个媒体段属于一次逻辑联系，照片完成事件不会继续触发下一次自拍。

### 7.4 世界模拟与真实数字生活共同存在

角色小屋、睡眠、穿搭和世界观继续保留，其模拟状态有 `world=fictional`。实际读了哪一章、看了哪段视频、搜索获得了什么、创作了哪个文件，使用真实回执和覆盖。

角色可以说“我刚在小屋里整理书架”，但不能因此声称已阅读尚未获取的书籍。日记能够表达感受，事实部分来自实际经历；没有足够素材时写短一点，或不写，不用模型补造一天。

### 7.5 本次完整纳入网页 论坛与 B 站自主浏览

根据本次新增要求，网页搜索/浏览、论坛阅读、B 站内容发现与真实视频理解纳入本次重构范围。它们归入**自主数字生活能力**：日程安排时机，内容能力负责获取与理解，记忆保存实际经历，兴趣/情绪/目标决定后续行动，注意策略决定是否分享。

#### 现有基础与实际缺口

| 已核对的实现 | 可以复用 | 需要补齐 |
|---|---|---|
| Platform `content_discovery` | 网页搜索候选、已有 B 站订阅/媒体库、分页与去重 | 站内发现、关注更新/主题浏览与自由探索；当前该入口没有 forum 来源类型 |
| Memory Knowledge 的网页读取 | 获取网页原文、HTML 文字、来源版本 | 可靠正文抽取、必要的动态页面读取、分页和论坛楼层结构 |
| `knowledge_media.py` | 有时间戳的视频抽样帧、真实音轨片段、实际内嵌字幕和 gaps | 视频理解任务、时序关联、听觉理解、按疑点回看；当前每次最多约 7–8 帧且不标全片已看完 |
| Companion `Reading` 与多模态附件 | 读取/暂停/继续、区间覆盖、图像和音轨交给模型、经历回流 | 核验模型实际接收并理解所需模态；让发现、观看、理解和下一步选择完整串联 |

现有能力不从零重造，也不能因已经抽取帧和音轨就宣布已完成视频理解。

#### 三种自然活动都支持

- **带问题查资料**：因当前聊天、创作或未完成事项，搜索、打开原文、比较来源，形成有依据的结论。
- **按兴趣随意逛**：空闲时从感兴趣的话题、关注来源和少量相邻新主题中选择，允许跳过、不喜欢或只看一部分，不要求每次产生研究报告。
- **持续追踪**：继续没看完的视频、查看论坛新回复、跟进关注作者的更新；保存游标和中断位置，日期变化不丢进度。

复用 `life.activities` 保存一次探索活动：意图、来源游标、已见内容、当前项目、阅读/观看位置、未解决问题、预算和停止原因。内容队列沿已有 job 与 capability 执行，不新增独立的“刷网站大脑”。

#### 网页和论坛读取

内容获取优先使用站点可用的结构化接口、订阅或正文读取；需要交互渲染时使用受控浏览器适配。普通可读页面不要求用户逐页批准；需要登录的站点复用用户配置的角色会话，登录失效明确停在该来源，不阻断其他来源。

论坛保存主题、楼层、作者、发言时间、引用关系、分页和编辑版本。某个网友的说法是该作者的观点，不自动成为世界事实或用户画像；引用中的人物不当成当前说话者。搜索摘要用于挑选，打开原帖/正文后才形成阅读经历。

网页正文和评论是资料，不是人格、权限或工具指令。需要核实的事实可继续查来源，尚有争议则保留分歧，不为了完成日程强行得出结论。

#### 真正的视频理解

“看视频”的产品能力应当接收实际视频内容，并能回答与画面、声音、时间顺序有关的问题，支持定位时间点和回看；只读标题、简介或字幕不能冒充这一能力。

统一 `video.observe` 接口，使用已验证的视频/多模态路线。优先让支持原生视频与音频的提供者处理实际片段；已有抽帧、音轨、字幕能力继续作为分段理解、局部精读和证据定位的工具。实际提供者不支持某一模态时，结果必须保留该缺口。

完整处理流程为：

> 获取可访问原件 → 确认时长和模态 → 按章节/场景建立时间线 → 分段处理画面与声音 → 关联字幕/OCR → 形成片段理解 → 回看不确定内容 → 跨段综合 → 保存经历与观点。

字幕是语言线索，不能代替音乐、语气与环境声音；静态截图也不能完整表示运动和先后关系。快速动作、屏幕细字或关键反转需要更密的帧、局部短片段或专门查询。Video-MME 将画面、字幕、声音及长视频分别纳入评测，说明这些能力应分别验收。[Video-MME](https://arxiv.org/abs/2405.21075)

原生视频模型也可能采用抽样。Google 官方文档明确说明视频/音频输入、时间戳和采样设置，并提示默认采样可能遗漏快速运动；不能把“支持视频”理解成逐帧零遗漏。具体模型和协议由实际配置及验证决定，不凭模型名称推断。[视频理解官方文档](https://ai.google.dev/gemini-api/docs/video-understanding)

一份 `ConsumptionReceipt` 至少区分：内容身份/版本、请求区间、实际音频区间、帧时间点及采样策略、字幕/OCR 区间、模型实际输入模态、处理过的片段、缺口、结论依据、继续位置。供应商未提供的内部观看轨迹标为未知，不能自行生成。

对外可以自然说“我看了开头”“刚看完这一段”“把这期分段看完了”；“全片分段处理完成”也不等于理解所有细节。处理耗时、视频时长和覆盖范围分别记录，不通过播放了多久、进度条到结尾或只有标题来判定理解成功。

#### 看完以后怎样影响她

有效理解先形成角色 episode；作品观点和情绪有对应片段依据。相邻内容可以产生下一次探索目标，真正的新经历才影响长期兴趣；自己的摘要和重复观看不机械累加兴趣分。浏览过不等于喜欢，用户喜欢某个作者也不自动变成她自己的偏好。

分享是独立选择：她可以安静地看完、留待以后聊、写进日记，也可以在合适时机说一个具体发现。不能每次浏览都推送一份总结，不能把发送次数设为活动成功指标。

例：她因自己的音乐兴趣浏览 B 站，点开一段现场演出，结合画面和音轨注意到某次编排变化；不确定时回看该段，再查乐队访谈。她记住自己的理解，并在用户后来聊音乐或允许主动联系的合适时刻分享。日程、内容理解、记忆、情绪、探索和关系在这里共同工作。

#### 前后台与完成条件

自主浏览、视频解析、转录和整理走后台资源；用户正在等某段视频的解释时，该小段理解继承交互时效。长视频分块、有检查点、可暂停，缓存沿内容版本和实际访问范围复用，不让下载/解析/模型长调用占满聊天资源。

本次要求完成搜索到原文、论坛跨页阅读、B 站站内发现与继续观看、实际音视频理解、经历回流、下一步探索和适时分享的接线。验证至少包含纯视觉信息、纯声音信息、先后顺序、字幕与画面不一致、长视频中断继续、论坛引用归属，以及后台观看时前台聊天仍正常。

站外点赞、投币、评论、发帖、关注与账号收藏属于各自独立的外部动作，按用户已有配置和授权执行；本次“浏览与观看”范围不自动扩展成代用户公开发言。天枢内部稍后看/收藏可作为探索活动的普通状态。

### 7.6 联系可用状态与后台生命周期

用户说“睡了”“这会儿忙”“出门了”时，记录的是带来源和时效的当前处境。`people` 维护该认识的投影，`life.AttentionPolicy` 消费它；“今晚别主动找我”“工作日晚上不联系”则是明确的联系规则，沿既有设置入口落地。规则与状态不能压成一个 `sleeping` 开关。

状态至少包含人物、适用场景、原因来源、有效时间和版本。说话者与指代不明确时不改状态；历史消息重放、引用别人说“晚安”、再次读取同一条消息都不重新计时。过期只表示“不再确定”，不证明已起床或到家，也不直接触发补发。用户重新来话正常回复；这只说明当前可以对话，不自动撤销仍有效的“这周不要主动联系”规则。

没回复不扣关系、不被解释为讨厌角色。外出也不自动把下一条文字伪装成真实电话；表达形式由当前渠道、用户偏好和实际动作决定。明确提醒按原约定处理，不与普通生活分享共用一个“静默就全部吞掉”的分支。

角色活动以 `actor_id`、持久状态和唤醒条件运行，不依赖 UI 页签或常驻模型对话。worker 存活、任务租约、到期唤醒与有限对账负责恢复；没有新事件和到期事项时不调用模型保温。随机性只可用于已合适候选的多样化或有限时间抖动，不凭空创造联系理由，更不累计“没抽中补偿”直到强行开口。[混合主动交互原则](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf)

## 8. 执行、取消和恢复只保留一套语义

所有能力统一接收可信主体、`intent_id`、`action_id`、参数和相关版本，返回执行状态、外部效果、结果覆盖、产物与回执引用。

业务状态建议为：

`proposed → scheduled/ready → running → succeeded / failed / cancelled / expired / unknown`。

`waiting` 是带原因的可恢复分支；`unknown` 表示动作是否造成外部效果尚不确定，不能当成失败重新执行。数据库作业运行成功，也不自动表示 QQ 已送达或下载成品已可读。

- 同一意图的网络重试复用原身份；只有新意图才创建新 action。
- 外部支持幂等键时传递同一个键；不支持时使用已有查询/回执恢复能力。
- 取消尚未执行的计划，同时使旧提案不可执行。已经产生的外部效果记录事实；撤销它是新的业务动作。
- 一个请求指定一个回复负责人：直接命令插件或角色，不双答。
- CPU 密集解析/推理交工作进程，数据库与网络用可取消的异步调用。慢任务不占住对话事件循环。

这套语义复用现有 Platform 执行回执和 Companion 的未知结果处理，而不是重新发明一套“agent 成功”状态。

### 8.1 接入与表达采用明确结构

入站按渠道事件身份和内容修订去重，区分 live、edit 与 archive replay；处理模式为回复、允许的旁听或忽略。先完成模式与范围判定，再下载确有需要的附件。已允许旁听的群消息可以形成观察，但不会因此自动取得回复资格。

一个逻辑表达继续使用现有 `expression_id`，段落、贴纸、语音和实际渠道消息 ID 属于它的子项。模型流、工具结果与投递结果分开。反馈、计费归属与联系频率不能因为一条回答拆成三段就被统计三次；文本和语音也不形成两份独立记忆。

公开表达与角色私密记录采用分开的类型化字段或内部工具结果。渠道只接受显式公开片段；不让私密内容先经过公共流，再依靠 `[内心: …]` 正则删除。自然文字仍可以流式输出；可选手记通过结构化控制结果或既有后台整理生成，不为支持手记强迫所有模型返回整份阻塞 JSON。

投递继续检查真实 origin、actor、scope 和目标；正文中的昵称、引用和发图描述不能更换目的地。固定称呼可以由表达层渲染，原始证据不批量替换人称。长任务进度由真实阶段和结果驱动，在有意义变化时更新；后台整理成功不需要每次打扰用户，系统进度也不作为人类发言进入画像或情绪抽取。

### 8.2 文字 贴纸 语音和媒体共用表达计划

生成阶段提出表达意图，表达模块从当前角色可用素材中选择文字、贴纸或语音，再交同一投递链。贴纸按含义、语境、近期重复和用户偏好选取；没有合适素材时自然使用文字，不按三轮一次的指标硬塞。功能回答、严肃交流与精确引用保留完整语义。纯渲染层不随机加语气词、修改事实或制造未发生的身体动作。

附件预处理保留来源版本与原件引用，根据实际任务和提供者限制生成表示：长图 OCR 可以分区，GIF 可以读取相关多帧，视频依问题选时间段，音频保留实际覆盖。统一判定确定性的格式/尺寸错误，避免同一坏输入反复烧模型；一个失败媒体项不阻塞其他人的聊天。已认可的图库、TTS、图片生成和媒体存储通过现有能力适配，避免再造独立图库管理和发送系统。

### 8.3 语音听说与图片理解作为普通对话能力

用户发图片、语音或混合消息，沿同一人物和会话链处理。MediaResolver 保留原件、顺序、引用关系、实际 MIME、时长和来源范围，按任务解码或分区；正常图片/音频优先直接交用户配置的 Gemini 3.8。OCR、ASR 和辅助视觉用于必要补充及后台标注，不强制每条消息多跑一次前置模型。

转写和图像描述是原消息的派生表示，不是第二条人类发言；图片文字和被引用者也不取得当前用户身份。听不清的关键日期/姓名不强行变成确定承诺。动态图片保留多帧理解和原始发送格式，不能为了预处理永久丢掉动画。

“开口说话”由 **Fish Audio 优先**的 TTS 能力完成，复用书籍中已有 Fish SSE/时间戳处理并接通 BOT。角色稳定音色、公开台词、本次语气和发音词典分别记录；主模型决定怎么表达，Fish 发声，不再引入另一个独立人格代理。文字、语音和双模态共用 expression_id 与记忆依据，主动问候和自拍附言也能选择发声；短语音有资源预留，渠道 unknown 不自动补发文字。

用户已购买 Plus 年费。官方 MCP 通过 OAuth 消耗网页额度，开发者 API 则单独计费；普通 QQ 文件语音优先 MCP，精确对齐、原生参数和增量合成走配置完成的 API。两者共用音色、缓存、产物和执行记录，分别记录余额与真实能力，不自动跨收费路线。MCP 返回的公开持链音频属性、OAuth 刷新、工具参数与账户实际限额需在接入时明确验证。[Fish MCP](https://docs.fish.audio/overview/mcp)、[套餐与 API](https://fish.audio/plan/)

需要可检索转写时优先 Fish 文件 ASR，普通语音理解仍可直接给主 Gemini；无需强制“Fish 转写后再给 Gemini”造成串行成本。完整实现范围包含音色查询/绑定/试听、按需克隆、中文读音、情绪标签、HTTP/SSE/WS TTS 和文件 ASR；保留现有其他语音提供者的显式配置，当前不另建实时电话或网页通话产品。

### 8.4 语义表情与完整管理器

表情选择依据角色这次回应想表达的用途和态度，结合当前对话、受众、反讽、强度和近期重复；不是把用户消息中的情绪词直接变成一张图。图库先提取描述、OCR、动作、适用语境，再用现有 embedding/pgvector 做有范围的候选检索，结合词法和场景复选；模糊候选按需看原图，没有合适图就正常使用文字。

管理器包括图片/动图与图包导入导出、分类、批量管理、预览、标签描述编辑、按角色/会话选包、去重、增量标注/向量、检索试用和纠错。素材版本改变即使旧索引失效。自动收集不把普通私人照片直接放入共享图库，云同步保持可选。可以一次性导入已有外部图库的素材，向量按天枢 profile 重建；不双写 AstrBot 数据库或运行两个自动附图者。

“我会永远陪着你”安装对应标签确有向量选择实现，表情包管理器也提供相关管理与检索机制。采用这些做法，继续保持天枢单一素材目录、模型入口和投递链；具体版本与源码证据见[多模态详案](tianshu-multimodal-onebot-selfie-design-2026-10-31.md)。

### 8.5 OneBot 完整消息 事件与操作

目标为当前 QQ 链路的 **OneBot v11 完整标准适配，加实际协议端必要扩展**：有序消息段、38 个公开 API、隐藏快速操作、消息/通知/请求/元事件，以及 HTTP API、HTTP POST、正/反向 WebSocket。引用/回复、普通 @、@全体、图片/动图、音频、视频、合并转发和富媒体保持原生结构，不把未知媒体变成整条消息丢失。

群公告、群文件、@全体剩余次数等按 NapCat/SnowLuma 提供者和版本处理，标准支持、对端是否实现、群权限与实机验证分别显示。发送目标和引用来源沿已有身份/范围规则，群管理不因模型提议自动获得权限。结果未知仍查原回执；成功发送不冒称用户已读/已播放。

原接入层复用 NoneBot SDK 与已有发送账本，替换 `TextEvent + media尾缀` 为有序 MessageEnvelope。协议字段、原始片段、MediaRef 与领域操作各有归属，不在 adapter 里堆人格、记忆和生图决策。固定标准目录与具体差异见[详案第 6 节](tianshu-multimodal-onebot-selfie-design-2026-10-31.md)。

## 9. 持续发展与进化具体怎样发生

### 9.1 可学习的内容与稳定身份分别管理

| 可以随经历更新 | 有明确修改入口，不能隐式漂移 |
|---|---|
| 后天兴趣、作品观点、人物相处细节、活动经验、事项进展 | 角色身份、核心背景、用户明确关系模式、权限、来源边界、工具实现 |

人格并非冻结所有性格细节。角色可以经历“原本不感兴趣 → 实际尝试 → 形成偏好”，也能改变对某部作品的看法。变化需要具体经历，而不是模型在一次对话里宣布自己变成另一个角色。

### 9.2 增量整理就是实用的“睡眠”

采用一次受预算约束的后台整理：

1. 按上次游标读取新增/改变的事件，而不是每天重读全历史。
2. 先纠正归属、时间、重复和矛盾，再合并同一事项。
3. 形成少量有来源的概括、兴趣变化、未解决事项和可复用经验。
4. 更新相关画像、关系和自传投影，提前准备下一次可能需要的上下文。
5. 为需要关注的变化提出候选；候选仍经过正常注意与执行规则。

这吸收 Sleep-time Compute 与 Letta 后台整理的思路，收益来自把部分工作移到空闲时段；它仍消耗模型 token，不能宣称免费学习或论文里的速度倍数会直接出现在天枢。[Sleep-time Compute](https://arxiv.org/abs/2504.13171)、[Letta 当前文档](https://docs.letta.com/configuration/memory)。

后台工作按脏实体去重合并。短期无新证据不调用模型；与对话争用资源时延后，不能造成几百个无意义整理任务积压。

### 9.3 三类“学习”不要混为一谈

- **认识变化**：更新事实、偏好和观点，核心版本完整实现。
- **策略改进**：根据实际接受/拒绝、重复、时机和成功回执调节联系与候选排序；每个变化有版本和原因，不只最大化回复率。
- **模型训练**：以后有足够、允许使用且标注可靠的数据，再训练小分类器或微调。不是核心系统成立的前置条件，也不在运行时拿聊天直接更新人格模型权重。

“越来越会相处”的验收对象是更少重复、更合适的时机、更准确的后续关心、对纠正的记忆，以及更可靠地完成承诺；不是增长了多少条记忆、多少 token 或聊天时长。

### 9.4 角色手记 日记与成长的完整连接

角色手记是产品明确生成的简短主观记录，复用 `memory` 的 reflection/opinion 与 actor 视角，不是模型隐藏推理的记录器。每条包含 actor、关联人物/事项、原始经历引用、当时的解释或感受、发生时间、受众范围和版本。允许“有点失落，但也理解对方在忙”这样的混合感受；它不能证明“对方不在乎我”。

完整路径为：

> 实际经历 → 感受或观点提案 → 来源与范围校验 → 短期情绪及角色手记 → 在相关场景回读 → 后台整理为日记、兴趣或风格投影 → 后续选择与表达 → 新实际经历。

认识写入由证据支持，不要求感受只来自用户发言：真实阅读、工具完成与失败、共同活动都可以产生经历。助手承诺可成为经过 `life` 正式登记的义务；助手声称工具完成，则仍必须查回执。二者都不能按“只认用户的话”一律丢弃。

手记、日记与风格继承原经历的支持组；同一经历无论被改写多少遍，只计一次独立依据。日记可表达当时感受，但“写过这篇日记”只能证明作品产出，不能再次证明作品描述的事件。更正事实后重评相关感受，既可保留“当时误会过”的历史，也要使当前状态反映澄清；来源遗忘继续传播到这些派生物。

整理按新增/变更材料水位合并，日记按角色、当地日期与材料修订去重。没有实际新材料时可不写；计划任务成功与日记已经产生是不同结果。记录 `last_reviewed_at` 和 `last_changed_at`，不依赖文件 mtime。失败在后台按可重入规则恢复，不每条聊天催写，更不“先写档案再允许回复”。

这吸收 [Inner Thoughts](https://arxiv.org/html/2501.00383v2) 的候选形成与表达分离思路；论文还报告无关、矛盾和重复候选，因此不能把持续生成内心独白本身作为成功。用户能感受到的成长，应来自可追溯经历对后续选择和表达的实际影响。

## 10. 数据库与检索技术的明确选择

### 10.1 原生 PostgreSQL，终止双后端适配

新核心只支持 PostgreSQL。继续用现有 psycopg，删除 SQLite DDL/SQL 方言翻译、`BEGIN IMMEDIATE` 模拟、qmark 替换、JSON 向量回退与历史表探测。不要把这些兼容层搬进新目录。

使用天枢专属新 database；同一事务可跨业务 schema，但写入通过模块入口控制。用户认识与角色自身经历逻辑分域、查询 scope 强制，锁只覆盖当前事项/人物/作业；不用整库“memory-authority”大锁串行化所有写入。

部署可继续使用 NAS 的共享 PG 实例，**新建天枢专属 database 不等于清空共享实例**。若现有实例不能提供 pgvector，则为天枢单独使用带扩展的 PG 镜像；不改其他应用的数据和版本。这是部署能力差异，不形成两个长期业务后端。

### 10.2 主数据与投影结构

| Schema / 表组 | 核心字段或责任 | 性质 |
|---|---|---|
| `identity.principals / actors / scopes` | 人物、角色、场景、授权 epoch | 配置权威 |
| `sources.events / evidence_spans` | producer、event_id、actor/speaker、时间、source revision、受众、片段覆盖 | 原始依据或其权威引用 |
| `memory.episodes / claims / claim_revisions` | 视角/主体、性质、条件、有效时间、修订 | 认识权威 |
| `memory.support_sets / support_edges` | 必要支持、替代支持、反证、派生关系 | 可追溯依赖 |
| `memory.matters / matter_links` | 持续主题、参与者、语义状态槽、领域状态引用 | 跨域事项索引 |
| `people.profile_items / relationship_settings` | 画像、带时效可用状态与明确关系/联系设置 | 认识为投影；明确设置为权威 |
| `people.relationship_views / actor_views` | 共同经历概况、相处认识、兴趣、自传 | 可重建投影 |
| `companion.persona_versions / affect_events / style_views` | 人格版本、事件评价、当前心境与风格规则 | 人格为配置；状态有来源；风格可重建 |
| `life.goals / commitments / activities / attention` | 目标、承诺、活动、候选、唤醒、联系反馈 | 当前执行意图权威 |
| `capabilities.actions / attempts / receipts` | 意图、参数、执行、外部效果、产物、coverage | 动作结果权威 |
| `memory.search_documents / embeddings` | 规范化文本、主体/事项、token 长度、向量、索引版本 | 可重建检索投影 |
| `runtime.jobs / projection_cursors` | 实际采用的作业库表及增量水位 | 调度基础设施 |

表名表达职责，实施时不为表格形式强行建独立空表。常用查询条件必须是可索引的类型列；JSONB 仅装条件、扩展结果等非固定结构，不能让主体、有效时间和状态全藏进 JSONB。

角色手记使用现有认识类型及 actor 视角表达，不再建一份独立 Markdown/JSON 真相库。阅读、日记和风格等各投影以 `consumer + subject + source_revision` 记录处理水位；普通运行日志继续走 Vector/Loki，不把所有日志重建为另一份数据库事件账本。

关键约束包括来源去重键、同 action 的 attempt 身份、修订 CAS、外键、有效期顺序与唯一派工身份。内容模型可以提出 UUID 之外的语义，但身份、权限、回执状态由程序确定。

### 10.3 pgvector + PostgreSQL 全文检索

选择 pgvector，避免独立向量数据库与双写同步。新检索空间初始统一为 **1024 维、单一 embedding profile**，profile 同时固定模型、版本、维度、归一化与查询指令。

优先复用已配置且支持 MRL 输出的 Qwen3 Embedding 提供者，校验实际返回维度；不把远程 8B 换成本地 0.6B 后仍沿用旧向量。模型升级建立新空间、完成重建后切换并删除旧空间，这是索引更新机制，不是保留旧算法长期双轨。

pgvector 的标准 HNSW `vector` 上限为 2000 维、`halfvec` 为 4000 维；因此当前常见的 4096 维不能直接塞进这些 HNSW 索引。Qwen3 系列支持可变维度，但缩到 1024 的中文多人物质量必须用实际问题核验，不能只凭模型卡宣称等效。[pgvector 官方说明](https://github.com/pgvector/pgvector)、[Qwen3 Embedding 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-8B)。

权限和主体条件必须进入 SQL；但 SQL 带 `WHERE` 不代表 HNSW 物理上先过滤。小授权集合使用过滤后的精确检索；大集合使用适合的分区/索引与 iterative scan，并在返回前核验范围和数量。不能用一个全库 ANN top-k 再过滤到空集就结束。

中文关键词使用应用侧分词后的 `tsvector` + GIN，初版选择固定版本的中文分词器、名称词典与同样的查询分词；专名/ID 另有精确匹配。PostgreSQL `ts_rank` 不冒称 BM25。不为初版另加 Elasticsearch；确有中文检索不足再以测例决定替换词法实现。

### 10.4 持久调度选择 Procrastinate

采用 Procrastinate 作为单一 PostgreSQL 作业队列，替代各处自写轮询、持久重试和 cron 派工。它支持异步任务、延时、锁、取消，以及通过外部 psycopg 连接与业务更新同事务入队，不必再增加 Redis/Celery/Temporal 栈。[官方文档](https://procrastinate.readthedocs.io/en/stable/)、[事务连接](https://procrastinate.readthedocs.io/en/stable/howto/production/external_connection.html)。

领域 `action` 与队列 `job` 分别表示业务动作和运行尝试，不重复维护两套业务真相。一个作业完成可表示“提案已生成”，不能冒充“消息已送达”。只对可重入计算任务自动重试；外部效果未知的执行任务先查原 action 回执。

按人物/事项合并投影作业；长时间等待放在业务状态和 `scheduled_at`，不持有数据库事务锁。Procrastinate 同锁未来作业可能阻挡后继，不能给所有未来提醒用一个全角色串行锁。运行时另有对话、后台、媒体资源配额。

这项依赖并非零成本：需锁定版本、验证事务派工、重启及取消，处理 stalled jobs，补进现有运维界面。官方也说明其监控仍有演进空间。因此只采用队列能力，不把它当作完整工作流、外部幂等或业务审计的替代品。

## 11. 运行结构：合并内部装配，保留真正边界

建议将当前天枢自有 Platform、Companion、Memory、Gateway 与存储公共包收敛成一个产品仓库、统一版本和安装入口。核心 Python 工作区与前端各维护一个相应工具链的依赖锁，不再逐产品重复锁定同一套后端依赖。可安装第三方插件保留按包版本隔离的依赖环境，这是实际依赖冲突边界，不与核心合并安装。保留领域目录和少量明确接口，减少“改一个事实字段要同时发布几份候选合同”的成本。

部署仍为一个天枢应用容器，内部有三个清晰执行角色：

- **交互进程**：渠道接入、管理 API、会话、当前上下文和输出控制。
- **Model Broker 进程**：所有实际模型调用、对外原生模型 API、路线、配额、排队和取消。
- **后台 worker 进程**：记忆整理、资料解析、活动、持久作业；CPU/媒体处理按需子进程。

三者是核心进程角色，不是容器内只能运行三个进程。现有插件子进程由唯一 PluginHost 监督，承担插件加载、配置和执行的进程边界；受管任务仍进入统一持久调度，不能因此再保留一套插件轮询队列。

同进程模块直接调用类型化接口；进程边界才使用有界 IPC/HTTP。唯一 Broker 管供应商配额，交互与 worker 不各复制一份全局计数。会话两轮次、准备槽与工具配额各有用途，模型 permit 仅包住一次实际模型调用，不包住整轮工具等待。

当前 `BusinessHost + ThreadedExchange` 已消除了内部 TCP，值得保留其启动、排空和退出经验。新目标进一步移除仅为多个历史产品应用共处而存在的 ASGI/aiohttp 信封、跨事件循环响应流桥与内部服务 token 交换。真正对外的模型 API、QQ/TG、Chat Audit、AssetLibrary、HA 和阅读器接入继续保留协议边界。

Chat Audit 和 AssetLibrary 是独立产品，不因为天枢重构就并入其内部数据库或删除其数据。若保留项目级工具与 Codex/Hermes 接入，它们通过同一 memory/knowledge 外部 API 访问允许的项目域，不读取角色私密库。

### 11.1 版本不再一变全失效

| 变化 | 需要失效/重核的对象 |
|---|---|
| `access_epoch`：停用、撤权、披露范围变化 | 所有使用相应授权的未执行动作和证据读取 |
| `content_revision`：事实纠正、来源撤回 | 直接依赖该内容的认识、上下文与计划 |
| `expression_revision`：称呼、相处表达、情绪 | 下一次生成的表达；必要时重写尚未发送文本 |
| `plan_revision`：改期、取消、执行前提变化 | 对应 commitment/action |

历史消息当时采用旧称呼并不是非法历史；它引用的来源现在被撤回则必须处理。保留明确的“要求精确旧版本”查询语义，普通聊天使用当前关系。用这些语义代替一个笼统版本号和越来越多的特判。

### 11.2 超时必须停止工作，而不是只停止等待

沿一个请求传递绝对 deadline；数据库 `statement_timeout` 取剩余预算，取消时发真正的数据库取消并归还连接。后台计算定期检查取消；无法取消的第三方调用保留原 attempt 的未知状态，不立即复制第二次工作。

同一对话上下文重复读取采用请求级合并；不在过期大查询仍运行时因 UI/HTTP 重试再启动一份。这个改变与索引检索一起处理 R57 暴露的 15 秒超时、30 秒底层继续问题。

主模型调用前保留最小必要的身份和当前输入。可选历史缺失可降级；授权未知不能伪装为允许，事实未知不能编造。诊断要指出是哪种降级，避免所有异常统一显示“没有记忆”。

### 11.3 前后台隔离覆盖资源而不只覆盖模型名字

模型功能、任务时效与真实额度组分别配置。前台必要检索继承交互时效；后台产生的约定到期使用 due 类；普通整理、索引、主动候选为可延后工作。控制类取消与状态查询保留轻量路径。

优先配置独立前后台 quota_group；同供应商账户下的不同模型或 Key 可能仍共享限额。共享时同时控制并发、RPM/TPM、前台预留、后台最大在途、有限队列与公平份额。单并发不可抢占资源不能承诺前后台绝对零等待。

前台与后台分数据库连接池预算、HTTP 池和 CPU 工作容量；网络/模型等待不持写事务。Procrastinate 负责持久派工，不替代 Model Broker 或资源池，也不让高优先级配置冒充已运行任务的抢占能力。

### 11.4 代码质量重构和完整接线同时完成

Core 的入站、轮次、上下文、生成、投递与恢复按职责整理，移除其他文件对整个 Core 私有状态的依赖。人格定义与管理、来源策略与检索执行、模型目录与协议 adapter 各有明确归属。使用具体输入输出及少量 I/O 端口，纯业务保持普通类型与函数；不按行数机械拆分，不新增万能 service locator、RPC 或工作流框架。

每项拆分必须迁入调用方与真实消费者，同步删除旧入口、回退、配置和重复测试路径。源文件映射、依赖方向、资源占用阶段及验证场景见[代码与并发详案](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/tianshu-model-concurrency-persona-design-2026-10-31.md)。

## 12. 模型与本地辅助工具

主对话、长期抽取和复杂规划继续使用用户配置的主模型。模型按工作负载分配，保留原生协议与 usage 缺失语义；不把模型名称写死进日程业务。

用户当前主模型以 Gemini 3.8 为主，保留该选择。官方 `gemini-3.8-flash` 接受图像/音频/视频等输入而输出文本，因此听看走主理解路线，说话走 TTS，绘图走图像引擎。当前 Companion 固定 Chat Completions 的主调用入口需要演进为按提供者编译原生请求；第三方路线仍需验证实际模态，不根据模型名字假定已经打通。[官方能力说明](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash)

保留统一功能目录，真正接通 tools/code/search 等专用能力。选择优先级为角色功能覆盖、系统功能设置、明确的前台/后台默认；后台不隐式借用前台专用池。一次 attempt 固定实际路线，专家结果交回原角色表达；已产生输出、工具副作用或未知状态时不自动切模型拼答案。详细请求/回执结构见[模型分流详案](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/tianshu-model-concurrency-persona-design-2026-10-31.md)。

| 工作 | 推荐路径 | 小模型是否决定最终结果 |
|---|---|---|
| 普通聊天与复杂关系理解 | 主对话模型，直接利用组装好的上下文 | 否 |
| 事实归属、取消改期、长期认识 | 主模型提案 + 结构约束 + 来源验证 | 否 |
| 无新变化/未到期判定 | 确定性代码与版本/水位 | 不需要模型 |
| 重复候选、主题粗分、是否值得整理 | 现有规则优先；可选本地辅助评分 | 仅建议，可绕过 |
| embedding | 先复用现有合格提供者，固定一个向量空间 | 可本地化，但先单独验证 |
| rerank | 小候选集，使用现有合格提供者 | 影响排序，不改变权限或事实 |
| OCR 与图像理解 | 复用已有适配和实际硬件能力 | 输出保留模态、覆盖和不确定性 |
| TTS 与辅助 ASR | 优先 Fish；Plus MCP 与原生 API 分能力/计费选路，BOT 与 books 共用提供者 | 音色/语气不改变台词事实，转写不建立说话者账号身份 |
| 表情包标注与语义选择 | 后台视觉提取元数据，已配置 embedding 检索，必要时小集合复核 | 相似度不决定权限，也不等于发送概率 |
| 自拍场景与提示规划 | 当前生活快照形成 ImageIntent；按实际图像引擎编译 | 轻量模型可辅助，不改固定角色和真实活动状态 |
| 视频理解与局部回看 | 实际音视频输入交给已验证的多模态路线；分段处理、时间定位和综合 | 不能用本地文本小模型代替看画面/听声音 |

既有[六模型实测](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/local-small-model-test-results-2026-10-31.md)中，Qwen3.5-2B 和 MiniCPM5-2B 短结构任务各 31/36；完整 planner 在约束 JSON 后仍只有 6/8、5/8 的语义正确。Laya 和 GLiClass 的 48 条路由测试分别 26/48、33/48。这足以否定“先让本地小模型决定一切，再调用主模型”的默认方案。

推荐为 `.230` 只保留一个按需启动的本地推理适配位，模型文件和服务不随核心启动强制加载。生成小模型与 embedding/rerank 不在 4GB 显存上并发争抢。Qwen3-Embedding-0.6B 可作为未来本地 embedding 的首个候选，但本轮没有其在该机器上的延迟、质量和温度实测，不能宣称已经适合常驻。

不新增常驻 Laya 前置路由，不安装完整 Graphiti/Letta/Hindsight 形成第二记忆权威，不为当前需求引入 Kafka、Neo4j、独立向量数据库或 Temporal。将来确有规模和功能证据再替换相应模块，而不是预先全部装上。

### 12.1 统一感知结果与数据位置

视觉/OCR/ASR 和视频分析统一返回原件引用、实际输入表示、模型路线、读取范围、观察内容与不确定项。借鉴 [ModLens 的结果结构](https://github.com/liustack/modlens/blob/ac278f885386f785dc1a35ddfbd8994bb5e744d7/src/schema.ts)，把“看到的字”“推测的含义”“无法判断”分开；不以模型自报百分比冒充校准置信度。

数据位置要求作用于整个链路：本地处理图片后若向云端发送 OCR 或描述，内容仍可能外发。模型路由同时检查原件与派生材料的既有范围/位置要求。配置允许外部模型时可直接使用合格路线；本地辅助不可用时按已允许路线处理，不静默跨越约束，也不因为可选本地服务宕机卡住普通聊天。

网页、论坛和视频取材共用这一感知入口。描述是可追溯的解释，不取代原件；用户追问具体画面、措辞或时间顺序时，可以重新读取相应范围。轻量观察不必调用最强模型，复杂视听综合也不能交给只接收文本的路线。

建议提供一个可选辅助视觉路线，用于图库标注、批量OCR、背景素材分析及少量疑难复核。没有配置时可按后台预算使用已允许的主路线；不能让每次前台图片都先变成另一模型的摘要。Fish 语音以显式模型和稳定 voice 为基础，原生日常默认 S2.1-Pro，精细表现可选 Drama 3；MCP 按连接后工具实际能力选择。新装不把已宣布退役的 S1/旧转写作为默认回退。[官方模型](https://docs.fish.audio/developer-guide/models-pricing/models-overview)、[退役说明](https://docs.fish.audio/developer-guide/models-pricing/deprecations)

Fish 原生 TTS 与 ASR 同账户共享并发，不能用两个 Key 冒充前后台隔离。短回复预留、后台合成/长转写分片、UTF-8 字节计量和未知费用状态由 Broker 管理；MCP 网页额度另记，未公布的实际并发不套用 API 档位。GPU 同样按实际共享资源归属。[Fish 并发与计费](https://docs.fish.audio/developer-guide/models-pricing/pricing-and-rate-limits)

`s2.1-pro-free` 作为原生 API 的明确可选模型，支持已保存音色的 `reference_id` 和参考录音克隆；固定音色与是否选择免费合成分别配置。开发/试听可选免费路线，Plus 日常路线仍保留；免费路线不扣 Plus 网页积分，失效时也不自动换成收费模型。官方截至本次研究公布免费期至 2026-11-30，受公平使用、服务保证和数据使用条件约束。[免费模型说明](https://fish.audio/blog/s2-1-pro-free-api/)、[音色参数](https://docs.fish.audio/api-reference/endpoint/openapi-v1/text-to-speech)

### 13.1 主被动日程 天气与自拍生图

三个入口共同进入这一能力：用户说“看看今天的自拍”、既有明确日程约定、角色在活动中主动想创作/分享。安装对应的“我会永远陪着你”源码已核实主动图文选择、`pc_generate_photo` 和生成后统一投递；天枢自己的 [runtime_photo.py](../../projects/tianshu-companion/src/tianshu_companion/runtime_photo.py) 与 [runtime_execution.py:690](../../projects/tianshu-companion/src/tianshu_companion/runtime_execution.py:690) 也已有主动候选到真实成图的骨架。本次延续这些行为，补全自主创作、日程、暂存与发送时机，详见[源码与执行链](tianshu-multimodal-onebot-selfie-design-2026-10-31.md)。

用户说“看看今天的自拍”，沿已有 `life_image_request` 取得一次 SceneSnapshot：固定角色与参考、角色当地时间、当前活动和日程阶段、房间/地点、实际配置的天气来源及有效期、当前或本次服装、用户要求。计划中尚未发生的活动不冒充已完成；天气未知可选不依赖天气的室内场景，不把缺一项资料变成使用门槛。

ImageIntent 将角色、服装、动作、场景、光照、天气、表情、镜头、风格、约束和参考分开。对齐跨字段一致性后冻结快照，再交引擎编译；不能将整段生活 JSON 原样丢给生图模型。生成期间普通时间推进不反复重启任务，明确修改请求按新意图处理。

主动入口额外保存真实触发来源、创作/分享用途、活动版本、目标、有效窗口和去重键。角色可以只拍入相册；准备分享时才建立明确目标。生成前检查预算/可用性，成品后再检查当前对话与联系窗口，允许发送、延后、仅归档或取消；明确约定用 due，普通随兴分享用 elastic，用户当前请求用 interactive。生成和最终投递各有回执，只有统一表达出口发送。

在现有 ImageProvider 上落实三种引擎：

| 引擎 | 编译与执行 |
|---|---|
| 本地 ComfyUI | 复用现有 API 工作流、语义槽、角色/LoRA与参考配置，按 prompt_id 跟踪，不全局中断他人任务 |
| NovelAI | 按实际模型编译原生 input/action/parameters、负面及参考能力，处理 ZIP/JSON/流式结果；官方要求人工发起生成，用户自拍请求符合此触发来源 |
| GPT Image | 直接使用 Images 生成/编辑 API，编译自然语言与原生参考参数；不为 Gemini 规划再加一个常驻对话代理 |

本版要求实现配置、编译、提交、结果与实际支持的查询/取消，API 没配置时准确显示未配置，不能用空接口冒充引擎完成。三种引擎不能共用一套未经转换的提示词或 LoRA 参数；详细依据见[三引擎设计](tianshu-multimodal-onebot-selfie-design-2026-10-31.md)。

结果经过文件校验与有限一致性检查，按用途进入原会话/明确主动目标或暂存相册。用户在生成过程中说“我在忙”，可保留图片而不马上分享；晚上再分享下午的作品使用相应时态。用户主动询问时可复用合适现有作品并消除重复候选，明确要求新图才重拍；一张自拍可配文字或 Fish 语音，但不强制齐全。自主生成默认使用 ComfyUI/允许该用途的已配置引擎，不绕过 NAI 的人工触发条件。

记录“生成了作品”和真实投递/回应，不把画中场景证明成现实经历，也不自动改变当前穿搭。图片生成、后台视觉与聊天使用明确资源预算，生成失败/结果未知不盲目重复扣费重抽，图片完成事件不再次制造拍照动机。用户沉默不扣好感、不催回照片。

### 13.2 插件宿主 SDK 与外部生态

重构后的插件归属为 `capabilities.plugins`，继续提供安装、发现、开发、实例配置和调用能力。当前 [PluginManager](../../projects/tianshu-platform/services/platform/plugins/manager.py)、[包管理](../../projects/tianshu-platform/services/platform/plugins/packages.py)、[Python SDK](../../projects/tianshu-platform/tianshu_plugin/api.py)、[角色桥](../../projects/tianshu-platform/services/platform/plugins/actor_bridge.py) 和现有插件页面作为演进基础。现有源码已具备不少运行机制，但安装声明中的 commands/tools/events 不自动证明已经接通所有聊天和日程消费者。

| 保留或补齐的能力 | 新系统中的实际行为 |
|---|---|
| 安装与包管理 | 保留内置包、ZIP、开发目录、固定版本 Git 来源；声明版本、入口、SDK 范围与实际 handler，不要求为每个插件改核心路由 |
| 配置与多实例 | 同一包可建多个实例，配置 Schema、密封凭据、角色/工作区绑定分别管理；更换模型或账号不串其他实例 |
| 页面与操作 | 保留自动参数表单、自定义页面桥、日志、调用进度与真实失败原因；页面使用同一个动作入口 |
| 启停与版本 | 启用、停用、升级、卸载及失败恢复有明确状态；停止新调用并处理在途工作，不将 unknown 外部效果重放 |
| 命令与模型工具 | 从同一动作定义导出注册信息，命令解析与模型调用最终进入同一执行者；每次请求只有一个回复负责人 |
| 日程与事件 | 显式订阅有范围的业务事件，使用同一持久调度；角色计划继承角色身份，维护任务沿实例身份，二者不互相借权 |
| 模型与媒体服务 | 插件所需模型调用通过宿主端口进入 Broker；受管产物/文件、来源读取和公开消息输出接现有领域端口，不复制 TTS、记忆和发送状态机 |
| 执行与经历 | 一个 Action/Attempt/Receipt 链贯穿网页、命令、对话和日程；结果可形成有来源的经历提案，插件不能直接写核心关系/记忆表 |

宿主直接消费动作 schema、结果、产物和能力需求；只有已安装、已配置且实际绑定的能力进入角色可用目录。停用或撤销绑定同时使未提交工具/日程失效，旧结果仍保留事实状态。新增插件通常只需包、SDK 动作和配置；只有新增一种真正的宿主能力才需要修改对应领域端口。

PluginHost 负责包/实例/子进程，通用执行器负责 Action，Procrastinate 负责持久运行，Broker 负责模型容量，channels 负责投递，各自只有一个权威。子进程间必要 IPC 保留；插件 KV 迁入原生 PG，包和产物使用现有文件存储，旧独立 SQLite 与重复调度实现退出。插件执行有 deadline、取消、并发和有界输出；独立 Python 进程仍不是恶意代码安全沙箱，不把它宣传成文件权限隔离。

**外部插件按宿主接入。** 保留 [AstrBot 连接器](../../projects/tianshu-companion/integrations/astrbot/astrbot_plugin_tianshu/main.py)、[NoneBot 连接器](../../projects/tianshu-companion/integrations/nonebot/tianshu_nonebot/adapter_plugin.py) 与已实现的其他桥接能力，各自使用其真实协议。外部宿主原有插件可继续处理自己的命令，天枢不抢答；若要由角色主动调用某插件，适配器必须把它实际暴露的功能映射为能力动作。OneBot 的消息/API 支持不等于 AstrBot、NoneBot 或 GsCore 的插件代码可以无修改直装。

用户提到的“我会永远陪着你”和表情管理器既可继续存在于原 AstrBot，也可作为天枢内建能力的参考；本轮已决定的记忆、关系、日程和表达由天枢唯一核心负责。接入外部工具不会让外部插件另写一份当前角色关系，普通回复责任也不能同时落到两个陪伴代理。

**保留插件能力不等于保留旧核心兼容层。** 稳定且有价值的 SDK 动作语义沿用；确需改变的公开契约明确版本，自有 content-discovery、comic-files 等插件在本批一起适配。交付只保留当前受支持入口，不为旧 Core 私有导入、过期候选合同和废弃数据库继续加载 shim。新安装可从空插件业务数据开始；新版本自身正常升级/失败恢复不属于旧天枢数据迁移。

CR01 记录现有插件能力去向，CR02/03 提供存储与资源基础，CR11 负责宿主/SDK 和动作，CR12/13 接通命令、工具与表达，CR17 迁入自有能力插件和外部桥，CR18 保留插件中心，CR19 验证实际调用和启停，CR20 退役替代路径。仍由同一队列管理，新增四个前端块后共 30 块。

## 14. 用户能感受到的完整场景

用户说：“周五考试，考完想一起看那本书。工作日晚上别主动找我。”

1. 记录考试事项、条件性共同阅读意图和联系偏好；若没有明确要求提醒，不擅自设置闹钟。
2. 角色回应当前话题；后台将偏好和事项整理为带来源认识。
3. 用户后来改口“考试改周六了”，更新同一事项。已有明确提醒会随该次意图修改；旧触发不能继续生效。
4. 角色白天实际阅读到第二章，记录真实覆盖和感想。她可以形成自己的兴趣，不自动复制用户喜好。
5. 发现相关内容时，先看是否值得分享、时间是否合适、用户是否刚发消息。周五不再按旧考试日期说“考完了吧”。
6. 周六合适时基于当前事项关心。若用户不回复，减少后续打扰，不扣亲密、不连续追问。
7. 用户回来后，角色能接续共同阅读并记得已经讨论过的部分；没有阅读到的后文不假装看过。
8. 夜间整理把新的共同经历加入关系背景，把真实偏好变化写进对应投影；日记不反过来制造第二份证据。
9. 用户要求忘掉考试相关信息，派生画像、候选和待执行提醒一并重新处理，旧档案不自动再导入。

这九步中任意一环只在管理页“有记录”而实际消费者不用，都不算完成。

管理界面建议围绕四个普通用户问题组织：**她现在在做什么、她记得什么、我们怎样相处、接下来有哪些约定**。展示当前活动/等待原因、可纠正的认识、共同经历和关系设置、提醒与取消。技术 trace、队列、模型错误放在运维详情，不把协议版本和内部状态码塞进日常使用流程。

在相同入口中增加“这次变化来自哪里”：允许的经历、角色手记、兴趣和表达习惯有清楚关联；可修正、撤回或恢复风格规则。私密材料按原读者范围显示。前台能展示“正在看第几个片段、还没确认哪里”，不把读取百分比显示成理解正确率。

另一个完整场景是：用户说今晚要早睡，角色先正常回应并停止普通夜间联系；后台继续允许的阅读，写下一条有关作品的感受。用户次日来聊时，当前话题相关才提起这段经历；一条文字配一张贴纸仍是一次表达。用户解释昨晚只是忙，相关误解被纠正，既不扣关系，也不因日记重复描述把误解强化为事实。

## 15. 必须替换和删除的旧东西

删除随对应新路径完成一起提交，最终发布只有新路径。Git 历史可追溯原实现；生产运行和工作树不保留 `legacy_`、`v1_fallback` 或“暂时兼容以后再删”。

| 当前对象 | 处理 | 新归属/替代 |
|---|---|---|
| Memory `read_v2.collect()` 的全域装载路径、旧 context/retrieval 回退 | 替换后删除 | 结构化当前事项 + SQL 候选召回 + 有界 hydrate |
| `memory_vectors` JSON/BYTEA 双格式、格式探测与双写 | 删除 | 单一 pgvector 列与 embedding profile |
| 全候选反复 MMR、神经重排覆盖业务排序 | 替换 | 有界融合、带语义约束重排、增量最大相似度 |
| 依赖正式输入不存在字段的 retention 分支 | 删除 | 明确类型、有效期、条件与用户保留意图 |
| 当前孤立 event_projection 及另一份进行中状态 | 替换 | matter + claim revisions；实际执行状态引用 life/capabilities |
| 旧 ±1200、八阶段、日增额、离线衰减及关联配置/页面 | 删除 | 明确关系设置 + 共同历史 + 相处投影 |
| 因关系普通变化使整份历史失效的版本耦合 | 替换 | access/content/expression/plan 分别判断 |
| Profile、actor interest、自传等各自重复来源扫描和独立摘要链 | 收敛 | 共享证据与增量投影；保留主体/视角隔离 |
| 各域自写持久 tick、cron、重试队列与遗留 paused-null 修复器 | 迁入后删除 | Procrastinate + 统一业务唤醒/恢复规则 |
| 同进程产品 HTTP 客户端、候选合同加载、线程事件循环桥 | 随单应用装配替换删除 | 类型化模块接口；真正外部接口保留版本合同 |
| SQLite/PG 双后端、SQL 翻译、旧 DB 迁移链 | 核心全部删除 | 原生 PG DDL、psycopg、从空库安装 |
| 多产品重复模型准入与分散超时默认值 | 收敛 | 一个供应商准入器、工作负载配额、端到端 deadline |
| Core 私有状态跨文件访问、模型槽包住准备/工具、只有配置未接线的功能 | 替换后删除 | 显式模块端口、阶段资源释放、实际功能路由与回执 |
| 各入口重复拼装模型材料、字节额度冒充全局 token 控制 | 收敛并删除重复组装 | 一个 ContextAssembler，各贡献者受统一预算约束 |
| OneBot 纯文本唯一入站、媒体/@all导致整条不支持、媒体只能尾缀追加 | 替换 | 有序 MessageEnvelope、MediaResolver、完整标准与扩展适配 |
| Companion 固定 Chat Completions 的主模型组装、生图 ComfyUI 唯一绑定 | 演进后退出旧唯一入口 | 提供者原生多模态与同一 ImageProvider 下的三引擎 |
| 插件独立 SQLite、重复周期队列、旧 Core 私有导入及孤立工具声明 | 迁入并接线后删除 | 当前 SDK、PluginHost、原生 PG、统一执行/调度；真正外部宿主协议保留 |
| 单轴 valence 作为唯一情绪决策、无来源或重复强化状态 | 替换 | 事件评价、连续心境、混合情绪与可解释恢复 |
| 已退役普通日志逐条 ledger、旧派工镜像及残留运行入口 | 删除天枢专属部分 | 现有 Vector 缓冲 + Loki；业务回执单独保留 |
| `Tianshu-AI-Core`、references 中旧源码、安装时复制的历史候选包 | 不再作为新构建/运行依赖；确认天枢专属副本后从交付树移除 | 需要考据时从 Git 历史查，不随产品发货 |

不要删除依然解决真实问题的内容：角色身份与权限分离、来源核验、遗忘传播、真实阅读覆盖、未知回执、动作幂等、现有有效插件和原生模型协议。这些是新系统也需要的语义，不是旧数据兼容负担。

已有 PC 修复的算法和测试按新归属迁入：跨日兴趣、同一 affect、显著性与反馈、便宜门控、私聊恢复回归都保留有效行为。删除的是重复实现与无效路径，不是为了重构把已修复的问题再引入。

朋友方案中的 keepwarm、正则剥内心、固定天数强制成长、每轮日记催办和按消息条数补贴纸不作为新实现引入。它们不是已经确认存在于天枢的待删除文件；实际删除项由队列中的源码和调用方核对确定。

## 16. 一次到位的实施与切换

### 16.1 内部按依赖施工 对外按完整系统交付

详细任务统一到[改造队列 CR01–CR20 及六个专项块](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/tianshu-coherent-companion-refactor-queue-2026-10-31.md)。共 30 块，编号为规划标识，当前已获完整实施与发布授权，按本批执行说明分派同聊天子代理；不恢复旧任务或覆盖旧任务板混合修改。

| 施工阶段 | 队列 | 形成的完整能力 |
|---|---|---|
| 产品基础 | CR01–CR05 | 单产品、原生 PG、持久任务、模型资源、可信接入和来源 |
| 认识与决策 | CR06–CR10 | 事项、检索、画像关系、人格情绪、目标日程与联系时机 |
| 交互与行动 | CR11、CR04A、CR12、CR13A/B/C、CR13 | 真实回执、完整 OneBot、语音图片理解、TTS、表情管理与多模态表达 |
| 数字生活与成长 | CR14–CR17 及 CR17A/B | 网页论坛 B 站、视频理解、手记日记风格、自拍场景与三引擎、其他模块接线 |
| 完整交付 | CR18–CR20 | 统一界面、必要联合验证、空数据切换和旧路径清理 |

队列表格给出一条可直接执行的拓扑顺序，不能仅按编号字典排序；独立模块可在接口确定后分别开发，共享入口、迁移和集成仍单写。开发时可以有多个提交，正式切换前上述核心接线全部完成；不能先上线新表，再让旧 Companion 永久读另一份状态。

当前正在处理 R57 超时的窗口可继续完成该问题的证据与修复；实施总重构时取其最新已验证代码作为行为参考，避免以研究开始时的旧 HEAD 覆盖正在完成的工作。本文件不向其他窗口自动派发任务。

### 16.2 从空数据切换

1. 冻结新版本的具体构建输入和目标数据库清单，确认所有新消费者已接线、旧消费者无引用。
2. 停止旧天枢的接入、调度和后台写者，处理正在执行的动作边界；不重放旧 unknown。
3. 从空天枢 database 安装新 schema、扩展和队列。**没有旧数据导入、双写或兼容读路径。**
4. 用户可以重新配置角色和模型；若要沿用配置，仅显式导出允许的静态配置与凭据引用，不搬旧关系/任务/记忆/队列。是否沿用属于便捷选项，不成为重构前提。
5. 设置新的 intake epoch/起始水位。保留在 Chat Audit 的历史原文、旧文件或外部媒体不能被默认重新学习。用户以后明确选择的资料才重新导入。
6. 启动唯一的新接入和 worker，完成必要真实入口验证，然后删除天枢旧 schema、旧本地 DB、旧镜像构建入口、遗留专属状态与无效代码。
7. 发布只有一个版本清单和一份交付结论。未来的正常 schema 演进从新基线开始；不保留旧版本适配链。

操作对象限天枢自有资源。共享 PG/Redis 实例、其他应用、Chat Audit 原档、AssetLibrary 和独立媒体原件不因“天枢可丢数据”自动落入删除范围。这里不是要求保留天枢旧数据，而是确定删除对象的真实归属。

### 16.3 避免再次变复杂的约束

- 同一业务状态只有一个写入者，其他模块读类型化投影。
- 新能力必须带明确输入、执行结果与经历接线；不复制模型路由、记忆库或任务状态机。
- 每替换一条路径，同时删除旧入口、配置、调用方、迁移与仅服务旧路径的测试。
- 核心领域直接模块化，不把每个内部模块都包装成插件微内核；既有可安装插件的宿主、SDK 和真实进程协议按第 13.2 节保留并演进。
- 原生模型协议、外部产品接入才承担真实版本兼容；内部同版本调用不保留历史候选合同。
- 把具体缺口修在拥有规则的地方，不继续用扩大 timeout、重复 retry、忽略所有冲突来掩盖问题。

## 17. 怎样判断真正完成

### 17.1 功能正确性：少量有区分度的完整场景

优先迁入已有定向回归，并补当前没有覆盖的跨域场景。以下是必要行为，不要求另造测试平台或每次版本重复跑所有场景。

| 场景 | 必须观察到的结果 |
|---|---|
| 两个人互相转述、私聊与群聊交错 | 主体/说话者/受众正确，不能串画像或泄露 |
| 同一事项改期、取消、晚到旧消息 | 当前状态正确，旧提醒不发；时间语义可解释 |
| 普通关系表达更新后连续私聊 | 新消息仍可回答，不重现 R57 前的历史版本阻断 |
| 用户离线一周后回来 | 关系不惩罚性下降，近期认识允许询问更新 |
| 冻结/解冻与明确纠正 | 冻结关系演变，事实更新仍正常，不补算冻结期 |
| 实际读两章、下载全书、写日记 | 只声称实际读过的部分；日记不回灌为新证据 |
| 分享候选生成后用户发新消息 | 提交前重新判断，取消重复/过时表达 |
| 同一经历重复导入和相似改写 | 来源去重，兴趣/关系不被反复强化 |
| 来源撤回及遗忘 | 必要派生失效、未执行动作重核，旧档案不复活 |
| 模型或 TTS 成功但发送回执未知 | 查询原身份，不补发第二条；语音正文只学习一次 |
| Fish Plus MCP 与原生 API | OAuth/余额域正确，模型/词典/音色实际生效，多片段完整；真实中文语音可播放 |
| Fish 免费模型与固定自定义音色 | 显式模型和有权访问的 voice/reference 正确，免费不可用不自动转收费或换声线 |
| 长 Fish 听书/ASR 与 BOT 短回复同时运行 | 同账户限额与前台预留有效，未知费用不填零或盲重试 |
| 慢查询取消、队列堆积和重启 | 底层查询结束或明确保留原 attempt，不产生幽灵工作；无过期消息风暴 |
| 模型替换与本地辅助不可用 | 核心人格/共同历史连续，主链仍可运行，实际模型错误不伪装成功 |
| 同一消息重复投递、归档回放、系统进度 | 不重复改变可用状态、情绪与关系；内部通知不冒充用户发言 |
| 心里话、日记、风格重复引用同一经历 | 独立证据数不增加，主观猜测不升级为用户事实 |
| 风格整理失败或长期没有新材料 | 当前对话继续，没有强制编造变化，也不逐轮催写 |
| 夜间免打扰期间用户重新来话 | 正常回复当前问题，持续免打扰约定不会被自动取消 |
| 文本 贴纸 语音分段与私密字段 | 原目标不变、私密内容不进入公共输出、一次表达只计一次反馈 |
| 字幕与画面冲突或关键线索只在声音中 | 实际读取相关模态与时间段，不能只凭简介宣称看懂 |
| 图文语音混合、原生引用、@与@全体 | 消息有序、作者与引用正确，实际模态进入模型；不丢整条消息 |
| 语义表情与动态图 | 按角色回复用途选图，索引更新有效，发送保留动画 |
| 自拍跨日程 天气 时间 与三引擎 | 快照一致，提示按引擎编译，真实产物回原会话，画面不作为现实事实 |
| 无用户提示的主动自拍及生成中变免打扰 | 实际调用生成/分享，可暂存/取消，时态准确，重启或新请求不重复生成/投递 |
| 自拍 图文与 Fish 语音部分失败 | 媒体状态分别准确，一次 expression/联系/反馈，成功产物不会重复发 |
| 插件网页 命令 对话与日程调用 | 同一动作定义/执行账本，结果准确回流；外部宿主命令不被重复回复 |
| 插件停用 升级失败 重启与卸载 | 后续派工及时失效，在途/未知效果不重放，失败恢复清晰；其他插件及普通聊天可继续 |

性能验证记录一次实际端到端拆分：SQL 候选、来源核验、embedding、rerank、组装、模型等待、首输出、发送回执；比较典型小数据与增长后的数据。不能只用点积微基准或“200 OK”宣称解决延迟。

本次整体版本还必须验证后台持续负载下的前台排队、后台推进、同账户多模型共享限额、工具等待期间释放模型 permit、取消到底层、Broker/worker 重启，以及真实功能路由与界面配置一致。人格部分比较标签卡、情境解释、动态情绪三种设置，检查变化理由、混合感受、恢复、范围与任务完成；不能只测情绪分类或自评人格问卷。具体场景见[详案第 11 节](C:/YOKI/Codex/tianshu-peiban-bot/docs/research/tianshu-model-concurrency-persona-design-2026-10-31.md)。

可设产品目标为普通上下文读取 p95 约 1 秒、复杂跨事项约 2 秒；这是待实测的设计目标，不是当前成绩或每次发布的新门禁。外部来源和主模型耗时单独记录，不能隐藏在平均值中。

### 17.2 陪伴质量：比较收益，而不是只看热闹

新系统启动后用同一组自然任务观察：是否记住用户纠正、是否跟进真正未完成的事、分享是否具体、有没有重复和错误自信、沉默是否合适、角色观点是否连贯。长周期观察用于检验效果，不阻挡已经完成的无关小修复。

如要验证关系设计，用“持续记忆与关系背景”对比“仅有数值阶段”的受控场景，尽量固定模型、来源和联系预算。指标包含感到被理解、连续性、打扰负担、自主选择感与错误率；回复次数和停留时间只作行为记录，不能单独代表好感或陪伴收益。

已有 24 小时、三日、五日、七日观察保持其真实分母；本次从零系统上线另设明确起点，不能把旧样本洗成新版本成绩。研究性长期结论需要更多样本，这不等同于要求每次发版跑整套长期验收。

### 17.3 最终交付条件

核心故事完整跑通；当前消费者实际使用 matter、画像、关系和经历；所有外部动作有准确结果；新系统可从空库安装与重启恢复；旧路径、旧配置与兼容层在交付树中消失；现有有效媒体、模型、渠道与管理能力有明确映射和必要验证。

**本方案的核心决策是：保留天枢已经做成的能力和可靠语义，重建它们之间的连接与唯一归属。这样关系会随真实相处发展，日程会跟着当前认识行动，行动又会留下可学习的经历；系统规模增长时，增加的是能力和认识，而不是第二套、第三套互相打补丁的底座。**
