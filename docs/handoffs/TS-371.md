基线 `e18c4b5906a940cb879a9eb1fb1c5781bce6a128`；无产品修改、SSH、PG 实测或预算调整。
固定已装 Platform d214 与 storage 0.1.3 的源码事实：

- `services/platform/service.py:448` 给运行时 HealthInputs 注入的是
  `PlatformRuntime.probe`，复用原 pool/registered handles。`backends.py:66-87`
  对每 handle checkout + binding 校验、`check_schema` 两条查询、metadata 一条查询。
  `ReadOnlyRuntime.probe`（117-143）则每 handle 调用 `open_existing` **新建连接**；不能混称。
- `runtime_health.py:419,433` 的 store 和 sidecars 各调用一次同一 backend_check。
  配置启用 sidecars 时，一次 evaluate 因而可有 2 × 17 完整 storage 轮次，
  另有 web account、合同、静态资源、TLS、日志等检查。
- `Probe.ready` 预算为 2 秒、cache 为 1 秒，超时仍持有真实 worker；缓存 age 按开始时刻。
  每次 evaluate 若都超过 2 秒，晚到结果已过 cache，下一次再检查，表现可持续全 not_verified。
  这不是确认某项 failed，也不能通过增大预算直接洗绿。
- storage `_checkout` 用 options.connect_timeout 等 pool，并把 0.25 秒用于 PG lock_timeout；
  `open_existing` 的 PG connect_timeout 同样来自 StorageOptions，0.25 不等于总查询预算。

## 实际实例的临时 phase trace

root 后续实测：34 handles 无异常，TCP 两轮约 75.10/44.54ms，Unix relay
99.10/82.26ms；重复 backend 的冗余不能解释实际 worker 超过 2 秒。
`diagnostics_config.load_contract` 每次重读、校 hash、构建 validator 并运行正负例，
没有缓存；日志/runtime 又是实际运行对象的 callback，外部 stat 不能测到其锁竞争。

`linux_platform_probe_trace.py` 因此直接包装**原实例**的 Probe 方法，原函数、实参、
返回值、异常、预算与缓存时钟均不替换。只记录 phase、begin/end、单调时间、耗时、
线程 ID、Probe ID、inflight 与异常 class；不记录 settings、输入、结果、消息或凭据。
这属于 test-only 候选启动包装，不修改 site-packages 或发行应用源码。
