# TS-409 日志对账查询超时与满额恢复

基线 `d9e645a01d94b2b896718242dbfc8d6e4070439d`，分支
`codex/ts409-runtime-recovery-20261029`。本卡仅根仓库观测运行代码及其必要用例；
不改 Companion、Memory、容量守护、存储结构或生产配置。

## 原因与修改

协调者在既有生产 owner 内以 10001 身份执行只读原查询：台账10000条、529条
pending全部从未完成核对；原512 pending加512 confirmed组成40102字节请求，
在原10秒截止前未收到HTTP响应，机器原因 `query_deadline_exceeded`。因此原循环
一直在 reconcile 退出，来源证明、退休腾位与refill均未执行。满额本身不直接
使ready失败，不把Loki进程ready误当实际对账查询成功。原诊断证据由协调者持有：
`.runtime/companion-recovery-20261029/read_diagnostic.remote-result.json`。

沿原 Ledger.reconcile 演进：每次选择最多64条，保留pending/confirmed的公平选择，
按现有service索引和不超过一小时的collection时间页分组，所有查询共用原10秒。
已确认记录先复核其已存collected位置，未命中则保守降回pending；未知记录从最近
向过去逐页覆盖原30天，穿插当前页接住晚到日志。源事件timestamp与first_seen没有
被当作Loki collection边界。未扫完的缺席记录继续pending；只有原事件与hash相符
才能确认。已完成页更新原last_checked，失败页不修改核对事实；分组轮转避免一个
失败页永久占据首位。内存页进度最多原max_events条，重启重新查询，不充当证明。

原来源文件、coverage证明、确认前缀、expire/refill、水位和删除outbox规则不变；
原10000条/30天、clear、容量20GiB及鉴权不变，无DDL或迁移。没有读取、清空或
改写生产日志。guard仅在现有异常处理处增加固定stage/reason数值指标，恢复后
清除current；不输出异常原文、SQL、路径、selector、凭据或日志正文。

## R22 实际使用后的局部页修正

协调者已核对真实Vector配置，service标签与模板一致；一个新入台账pending
事件在最近一小时内，无论是否加service索引均HTTP200且0条。这只能说明该
时间页未命中，不能证明日志投递成功或索引错误；来源回填时间first_seen也
不代表中央collection时间。协调者另持有只读实机probe结果。

发现旧confirmed且collected为NULL时，局部页miss会误撤销原确认。现保留原
verified值及其时间，不把部分页完成冒充新ACK；此类记录持续公平参与分页，
只有原hash命中才更新collection，原窗口完整缺失才撤销原确认。已有明确
collection位置的记录仍在原位置缺失后降回pending。重启仅重做搜索，不创建
证明、不删除记录。未改原30天/10000条、来源证明、expire或容量守护。

新增一个固定用例覆盖局部miss、重启、历史命中以及完整窗口缺失；连同已有
明确collection丢失与confirmed/pending公平队列共3项通过。仅这两个变更Python
文件的ruff F/E9与diff检查通过，未重跑全量。真实当前送达/积压恢复仍由
协调者核对，不以ready或空查询宣布完成。

协调者随后只读查到真实最新Loki事件，但它尚未入满额台账，Vector buffer仅
2488字节且guard近期push成功，确认当前送达正常、台账正在历史回填。一个
原pending的occurred小时查询174ms返回1条，原ID与hash均一致，实际collection
比occurred晚约1.63秒；first_seen却比occurred晚约6845秒。实机依据保存在
协调者`probe_hint.remote-result.json`，没有读取或输出日志正文。

因此未知位置首次优先查询原occurred小时；缺失或超出原窗口时可用first_seen
小时。两者仅是一次检索提示，miss后从当前collection小时开始完整原30天
逐页搜索，不排除晚到日志或跳过提示与当前之间的页。仍为原64条批次、10秒
共用截止及每页不超过一小时，不改变任何来源证明或退休规则。

新增一个固定用例，覆盖first_seen远晚于occurred的历史回填首轮hash命中，以及
提示miss后在不同collection小时找到晚到事件。与上述legacy局部miss/重启、
已有明确collection丢失两项合计3项通过；同一变更两Python文件ruff F/E9与
diff检查通过。替身查询通过不替代协调者部署后的真实台账确认与积压检查。

## R23 积压吞吐修正

协调者实机确认真实ACK已恢复，但来源仍有303458701字节未消费。先前把整个
周期限制为64条、pending半池32条，且固定等30秒，形成追赶瓶颈。现恢复原
guard传入的每轮至多1024条；按service/hour分组后，每次HTTP仅64个ID，整轮
仍共享原10秒。confirmed池不足时用pending补满未使用配额，不改原公平顺序。

reconcile返回当轮实际原hash命中数量；只有整个周期成功、初始来源scan预算
耗尽且有真实ACK时，guard才等min(原interval,1秒)继续追赶。空闲、无命中或
任何阶段失败均保持原interval，部分页面成功后的后续失败也不会触发快重试。
原保留上限、30天、clear、源证明/退休/删除、鉴权和生产配置均未修改。

新增一个原1025条来源/1024条cap固定用例，覆盖HTTP64分片与同一个截止、
部分ACK后失败等30秒、成功积压等1秒、空闲回30秒，并检查原源文件字节不变。
连同已有1000/1024条完整/错hash/缺失/饱和及10000条公平队列节点共3项通过
（1.882秒）；四个变更Python文件ruff F/E9和diff检查通过，未扩大验证。

候选单轮只读探针在忽略目录`probe_throughput.remote.py`：仅生产SQLite ro
快照至多1024条元数据，在纯内存台账调用候选reconcile及原LokiClient；整轮
10秒、每HTTP64ID，只投影真实hash ACK与计数，不输出正文/ID/selector。
真实吞吐及后续积压消退仍由协调者运行和核对，不能用本地替身通过代替。
