# TS-364：统一日志保留策略装配与生产者日志挂载

## 范围与基线

基线 `5fc1de93ddffae23622ce5c013d05c771ead26db`，独立分支
`codex/unified-log-retention-projection-20261027`。本卡只改
`deploy/single_container/{plan,installation,compose}.py` 和对应 distribution 测试。
未改四产品 wheel/pin、OneBot/漫画业务账本、NAS ACL、生产配置或历史日志。
未 SSH、部署或运行 Docker。

TS-363 唯一拥有 `deploy.observability.retention.apply_retention`、Loki/guard/ledger
策略和实际原生日志删除；TS-366 唯一拥有宿主状态证据；capture/assembly 由其原负责人维护。
本卡不实现第二份删除或日志捕获系统。

## 实现与使用

- `make_installation(..., retention_days=None)` 和 `export(..., retention_days=None)`
  都调用 TS-363 的原生投影函数。显式参数优先，否则继承
  `files['observability/guard.json'].retention_days`，缺省 30 天。
  guard 是唯一保存的公共天数设置，Loki 的保留/查询/补传窗口由公共函数派生。
  不增加 installation 顶层字段、环境变量或第二个策略源。
- 导出 CLI 支持 `python -m deploy.single_container.installation --installation <input.json>
  --output <new-directory> --retention-days 7`。也可在调用导出前修改 installation 中的
  guard 设置；export 会同步派生 Loki，不修改传入对象。已运行实例的变更应用仍由原发布流程负责。
- `guard.host_state_path` 从同一 `host.json.state_file` 派生为
  `/run/tianshu/host/business-host.json`，用于 TS-363/366 的新实例完整性证明，
  不另维护宿主状态路径。
- `producer_log_mounts()` 只把五个精确 bind target
  `/data/logs/{platform,gateway,memory,knowledge,companion}` 改为 RW。
  原 `/sources/...` 只读观察目录在统一容器内同时有原生产品写入器，继续 RO 会令 append 失败。
  源路径、其他 bind 属性、媒体、数据库及日志根下面单独挂载的只读归档均保持原值。
  不扩大父目录写权，不遍历或 chmod/chown 既有 source；export 仍要求 source 已存在。
- Docker stdout/stderr 保持原 `local` 驱动 `10m × 3`，约 30 MB 环形运行缓存。
  它按容量轮转，不承诺按天保存。没有新增 stdout 文件捕获。

capture 的 receipt 必须保存 **`installation['mounts']`**，不能再保存投影前的
`capture.mounts.values()`；否则后续 candidate assembly 会恢复旧 RO 状态。
此接点已交 TS-366/capture 负责人单写新版本并保留历史 helper/hash。

原生封段命名：Platform `platform-<UUID>-NNNN.jsonl`，Gateway
`gateway-<UUID>-NNNNNN.jsonl`，Memory/Knowledge `<UUID>.NNNNNN.jsonl`，
Companion `companion.jsonl` 后接 `companion.jsonl.N`。它们各有进程内写锁和 close/fsync，
但没有共同的持久封段登记表或跨进程删除锁；Gateway 的 `log.segment_sealed` 事件在新段写入，
不能把它当旧段 footer。Vector checkpoint/EOF 也不能单独证明 Loki 已确认。

因此本卡只提供必要写权与配置，**不把成功导出等同于已安全删除原始日志**。
实际回收要求 TS-363 的封段、稳定身份、已扫描及逐事件完整性证据；活动/未证实尾段、
失败补传和 Vector buffer 仍保留。各生产者有目录容量缓存，是否能在外部回收后恢复接受日志，
应按 TS-363 的真实回收/复查结果验证，不能只看 guard 容量变绿。

### 10,000 条上限的追加装配

`make_installation` / `export` 同时接受 `log_max_events=None`，继承 guard 的唯一
`log_max_events` 主字段，缺省 **10,000**。导出 CLI 为 `--max-events 10000`。
本卡只传入 TS-363 的 `apply_retention(..., log_max_events=...)`；自动保留最旧淘汰、
按天/条数先到先清、`ledger_max_events` 内部准入容量和手动清理统一由 TS-363 拥有。
该函数同步设置 `ledger_max_events=log_max_events`，覆盖 captured 旧内部阈值；
Loki 同时投影 `deletion_mode=filter-and-delete`。本卡不独立解释这些规则。
内部满额停止不是自动清理的替代品。本卡没有在产品中 monkey patch 分段常量或文件句柄。

现候选的五生产者没有公共 rotate：只有 Companion 原配置
`TIANSHU_LOG_SEGMENT_BYTES`（`app.py:111-115`）可调；Platform 的 `Diagnostics`
构造接受 segment_bytes，但原 build_sink/严格 diagnostics 配置未透传；Memory/Knowledge
仅 `Sink` 构造可调、`Diagnostics(sink=...)` 可注入，原业务配置未透传；Gateway
`RuntimeLog` 构造无分段参数，`_plan` 固定 64 MiB。flush 是持久化屏障而不封段，
close/shutdown 会终止原写入器。10,000 条很可能尚未达到 64 MiB，因此只配天数/条数
不能被宣传成活动原始文件也严格只有 10,000 条；需由真实封段/保留实现解决边界。
此事实已同时交协调者和 TS-363，不越权操作 writer 私有状态。
TS-363 随后决定以活动文件连续前缀的持久证明解除对 64 MiB 封段的依赖；
具体可清理范围与异步删除证据以其实现/测试为准，不能把本卡投影测试当作容量实测。

追加后的实际 canonical helper SHA-256 为
`1e0ca716df8d7bddc8d98edc1a56dbdcde7bfdc212a7a4c207d6ded47942cccc`。
使用此真实公共实现重新跑受影响 distribution 套件 **21 项通过 / 0.575s**，

### 手动清理现有入口调查

没有发现统一原始日志管理网页或清理按钮。两个现有“日志”入口职责不同：

- `apps/web/src/features/infrastructure/ContainerInspector.tsx:18-48` 是基础设施容器
  最近 1 小时、最多 200 行/64 KiB 的缓存预览；
  `/api/web/infrastructure/logs` 与 `/logs/refresh` 经
  `services/platform/infrastructure/web.py:90-97` 调用登记节点的 `docker.logs`，
  不能清理 Loki 或五个 raw 目录。
- `apps/web/src/features/plugins/InstancePanel.tsx:367` 是插件实例执行审计日志。
  `plugins/repository.py:234-247` 原来每实例保留 1,000 项、查询返回 100 项，
  `plugins/web.py:146-147` 是只读返回；它不是统一运行日志删除入口。

原 guard 仅 writer/query/metrics 三角色，`guard.py:44-55` 没有删除路由。
不能给 query/read token 增加删除权。当前最小手动方案是复用 TS-363 明确鉴权的管理 CLI，
本机 `docker exec` 读取原观测配置的相应写凭据，由 guard 的唯一管理入口处理。
将来需要网页时，可在原同源管理会话下增薄代理和按钮，不新起管理台或让浏览器取得 guard 凭据。
本卡没有虚构或交付该按钮。

用户另已授权“调整验证后将之前日志全部清空”。协调者单写者将按正式停旧 13 owner、
最新冷备后清理明确 raw/guard log ledger/Loki log state/Vector 旧 queue；
聊天、记忆、日程、配置、业务回执不属于清理对象。本卡不操作任何真实日志，也不声称已清空。
