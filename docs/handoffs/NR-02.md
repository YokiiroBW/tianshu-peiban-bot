## 结果与复用

`memory/generation.py` 复用 Models 的 `generation_profile`、`with_output_tokens` 和现有 ModelRequest。新整理步骤固定实际 route/revision/protocol、原生输出参数和请求时窗；不改 Models 代码或共享作者路由，不影响 Life/reflect 的参数。

DeepSeek Chat 的 `memory.extract` 功能策略使用 `reasoning_effort=low`、`response_format={type:json_object}`，原有 4,096 可见 + 8,192 推理合计 12,288 原生输出额度保持。默认请求窗口为 300 秒。ModelSteps 持久化每一步的时窗，不再把新请求强行截成 120 秒。原步骤的 request JSON、attempt、source_refs 和旧时窗不改。

固定批次最多一个补查步骤、一个输出返修步骤，两个次数分别持久化，因此最多三个模型步骤。只对已知返回的输出做返修：非法或空白 JSON、严格 Schema/完整覆盖错误、作者/自证证据拒绝等；JSON 错误带行列/位置，Schema 错误带 path/validator。输入使用原冻结材料、主体与旧记录映射，失败输出只是明确标注的不可信诊断；输入不足时先整块省略失败候选，绝不裁原始证据。原事务拒绝后整批回滚。

已知 DeepSeek 长度截断最多以 `thinking.type=disabled` 返修一次；保持原 12,288 输出额度，不把可见窗口反降至 4,096。再次失败沿用已有有限前缀缩小或停止逻辑。未知、不完整响应和来源/CAS 错误不授权此类新模型请求。旧最小截断批次的 budget 指纹增加 `generation_policy=memory-native-low-json-v1` 和 `request_seconds=300`，旧失败可由既有 resume 进入新策略，未改原已发送请求。

## 未知隔离及迟到提交

只有 Broker 的原 attempt 回执实读为 unknown 时，才把该批次改为 `quarantined`，不是 failed/applied。原请求、模型步骤和回执保留；精确未变化 Episode 变成 `consolidation_unknown`，cursor 不推进，active pointer 仅在仍指向该批次时释放。该状态位于现有唯一活动批次索引的 prepared/waiting_model/ready 之外。

复用现有 `memory.recover` 和分区整理入口，每次分区唤醒至多观察一个隔离原 attempt，不创建恢复 API，不重发。原结果仍不可用时，同一次唤醒可以继续其他到期 pending 材料。观察失败更新原批次时间，使多个隔离批次可按更新时间轮转。

迟到结果经现有 Sources 复核、Identity、原 Episode revision/sequence/cursor、完整 read-set 和领域 CAS 提交。迟到结果不触发新的补查/返修。CAS 不通过则记录 stale，原材料维持 `consolidation_stale`，不自动生成；现有明确 resume 可重新准备。来源撤回继续失效原批次和步骤。迟到成功或失败都只条件清理自己的 active pointer，不释放别人的 lease。

请求与 lease 一起修正：初始 360 秒窗口为准备保留 55 秒；每个步骤前按 owner 续租 360 秒；补查、返修和提交都检查 owner。保持 Sources → partition → batch → domain 锁序；lease 仅由 run 的 finally 按 owner 释放。

Memory 状态界面明确显示“原请求结果未知，已隔离，不阻塞后续整理”，仅提供观察原执行。已知 stale held 显示未写入原因及明确重新准备入口。

根发布前备份受影响 Memory 域。存在 quarantined 行后不能通过把 unknown 改为 failed/applied、删除状态或整库回滚来退回旧版本。旧 resume 不认识 quarantined，直接恢复旧 Memory 处理可能重发，不能按无状态代码回退处理。保留当前新业务数据和未知记录，优先前向修复；若确需回退，由唯一生产写者协调 Memory 处理、旧恢复入口与受影响域快照，不回退 Sources/Identity 或无关业务。无自动 down migration。

## 已知失败恢复与实机边界

根部署后可对已确认的约 39 条 consolidation_failed 使用现有 extraction/status → extraction/resume：保留原 Episode/revision/source/cursor，以明确命令重新准备新 batch，原失败 attempt 与诊断保留。旧整数预算相同也因执行策略指纹变化获得新策略。先核实原 failure 身份和来源，再按实际回执确认，队列成功不是事实写入成功。

unknown/quarantined 和原 timeout_unknown **不得进入该已知失败刷新集合**；只观察原 attempt。迟到已知 stale held 才允许明确 resume。不要扩大到其他历史 jobs，不直接 SQL 改结果状态。

供应商可能仍返回截断、非法结构或 unknown；一次返修不是外部供应商永久修复证明。Go 的实际 thinking/JSON 参数透传，以及新请求自然运行和原隔离批次的实机推进，仍由根最终验证。根是唯一生产、配置与恢复写者。
