## 调度修复

- 五类作者定时源（视频订阅、书籍订阅、漫画订阅、音乐播放列表、书源 feed）继续共用 `media/scheduling.py`，调用现有 `Identity.refresh_scheduled_context`。根实读确认四条 feed 是全局管理员配置，actor_id=null；公开端口精确增加 `require_actor=True` 默认参数，只有 Media 显式传 False。全局作者保持 actor=None，不借角色；Life 等现有调用默认行为不变，角色非空仍检查其启用状态。原 actor/conversation、人、权限、scope、audience 上界不变；当前 scan handler 没有命名权限，因此刷新参数为 `permission=None`，Actions 继续检查 handler 的完整权限集，未发明 `capabilities.invoke` 权限。
- 刷新后由原 Authority 和 Actions 再校验 SourceRefs，Actions 的事务级来源复核保留。只更新作者定时上下文；已入账 Action/Attempt 的上下文与身份不变。提交前先以原 intent 查询 Actions；排队/运行中的动作只观察，transport/epoch 竞态保留原 key，unknown 或未知外部效果明确暂停，不自动重发。
- 每项写入 `schedule` 观察：submitted/pending/completed/retry_wait/blocked、原动作 key、失败次数、观察时间和下一次检查。可恢复错误从 60 秒指数退避至最多一小时；失权、来源撤回、停用角色、缺作者等改为 `state=paused` 并保留明确 code。单项异常不阻断后续来源。
- `Repository.record_schedule` 在原媒体仓储写运行事实，不提升配置 revision，以 revision/原 due/CAS 避免覆盖作者修改。显式 save/resume/control 经现有 `CURRENT_ACTION` 重授作者上下文并清 schedule 阻断，已有 SourceRefs 保留；不保留旧 epoch 旁路。
- `Background` 保存共享扫描返回的 partial/blocked/retry_wait 和计数；submitted 仅代表动作入队，不能当成书源下载/导入完成。

无 DDL、无数据清理或兼容迁移。当前 active 且到期的原记录自动刷新，四条全局管理员 feed 无需重绑角色；无需删除旧失败维护任务或旧 Action。真实来源/权限撤回仅在作者明确恢复后重授，保留原来源依赖；测试不得靠改回 epoch 或直接改数据库来通过。

## 可用性合同与搜索配置

`Availability` 末尾新增默认空字典 `constraints`。空/缺字段维持原有“不额外限制”语义。仅 `Operation.availability` 的 `content.discover` 分支改为读取 Content 的真实发现配置；`content.read` 的给定公共 URL 阅读独立可用。共享装配改动只有 `src/tianshu/capabilities/service.py` 这一分支。

规划端路径为 `item.availability.constraints`：

```json
{
  "sources": {
    "web": {
      "configured": false,
      "can_execute": false,
      "reason": "search_provider_not_configured",
      "provider_ids": [],
      "requires_query": true
    }
  },
  "source_options": [{"provider_id": null, "sources": ["bilibili"]}]
}
```

`sources` 始终含原注册的 web/forum/bilibili/music/books/comics 六项，均为同一形状。来源集合与 provider_id 从 `source_options` 表达；B 站公开代码是基线已有路径，其 `verified_at=null` 不宣称本轮业务验收通过。论坛没有 followed_forums 时不可选；本轮不启用的媒体库也不可选，不因为目录已有这些名字就串联独立订阅。作者配置的 actor/scope/audience 过滤由可用性与执行共同复用，actor 为空不会绕过 scope/audience。

Content 仍复用 `content_discovery.Discovery` 的 SearX JSON 接口、候选定义、来源游标与预算，没有另建搜索账本。自动选择能覆盖请求来源的提供方，避免一个纯浏览器 profile 遮住搜索配置；实际 provider_id 固定在 continuation。支持同页 offset 及真实 `pageno` 续页，响应错误保留来源 code。片段明确为 `summary_kind=search_snippet`、`read_basis=discovery_metadata`、`experience_eligible=false`；只有随后的真实正文读取形成已读材料。

根配置示例（现有 `POST /api/v1/content/providers.save`，用正常授权上下文与新请求 ID；expected_revision 按当前记录读取）：

```json
{
  "id": "lan-search",
  "expected_revision": 0,
  "client_request_id": "<fresh-request-id>",
  "enabled": true,
  "search_engine": "searxng",
  "base_url": "http://tianshu-core-search:8080",
  "allow_private_network": true,
  "search_language": "auto",
  "followed_forums": []
}
```

此路径既有 `config.publish` 权限不变。`search_engine` 可为 searxng/searx，省略为 searxng。`search_language` 可省略。不给公共实例默认值。

根负责 helper 实际部署和配置：同一私有容器网络可解析该服务名，固定镜像 digest，SearXNG `settings.yml` 的 `search.formats` 包含 json，正常可出网到其启用引擎。无需向 LAN/公网发布搜索端口。官方 [Search API](https://docs.searxng.org/dev/search_api.html) 规定 GET `/search` 的 q/format/pageno 参数，JSON 未开启会返回 403；[search 设置](https://docs.searxng.org/admin/settings/settings_search.html) 与[容器安装](https://docs.searxng.org/admin/installation-docker.html)供根部署核对。

固定搜索端点的 LAN 授权与网页 URL 分离：只有保存的基址派生的精确 `/search` 可继承 `allow_private_network`；拒绝 HTTP 跳转，不接受调用方提供的任意 headers/cookie/proxy，不让 discover 参数替换基址。普通候选/HTTP 正文/浏览器网络继续使用公共地址策略，拒绝私网字面 IP 和私网 DNS 结果；连接复用已校验 DNS 地址，浏览器不再在校验后自行重解析。浏览器同源账户 headers 仅保留给已授权 origin，跨源 CDN 保持无账户访问。没有给普通 URL 引入 LAN 例外。

## 局限

生产 helper 的实际搜索成功、不同引擎的可达性、真实网页/浏览器与四条作者源运行尚待根验收。`configured/can_execute` 是当下授权配置能力，不是网络健康承诺；远端封禁、登录、限流与空结果通过实际回执报告。SearX 没有可靠的统一总页数，非空页可继续，遇空页/预算耗尽停止；同页内容变化明确 version_conflict，不伪装稳定结果。

用户侧 Memory/Companion 算法、Life、models、channels、images 和生产配置均未修改；Identity 仅修改上述公开刷新端口的可选参数与对应 actor 检查，不推送、不部署。
