## 接口与复用

```python
exchange = ThreadedExchange(buffer_bytes=65536)
exchange.register_factory(name, factory, framework, origin)
await exchange.open()
await exchange.invoke(name, lambda app: app.state.lifecycle.quiesce())
await exchange.invoke(name, lambda app: app.state.lifecycle.drain())
closed = await exchange.close(grace=30, cleanup_timeout=30)
```

`factory(ports)` 在各模块自己的线程/asyncio loop 构造原 app、Store、客户端，并在相同 owner 运行原 framework startup/request/shutdown。没有把已构造的 SQLite connection 移线程，没有改 Store 线程约束。模块按注册顺序构造和启动，注册表先冻结；factory 可以先取得其他模块 transport，实际请求才等待其真实 framework startup。

`ports.owns(request)` 仍调用该 owner 原 LocalExchange 的可信 scope/request 登记，伪造字段、URL 或 TLS 不算可信。`ports.async_transport(target)`、`ports.sync_transport(target)`、`ports.session_factory(target)` 复用原 HTTPX/aiohttp 适配器。同步 transport 绑定**调用方模块** owner loop，继续只允许其原工作线程调用，loop 线程调用会拒绝，防止阻塞等待自己。

`invoke(name, operation)` 在目标 owner 调用 `operation(app)`，同步返回或 awaitable 均在目标 loop 完成；结果只允许递归复制的普通值（None/bool/int/float/str/bytes/list/tuple/字符串键 dict）。不能把 app、Store、游标、连接等 owner 资源传回主线程使用。invoke 不绕过业务身份：它是可信宿主的生命周期/状态控制接点，跨产品业务仍走原 HTTP 合同与鉴权。

新增 `threaded_exchange.py` 管线程、目标、调用链和关闭，`loop_bridge.py` 只管 owner 调用/ack 与字节拉取；原 LocalExchange、ByteChannel、ASGI/aiohttp application adapter 未另行实现或修改。原 framework client 仅补下述必要的错误/超时兼容接点。

## 流与冷启动

目标 loop 继续运行原 `_Call` 与每请求输入/输出 ByteChannel。请求体 anext/aclose 留在源 loop，响应 receive/aclose 留在目标 loop；跨 loop 只逐块传递 bytes，单块不超过 buffer_bytes，每方向至多一个在途 pull。没有拼完整 HTTP body，也没有跨 loop 共享 asyncio.Condition/Future。body iterator 与原 body stream 均在来源 loop 收尾。

A→B→A 在各自 loop await 对端，只有短线程锁维护调用登记，没有包围远端 await 的模块锁或总串行队列。内存中的可信 lineage 随实际调用传播，不加 HTTP 权限头；关闭只放行仍活跃调用的子回调。已有请求/响应仍经过原 middleware、token、schema、状态码与实体，原协议序列化成本仍在。

每个已注册 owner 有独立 startup Future，只有原 framework startup 真正完成才成功。Platform 式后台 pump 可等待尚未启动的 Companion；Gateway 式 startup 可读已启动 Platform。单个等待者取消/超时不会 cancel 共享 Future；HTTPX 原 read deadline、aiohttp 原 total/sock_read deadline 限制等待。startup 失败产生 `TargetUnavailable(ConnectionError)`，HTTPX 映射 ConnectError、aiohttp 映射 ClientConnectionError，原 pump 能进入既有错误处理。未知模块与错 origin 继续是明确配置错误，没有网络 fallback。

只把**确定尚未进入 handler**的 TargetUnavailable 映射连接失败；不把执行后的任意 ConnectionResetError 包装成“未发送”，避免改变命令 unknown/重试判断。等待 startup 时尚未登记远端请求的取消，也会关闭来源 body。startup Future 只证明框架可接请求，不替代产品自己的业务健康判断。

## 真实收尾与停止顺序

宿主先排空外部根请求，再通过 invoke 停各产品 producer 并 drain owned domain work，期间 router 必须保持 open；本卡不重写产品调度。`router.close` 是最后阶段：

1. 拒绝新 root，保留活跃链的 A→B→A 子回调，等待流消费与原 handler finally。
2. grace 到期只发一次 abort/cancel。另用独立 ack 确认远端 Task 的实际 finally 已结束，不把 concurrent Future.cancel 当成清理完成。取消一个 close 等待者不会取消那轮实际关闭，也不会二次打断业务 finally。
3. 调用与源 body 收尾后，在 owner loop 反序关闭原 app/client/Store；再停 loop、清理其任务/async generators/default executor，真正 join 模块线程。

`close` 只有真实 join 后才返回 true。同步 SQL 等不可被 Python 强杀的调用超出 cleanup_timeout 时返回 false，线程/Store 留在原 owner，不冒称已停止；重复 close 会等待当下事实并继续完成。宿主必须检查此返回值。app 或 body 的清理抛错仍完成其他 owner 的反序关闭与 join，最后报告 ExceptionGroup。

invoke/流操作的取消等待会等待远端 ack，因此同步调用卡住时可能超过外层 wait_for 的名义时限；主 loop 仍可处理其他任务。需要硬响应期限的宿主诊断可用 asyncio.wait 留下在途 invoke 并先报告 degraded，不能把其 cancel 当成资源已释放。close 的 cleanup_timeout 是有界的“不完整”判断。
