# TS-363 — 运行日志统一保留与手动清空

基线 `b17db5c47f4682ab51fb62b533246a92aeda4349`；本地实现，未操作 NAS、生产日志、业务库或构建镜像。用户最新授权覆盖原 1M/5M 方案：五来源合计默认最多 **10000 个逻辑事件**，默认 30 天，手动清空包含旧 pending；仅运行日志，不处理聊天/记忆/日程/业务数据。

## 实现及接点

- `retention.apply_retention(guard, loki, retention_days=30, log_max_events=10000)` 为唯一投影规则。guard 为策略真值；`log_max_events` 与兼容的 `ledger_max_events` 同步。原 configure 设置一次生成；单容器薄接点由 TS-364 的 `53cd164`、`ce5e686` 提供，不在本卡重复修改。修改后重新导出并重启 guard/Loki，无热重载承诺。
- v3 账本保原 SHA256、原 8 字段/位点/事务汇总，新增 source 时间、collection 时间、退役前缀、原字节前缀收据、删除 outbox、清空 cutoff、持久扫描入口。v0/v1/v2 同事务无损迁移，不自动 VACUUM。**TS-359 冻结的 v2 压缩工具不可直接用于 v3**；首次切换清空运行日志，无需再迁移旧 1M 账本。
- 自动只退役已确认且有原字节收据的最旧可行连续前缀；真实 gap/pending 阻止对应 stream。每个来源按实际消费进度轮转，修复高流量 Platform 可永久饿死其他来源的问题。仍使用原 scan/reconcile/汇总，无新队列。
- 原始文件只有原生更高分段，或 TS-366 完整新 host 实例表证明旧 UUID 已退出，才可 unlink。要求 ready、complete、五 UUID、存活 PID、0..120 秒 freshness。活动文件仅证明前缀，不删活动段；先提交收据，再核 inode/字节/时间和目录 fsync。TS-364 提供明确五目录 RW；产品容量恢复由 TS-368 负责。
- 用户 query 在每个 LogQL selector 内注入紧凑 service/instance/sequence 范围，后续原过滤和聚合继续执行；正常五 stream/10000 条表达式小于 2KB，避免一万 UUID regex。特殊已知 sequence conflict 核 accepted ID；临时提取字段在原 pipeline 前 drop。physical index/stats 与暂存字节不伪称逻辑条数。
- 自动及手动复用同一水位/outbox。Loki delete 只提交本包固定 tenant/stream/prefix，按实际 collection 时间缩窄删除窗，失败不推进 submitted。原 Loki compactor 异步回收/取消窗口仍在。
- 固定 `POST /retention/clear` 只接受原 **writer** 角色及空 body；query/metrics 不升权。`manage_logs.py clear --settings ...` 读取原 token 引用，经原 TLS 调用，返回持久 cutoff/已知条数/pending 数。旧 raw/未扫数据/Vector replay 按 cutoff 消费而不回灌；之后新日志可进。清空与正在 reconcile 交错的旧窗口覆盖竞态已有回归。
- 原 15 告警 UID/持续时间保留；`LedgerCapacity` 改为当前无法腾位拒绝、源回收失败、Loki 删除失败。正常满 10000 不报警，历史 counter 不清洗也不永久锁死告警。捕获的原 Grafana 仅替换此规则 A 表达式，不能重建其他自定义规则。

操作及物理边界见 [RETENTION.md](../../deploy/observability/RETENTION.md)。原始活动段约 64MiB/源、Vector 持久补传、Loki WAL/chunk/cache/异步删除是另外的物理暂存，不声称磁盘瞬时只有 10000 条。未确认、坏字节、真实 gap 或 I/O 故障会保留额外原件并报警。保留天数自首次落账/collection 起计，保证离线补传不会刚进账就因原事件较旧被自动删；显式手动 cutoff 使用原事件时间。
