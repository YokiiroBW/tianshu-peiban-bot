## 精确一次性撤回建议：由根执行

不增加产品 API，也不通过 Sources 的撤回接口撤回消息原件。`channels.read` 结果只是展开动作；转发/引用原件及真实用户输入属于另一条有效来源链。应先冻结事故 Episode 的显式 ID/版本/hash 清单，再在本产品写者停写的短窗口内完成一次事务处理。

建议候选清单的只读联表条件如下；source_refs 为空只用于确认本次事故形状，技术用途与真实 Action 来源才是选择依据：

```sql
SELECT e.episode_id,e.revision,e.content_hash,e.actor_id,e.action_id,e.receipt_id,
       e.source_refs,e.coverage,
       a.action->'context'->>'origin_kind' AS authority_origin
FROM memory.episodes e
JOIN capabilities.actions a ON a.id=e.action_id
JOIN conversation.result_consumption c
  ON c.receipt_id=e.receipt_id AND c.action_id=e.action_id
WHERE e.active
  AND e.origin_kind='tool_result'
  AND e.episode_id='action:'||a.id AND e.event_id=e.episode_id
  AND a.kind='channels.read'
  AND a.action->>'capability_id'='channels.read'
  AND a.action->>'origin_kind'='observation'
  AND e.actual_result->>'capability_id'='channels.read'
  AND e.receipt_id=a.receipt->>'receipt_id'
  AND e.revision=a.result_revision
  AND e.source_refs='[]'::jsonb
ORDER BY e.actor_id,e.episode_id;
```

复盘已确认 24 条，但实时数量可能变化，不能把旧计数冒充最新范围。根需记录当次完整清单及非目标的原件/消息/动作计数或摘要。事务中再次锁定这些 episode_id，并校验 revision、content_hash、receipt_id 和上述联表条件；不重新执行一个不限 ID 的全库筛选写入。

对冻结清单还需只读确认：

- `memory.reflections` 的 active 行及 `companion.style_rules` 的 active 行，没有 `episode_ids` 与清单交集。
- `companion.organize_state.active_batch.inputs`、`blocked_material` 和 `life.diaries.episode_ids` 没有引用这些版本。
- `companion.growth_inputs` 的对应版本应已因 original_source_missing 记为 unavailable，或仍待处理。现有 Growth 会把无来源版本单独标记 unavailable，不会把它们提交为有来源反思；这是对当前实现的静态判断，仍需根读回实证。

在上述派生引用为零的本次事故形状下，只改冻结清单对应的两类行：

1. `memory.episodes` 设 `active=false`，分配新的 revision_sequence 游标；清空 lexical、embedding、embedding_profile、semantic_fingerprint。保留原 episode ID/版本、原结果和动作审计供追溯，不改用户消息/source。
2. 对同一 episode_id/revision 的 `companion.growth_inputs` 设 `reviewed_revision=revision,state='unavailable'`，保留已有 missing 并追加 `technical_ingress_read_retracted`。不动其他 pending input、组织游标、原模型回执或 unknown 请求。

根的一次性私有脚本可使用以下事务骨架；`lr_c_manifest` 只装入前述已冻结并审阅的显式清单，使用参数化批量 INSERT，不能用一个不受清单约束的 INSERT SELECT 替代。既有 Memory 按 Source 撤回会波及真实消息来源，本事故 source-less Episode 不适用该接口；以下沿用所属表已有的 active/sequence/索引失效语义，不增加产品逻辑。

```sql
BEGIN;
CREATE TEMP TABLE lr_c_manifest (
  episode_id text PRIMARY KEY, revision bigint NOT NULL,
  content_hash text NOT NULL, action_id text NOT NULL, receipt_id text NOT NULL
) ON COMMIT DROP;
-- 由根参数化插入已冻结的精确行，随后锁定并比对完整行数：
SELECT e.episode_id FROM memory.episodes e JOIN lr_c_manifest m USING(episode_id)
WHERE e.active AND e.revision=m.revision AND e.content_hash=m.content_hash
  AND e.action_id=m.action_id AND e.receipt_id=m.receipt_id
FOR UPDATE OF e;

-- 以下四个计数必须为0；有派生引用时先精确分析对应行。
SELECT 'reflection' AS kind,count(*) AS n FROM memory.reflections
WHERE active AND episode_ids && ARRAY(SELECT episode_id FROM lr_c_manifest)
UNION ALL SELECT 'style_rule',count(*) FROM companion.style_rules
WHERE state='active' AND episode_ids && ARRAY(SELECT episode_id FROM lr_c_manifest)
UNION ALL SELECT 'diary',count(*) FROM life.diaries
WHERE episode_ids && ARRAY(SELECT episode_id FROM lr_c_manifest)
UNION ALL SELECT 'growth_batch_or_blocker',count(*) FROM companion.organize_state s
WHERE s.blocked_material->>'episode_id' IN (SELECT episode_id FROM lr_c_manifest)
   OR EXISTS (SELECT 1 FROM jsonb_array_elements(COALESCE(s.active_batch->'inputs','[]'::jsonb)) i
              JOIN lr_c_manifest m ON i->>0=m.episode_id AND (i->>1)::bigint=m.revision);

UPDATE memory.episodes e
SET active=false,sequence=nextval('memory.revision_sequence'),lexical='',
    embedding=NULL,embedding_profile=NULL,semantic_fingerprint=NULL
FROM lr_c_manifest m,capabilities.actions a,conversation.result_consumption c
WHERE e.episode_id=m.episode_id AND e.revision=m.revision AND e.content_hash=m.content_hash
  AND e.action_id=m.action_id AND e.receipt_id=m.receipt_id AND e.active
  AND a.id=e.action_id AND a.kind='channels.read'
  AND a.action->>'capability_id'='channels.read' AND a.action->>'origin_kind'='observation'
  AND e.origin_kind='tool_result' AND e.event_id=e.episode_id AND e.episode_id='action:'||a.id
  AND e.actual_result->>'capability_id'='channels.read' AND e.source_refs='[]'::jsonb
  AND e.receipt_id=a.receipt->>'receipt_id' AND e.revision=a.result_revision
  AND c.receipt_id=e.receipt_id AND c.action_id=e.action_id
RETURNING e.episode_id,e.revision;
-- 根脚本断言返回行数严格等于manifest数量；失败即回滚。

UPDATE companion.growth_inputs i
SET reviewed_revision=i.revision,state='unavailable',updated_at=now(),
    missing=ARRAY(SELECT DISTINCT reason
                  FROM unnest(i.missing||ARRAY['technical_ingress_read_retracted']) reason)
FROM lr_c_manifest m
WHERE i.episode_id=m.episode_id AND i.revision=m.revision;
-- 完成下述同事务目标/非目标读回后才由根提交。
COMMIT;
```

若实际出现派生引用，先把具体引用行并入冻结清单，按现有所属领域失效语义精确撤回；不能直接清空整个 Growth 分区、日记、用户事实或 Sources。原本 source-less 的事故记录正常应没有这类派生行。

最后读回：目标 active Episode 为零；原 Action/Attempt/Receipt、result_consumption、conversation.messages/turns、转发/媒体 Sources 的 ID/摘要未变；非目标用户 Episode/Claim 计数未变，Growth 仍能处理后续有效输入。不得重放 QQ、重新触发旧动作或把历史 unknown 改成成功。此次代码只防止新污染，不自行执行这一数据操作。

## 原生图片验收后的精确追加返修

确定的问题在 `Images.recovered_receipt`：此前只有非请求图片发生一致性冲突才归档，导致 create_only 在 matched/unknown 时也返回 `recheck`。现在 create_only 始终返回 archive，不再带 `reconciled_requires_expression_recheck`；一致性冲突仍保留原提示，share_candidate/requested_delivery 的既有恢复复核保持。
