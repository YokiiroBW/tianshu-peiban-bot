# TS-354 installed-wheel 插件安装失败定位

状态：`diagnosed_no_product_change`。根协调的候选 Linux 镜像 `a02bdcab…` 中，原4个 plugin schedule/receipt 场景在 `asyncSetUp` 安装阶段约0.2秒内得到 `plugin_install_failed`。该失败保留，不能因诊断进程外层 returncode=0 就当作插件测试通过。

## 已确认原因

根协调在同候选隔离条件取得 `.runtime/unified-deploy-20261027/plugin-diagnostic-r2.json`：

- 实际 `packages.py` 来自 `/opt/tianshu-venv/lib/python3.12/site-packages/services/platform/plugins/`；SDK worker 存在，5份协议schema齐全。
- `/tmp` 实际挂载为 `rw,nosuid,nodev,noexec,…`。
- 原异常首次落在 `process.py:28` 的 `asyncio.create_subprocess_exec`，为 `PermissionError` / errno13；随后由原安装台账折叠为 `plugin_install_failed`。
- 原 `PluginTests.asyncSetUp` 使用 `TemporaryDirectory()`，把插件包及其私有 `.environment/bin/python` 放在 `/tmp`。`Packages.prepare` 原本使用独立 `venv.EnvBuilder`；创建出的解释器位于 noexec 挂载，首次启动被系统拒绝。此验证临时目录的执行属性与实际持久插件目录不一致。

原诊断收据 raw SHA256：`e50774f188e571463ff2247a171453aa58d0efb4e7d844329d26d8152a48b8ed`。收据位于协调工作树，未改写或规范化。

## installed-wheel 本地交叉核对

本地共享已安装运行环境使用 `python -I -`，通过 `importlib.util.spec_from_file_location` **只加载原 `tests/backend/test_plugins.py` 夹具**，未把产品或 SDK 源码目录加入路径。实际模块路径为共享 venv 的 site-packages；原 `test_schedule_coalesces_missed_runs_and_stop_prevents_new_ticks` 真实 worker 场景 **1项通过（0.564秒）**。它是 Windows 已安装wheel接点证据，不冒称 Linux 通过。

独立只读比较了已安装 `packages.py/process.py/manager.py/tianshu_plugin/worker.py` 与精确 `d214ec237858f4e5c9e949f3999ec499864a6023`，四者除代码文件换行表示外一致；没有修改字节或合同。普通 wheel 布局中 `Path(process.py).parents[3]/tianshu_plugin/worker.py` 正确指向 site-packages，不能把本次失败归为 SDK source-relative 文件缺失。

复验方法应保持隔离解释器（建议 `-I -B` 避免路径及字节码副作用），显式加载原测试夹具，并先记录已导入产品/SDK的实际 `__file__`。不能用在源码根运行通过替代已安装wheel测试。
