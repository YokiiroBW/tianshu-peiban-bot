# LOG-SIMPLIFY：移除运行日志逐条核对账本

## 用户授权与目标

在确认保留日志存储、查询、轮转、Vector 断点与缓冲，仅移除日志核对层及其阻塞依赖后，用户明确授权：

> 可以，交给对应窗口升级吧，把这个去了。

这是实施并通过既有单写发布流程升级的授权，不是一次仅归档的监控通知。此新要求覆盖历史要求继续保留、修补日志逐条核对账本的限制；不扩大到业务账本、模型调用或消息发送。

目标链路：程序写日志 → Vector 采集与缓冲 → Loki 存储 → 既有页面直接查询。日志按保留策略回收，不再等逐条完整性核对成功。

## 实施范围

1. 移除日志专用 integrity ledger 的运行依赖，包括独立逐条入账、查回、内容 hash 比对、pending/verified 排队、连续序号退休，以及由它们引起的扫描、清理、查询和健康判定阻塞。
2. 追踪现有 guard、retained query、source retention、删除请求、CLI/API、UI/仪表盘、配置生成与发布装配的实际依赖。公共鉴权、TLS、查询转发与正常容量保护继续复用；不要因为部分功能叫 guard 就整体删除。
3. 日志源文件和 Loki 的回收应由保留策略及实际存储状态负责，不依赖自建逐条对账成功。保留既有日志查询功能和用户可见保留设置的实际含义；清理仅供账本使用的条目准入上限，不能把它继续当成日志写入或业务可用性的门槛，也不要另建同类账本替代。
4. 保留 Vector 原生 checkpoint、acknowledgements、磁盘缓冲及重试机制，保留有效的日志去敏与访问控制。仍监测采集错误、缓冲持续增长、Loki 存取可用性和真实磁盘容量。
5. 移除/调整账本专属指标、告警、仪表盘和现有十分钟采样器依赖。旧版线上尚未切换时继续如实报告；切换后区分“指标已退役”和“故障恢复”，不能把缺失指标填零冒充正常。巡检频率与通知偏好不变。
6. 日志历史及配置不因本次升级批量清空；旧 integrity.sqlite 退出活跃依赖后作为有限回退材料处理，不通过清空数据库制造修复成功。正常保留策略的既有回收行为继续生效。

明确不在本次删除范围：消息送达回执、Gateway 请求/结果状态、Memory 整理账本、unknown 执行记录、业务幂等与权限数据。也不重放任何未知任务，不新增真实 QQ 或模型测试调用。
