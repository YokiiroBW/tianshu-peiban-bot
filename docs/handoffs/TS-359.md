## 数据与 schema 核验

复用 TS347 大库迁移的逐行规范化方式：按稳定主键排序，唯一转换是将64位十六进制SHA或32字节BLOB规范为同一完整SHA256值，再对整行JSON计算SHA256。流式读取，内存不装载百万行。原脚本顶层固定执行旧任务，不能直接import，所以这里只复用相同规范化算法，保持旧脚本和冻结证据不变；实际迁移全部调用所属 Ledger。

| 对象 | 校验内容 |
|---|---|
| events | 全部8字段 `id/service/instance/sequence/hash/first_seen/verified/last_checked`、全部ID成员及行数、完整32字节SHA；不只比较id/hash |
| files | 每个 `name/identity/offset` 完整字段与行数，保留已消费位点与源身份 |
| counters | 每个 `name/value`，包括重放、冲突、无效行等现有所有键值 |
| totals | 必须唯一 `(singleton=1,landed,pending)` 与 events 全表计算一致 |
| streams | 每个 `service/instance/landed/maximum` 必须与 events 分组 count/max 完全一致；同时核总 gap |
| SQLite | 输入、迁移、压缩各阶段 integrity_check；压缩后user_version2、freelist0、无sidecar；原 source SHA 不变 |

events没有独立删除标志。规范化全成员指纹保留已删除ID的缺席；不重新生成已删除事件或改变保留/确认状态。合成测试在有历史DELETE的输入上验证，并在最终库的**内存副本**执行 verified更新/删除最高sequence，确认摘要和maximum正确，再rollback恢复原指纹。没有为测试改紧凑文件。

迁移后 schema 与原 Ledger 在内存创建的当前v2 schema比较，包含5张表、主键/约束、WITHOUT ROWID、全部显式/自动索引和两触发器定义。保留 `event_sequence` 唯一索引；`event_pending(last_checked,first_seen) WHERE verified=0`、`event_pending_age(first_seen) WHERE verified=0`、`event_confirmed(last_checked) WHERE verified>0`；保留 `event_verified` 的pending增减与 `event_delete` 的total/stream/max/空stream处理，且没有v1旧 `event_insert`。

v0原 events表的hash声明可继续为TEXT，实际值已无损转BLOB；参考schema比较仅容许这项既有迁移差异。随后 VACUUM 前后的实际 schema 单独完全等值，不要求v0原schema等于v2；压缩不会丢索引、触发器、字段或增添格式。业务身份由 events.id 和唯一 service/instance/sequence 保持；SQLite内部页与隐藏rowid可重排。账本保存摘要与状态，完整日志正文保持在原日志源/Loki，本工具不读取或改写它们。
