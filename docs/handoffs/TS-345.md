```text
python -m deploy.single_container.build --release release.json --output NEW_CONTEXT --uv /path/to/uv
# 具有 Docker 的 Linux amd64 环境后续执行：
docker build --platform linux/amd64 -t tianshu:release-version NEW_CONTEXT
```

`prepare(release, output, *, uv="uv", python=sys.executable)` 是对应 Python 入口。output 必须是新目录；发生失败保留不完整输出和真实命令错误，只有完成才写成功 receipt，不能把残缺目录当作发行完成。源均以显式仓库和完整 commit 的 git archive 导出到临时目录，不 checkout/reset 或读取产品工作树修改。receipt 记录 commit 和 archive SHA256。

产品 wheel 由现有 uv build / setuptools 后端构建，约束 setuptools 80.9.0、wheel 0.45.1；构建工具不进入应用运行依赖。导出的四个产品 wheel 是 Platform、Companion、Memory、Gateway；Memory wheel 已含 Knowledge，Companion wheel 已含 NoneBot 集成。四个 vendor/storage wheel 必须逐字节一致，只留 `tianshu_storage-0.1.3-py3-none-any.whl` 一份。

## 单份 Linux 锁

读取实际 wheel 的 METADATA、Requires-Dist、Provides-Extra 和 WHEEL tags；显式纳入 Companion 的 nonebot extra。uv pip compile 针对 CPython 3.12 / x86_64-manylinux_2_36（Debian Bookworm glibc 2.36）解析，生成哈希，限定二进制。忽略原工作区 uv source 覆盖，不从 PyPI 取得内部 storage 包。

uv 解析局部 wheel 依赖图后，仅不输出它们的机器 file:// 路径，再以实际 wheel 哈希追加相对 `./wheels/*.whl` 行；最终 runtime.lock 不包含 Windows 构建机路径。pip download 按同一目标 ABI/platform、`--require-hashes --only-binary=:all:` 下载全部公开 wheel。该步骤 `--no-deps` 防止 Windows 构建机重新按本机 marker 解读 Linux 图；完整依赖闭包已由 uv 解析，Docker 内原生 Linux 安装仍执行依赖检查。

这里以产品 metadata 的真实约束解析，传递依赖可能比各旧产品锁更新；未擅自选取/拼凑矛盾版本，也没有把 metadata 可解析写成应用运行兼容已证明。本地证明实际解析如 FastAPI 0.135.1、uvicorn 0.42.0、httpx 0.28.1、aiohttp 3.14.1，传递依赖包含 Starlette 1.10.0 / Pydantic 2.14.1。后续 Linux 应用验证仍必须使用这份实际发行锁，不能套用旧独立 venv 的通过结果。

输出为一个离线可安装 context：`wheels/`、`requirements.in`、`runtime.lock`、`dependencies.json`、`release.json`、`Dockerfile` 和允许的 deploy 运行源。dependencies.json 含所有实际 wheel 的 metadata/hash；release.json 含源、引擎 pin、运行源 hash、构建工具版本与锁 hash。

## 镜像和宿主分工

只有固定 Platform base 与 Vector/Loki/Prometheus/Grafana 四个 source image，共五个输入。保留 Platform base 的 OS、ffmpeg、git、music tools、对应源代码许可和 web 资产；保留四个成熟引擎，完整复制 Grafana home/config/run.sh，Prometheus/promtool，不删历史日志或采样。

镜像重建单一 `/opt/tianshu-venv`，离线 `pip install --no-index --find-links=./wheels --only-binary=:all: --require-hashes -r runtime.lock`，保留 pip check 与产品导入检查。重建而非覆盖原 venv，防同为 0.1.0 的产品 wheel 被 pip 当已安装而保留旧代码。没有独立 Knowledge/OneBot 镜像或每产品 site-packages 树。

根 deploy 源位于 `/opt/tianshu/application/deploy/{single_container,observability,tianshu/runtime_guard.py}`，PYTHONPATH 只有 `/opt/tianshu/application`；静态 JSON（如 runtime-identity.schema.json/vocabulary.json）随精确 application 源一起复制，私有 env、运行库、.runtime 不复制。PID1 入口为 `/opt/tianshu-venv/bin/python -m deploy.single_container.runtime --config /config/runtime.json`；根负责生成该 runtime 的业务 host argv：`/opt/tianshu-venv/bin/python -m deploy.single_container.host --config /config/host.json`。

USER 保持 `0:10001`，漫画 UID/GID、CAP、IPC 和真实挂载的 ACL 由原 runtime/Compose 负责；镜像不递归改实际挂载权限。Platform base 继承 `/var/lib/tianshu`、`/var/log/tianshu` 的 VOLUME metadata，根 Compose 仍须显式映射避免匿名卷；Dockerfile 不能可靠删除继承声明。base 下层原 venv 字节也仍在镜像层，不能提前声称镜像尺寸已下降。引擎 ELF/libc 连接与实际复制路径仍须 Linux build 的原 --version 检查及运行验收，未伪称 Windows 已验证。
