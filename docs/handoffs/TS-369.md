# TS-369：原生 producer 的 Linux 容量验证工具

基线协调根 `2f2ab3a13b7b7c6afeddd68cf91c40b06d04ad34`，分支 `codex/linux-producer-capacity-20261027`。只新增stdlib operational脚本及工具自身测试，不修改产品、运行配置或Linux设备。本代理未SSH/执行Docker；实际Linux运行由根协调唯一写者完成。

工具 `tests/deployment/single_container/linux_producer_capacity.py` 使用镜像Python，拒绝非Linux、非10001:10001、存在非lo网络接口或非installed product模块（源路径必须属于sys.prefix），共享metadata必须0.1.3。输出必须是显式新建的/tmp子目录，只在那里制造合成日志、chmod和删除本次自己创建的sealed文件；不启动app/Store/worker业务、不调用网络、不打开或修改任何原合同/配置/DB/生产路径。products的原单日志owner线程照常构造和关闭，不另建进程框架或维护线程。

实际验证目标：Memory native Diagnostics/Sink以原可测属性在首条事件前设1024/4096字节合成边界，真实写满后保留最高tail、只清sealed前缀。chmod0500由10001自己触发真实PermissionError，控制项仍红；恢复0700后等待原writer自动恢复，再真实append/fsync与3项原async admission结算，核seq delta4、不重号、不留sentinel。Memory满时可能已关闭待轮转handle，receipt据实给open_handle_at_capacity，不冒称持有阻塞fd。Knowledge仅构造其实际Diagnostics并证明与Memory同一个Sink类、原memory-knowledge身份及一次真实持久写，不重复同机制压力流程。

Companion只构造一个native LogAdapter，小预算写满后先核仍满probe不花号；保有已open active文件并只清sealed。真实chmod拒绝必须实际进入下一segment open（原active FD已被轮转关闭），失败期间保持红；恢复权限后等原owner自动恢复。核原runtime.log_probe实际持久化、失败尝试号未被复用、active旧字节仍保留，以及3项有界queue+1次真实durable admission的序号和drop增量。

输出仅JSON安全码、计数、实际pending观测、代码SHA256及限制，不输出实例/行ID、正文、凭据、路径或异常详情。pending是正常真实I/O的即时观测和结算，未人为hold内核调用，因此不冒称持续kernel阻塞场景。rootless、network-none、普通/tmp下不能可靠制造原日志文件的真实fsync unknown；明确输出not_exercised_no_privileged_fault_filesystem，没有mock fsync、换/dev/full/pipe fd或用合成异常冒充NAS证据。恢复和shutdown需真实ack，无法安全强杀同步内核I/O；18秒是轮询预算，不是强杀kernel调用的承诺。
