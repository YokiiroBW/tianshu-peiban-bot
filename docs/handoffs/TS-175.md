`Unsafe` 可携带 `docker_diagnostics`；CLI `arm` / `status` 成功或拒绝 JSON 增加该字段。Docker 方法增加可选的 `diagnostics` 收集参数，返回的容器对象和列表保持原形状。未改变其他产品、跨产品合同或配置 schema。

诊断只包含固定 `stage`（`ps` / `batch_inspect` / `inspect_one` / `update` / `term`）、尝试号、批量 ID 数量、退出码或 null、超时标志、固定 outcome、单调耗时，以及启动失败时的数字 OS errno。没有原始 stdout/stderr、原始命令、参数、ID、挂载路径或凭据进入诊断；既有 marker / stop 的精确 ID 字段保留其原职责。

运行循环将当前诊断写入原 `heartbeat.json`。首次 `failure.json` 保存触发原因及两轮诊断且后续不改写；每个 `stop-*.json` 保存 `trigger_docker_diagnostics` 和该次停止自身的 `docker_diagnostics`，原状态与错误仍决定 stopped / unconfirmed。健康的重采样另用原子写入保存到一个固定 `docker-resample.json`，只保留最近一次，后续正常心跳不会抹掉首轮失败与最终健康证据。`arm` / `status` 的诊断随 CLI 返回，不为失败的首次 arm 写入额外状态文件或制造新的锁存。

## 固定 ID 维护与重建接入

后续容器控制器必须识别受此 guard 保护的精确 resident 栈。普通停机／重启也会暂时违反 running 检查，重建会违反 ID 检查，因此整次动作应交给现有受控维护／更新恢复路径，不能直接从通用容器动作绕过。

1. 停止旧 unit，等待其 `ExecStopPost` 完成，读取原失败与全部停止回执，确认锁定 ID 已退出且 restart 关闭；不将请求 TERM 当成停止成功。
2. 同 ID 维护保留旧状态原件，使用新空 state 代次，经原维护流程恢复相同 ID 的 `unless-stopped`、按顺序启动、arm、启动 unit、要求 active / ready / 持续心跳，并比较新旧全部锁定 ID。
3. 计划内重建／镜像更新属于新部署代次。按原部署计划核验获准替换 ID、固定镜像摘要、Compose 标签、挂载、策略与容量，用匹配的新配置与新空 state arm 完整服务集合，核对预期替换及未替换 ID，保留旧停止和新 arm / readiness 回执。不在运行中静默改 marker 或 config。

本卡仅给接入说明，没有实现通用控制器、在线维护开关、新权限或新审批流程。

## 2026-10-17 协调者验收后的 watchdog 时序返修

协调者指出，原 `run` 成功 notify 后先 sleep（最大 10 秒），再允许一份完整 25 秒快照，两次通知可能相隔 35 秒，超出原 `WatchdogSec=30s`。这是既有循环边界，本次增加有限重采样使它必须被明确处理；最初 30 + 2 项通过不能证明该时序兼容。

返修在同一任务内完成，保持原 30 秒 watchdog、配置和保护条件。`run` 第一轮有 25 秒；其后整轮绝对截止固定为**上一次成功 notify 开始时刻 + 25 秒**，不能取 notify 返回时刻。前轮 notify 自身耗时、poll 等待、两次 Docker 采样、容量核验及状态落盘共同消耗该预算。`sample` / `snapshot` 接受可选绝对截止，并取自身原 25 秒上限与整轮剩余预算中较小者。poll=10、上次 notify 耗时为 0 时最多还剩 15 秒；上次 notify 再耗时 2 秒就只剩 13 秒。独立 arm / status / fail-close 的原快照预算不变。

容量完成后检查整轮截止；健康 heartbeat / 重采样回执的原子写入在临时文件 fsync 后、发布前检查截止，落盘返回后、发送下一次 notify 前再检查一次。Docker 超时沿用原错误；容量或状态写入逾期使用固定 `capacity_sample_timeout`，保留诊断并走原 failure 锁存与精确 ID 停止路径。不会提前发送 WATCHDOG 给尚未完成的检查延时。Python 不能中断阻塞的内核文件操作，独立 systemd watchdog / ExecStopPost 仍是该情况下的原有保护；没有据此扩大时限或声称所有内核调用都可硬中断。
