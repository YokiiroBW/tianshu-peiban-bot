## 设计映射和实现

- 总方案 7.5、CR14：沿原 `Content` 与 `Discovery`，补齐 research/explore/continue。问题研究保留问题；兴趣闲逛消费兴趣主题或公开热门；关注更新使用已配置 UP 主和论坛主题。B 站沿现 `Bilibili` connector/WBI 签名实际读取 search/popular/uploader 页面，不把订阅库当作站内搜索。各来源独立失败，游标绑定配置、问题和来源，候选去重保留稳定身份。
- 网页继续复用实际 HTTP/受控浏览器和角色会话。论坛单独保存作者、自己的正文、被引用作者/楼层/文字、时间、版本和分页。Discourse `/posts.json` 返回不含 topic/stream 时，通过原阅读游标保留剩余帖子，每页最多 20 帖；`follow_up` 用原主题地址及 `after_post_number` 查看新回复。无新回复明确返回 `experience_eligible=false`，不会把搜索摘要标成读过。
- CR15：保留现 PyAV 实际帧、音轨与内嵌字幕。`video.observe` 每次处理最多 30 秒；当配置的实际 Gemini 路线已经验证 video/audio 且原件适合现有 inline 预算时，优先提交真实 video 及明确时间窗口，内部采样仍为未知。其他情况使用真实帧及声音；配置路线缺少某模态时只提交实际支持的输入并记录缺口。未提交字幕/OCR时不制造对应覆盖。
- 疑点最多自动密读一次、最多 8 秒，保留仍未解决的问题；相同疑点标记已经回看，不在后续每段重复回看。每 8 段和窗口末尾进行一次跨段综合，依据原真实段落及先前综合；综合是派生材料。失败保留已完成段落和明确缺口。
- 观看续接只接受服务端已保存的 `consumption_id`，重新读取同一来源、版本、原件和真实下一位置；不信任调用者自带的摘要或覆盖声明。已取得原件的续段不再下载。URL 请求可省略 end，按实际分 P 时长观看；一 P 结束可沿真实下一 P 继续。原件证据单元沿 BVID/CID/原始文件 hash，角色经历不从标题推断。
- 总方案 13.1、CR17A/B：既有 SceneSnapshot → ImageIntent → 引擎编译/实际 graph → 产物保留。没有改用户 CFG/LoRA/工作流参数、增加第二引擎或自动重抽。产物后通过现有 `vision` function 做一次有时限的可见场景核验，使用原 ServiceClass/角色路由；未配置/失败/截断/缺项保持 unknown。结果存原 `image_work.completion`，重查直接复用。明确冲突的普通自主分享归档；用户明确请求仍保留并交付真实作品，附准确说明。

## 正式接线端口

`src/tianshu/capabilities/content/continuation.py` 提供：

```python
continuation_arguments(capability_id, original_args, result) -> dict | None
continuation_step(capability_id, original_args, result) -> dict | None
exploration_checkpoint(capability_id, arguments, result, previous=None) -> dict
```

`continuation_step` 可跨能力：发现 → 原文/原片。`result.continuation` 为 `{capability_id, arguments}`；发现另有 `next_actions`（真实可读候选）和 `discovery_continuation`（翻页）。活动 checkpoint 保存意图、来源游标、已见集合、实际消费来源、当前项目、未解决问题、预算、停止原因和剩余动作。A 的 `LifeService`/worker/规划消费者负责将这些值保存进原 `life.activities` 并用新 Action 身份续接；已经直接发送接口约定，父级集成时核对其真实调用，不新增队列或探索记忆。

`ReadingService` 的 open/read 结果增加 source_ref、revision、标准 continuation。读取完成与分析完成仍分开，暂停/关闭不会制造续读。

能力实际注册继续在原 `Capabilities`：`content.read` 原 handler，`content.discover` 原 Operation。共享装配仅把 discover schema 指向 `Content.discovery_schema`，并传 Action/Attempt 以保存真实发现回执；两个能力声明 `long_running=True`，沿现 `capabilities.execute`/MEDIA lane，调用方 ServiceClass 保持。没有新增 runtime 构造参数、回调或任务名。

## 消费回执和图片结果

`ConsumptionReceipt` 保留已有字段语义，新增带默认值的：media、audio_ranges、subtitle_ranges、ocr_ranges、processed_segments、model_input_modalities、provider_sampling、evidence、unresolved_questions、stop_reason、requested_completed。`ranges` 为本步实际进度；累计段落保留每段的输入模态、帧时点、音频范围和缺口。`requested_completed` 只表示请求窗口已分段处理，`Coverage.complete` 仍 false，不宣称逐帧或全细节理解。真实动作回执、来源与分析产物仍沿原 A 的 Action → Episode → 已有 BOT 反思/后续选择路径，未改用户记忆行为。

图片 Receipt.result 增加：

```text
consistency = {
  state: matched | conflict | unknown,
  checks: [{field, status: matched | conflict | unknown, observed}],
  model_receipt?: ModelReceipt | null, reason?: code,
  scope?: visible_scene_consistency, regeneration_attempts: 0
}
sharing = 原字段 + notice?: string | null
generation_time_basis = completion_observed
```

显著冲突：share_candidate → archive；requested_delivery → send，并提供 notice。恢复结果需要统一表达重新检查联系窗口；已有产物不丢弃。A 的联系/Expression 消费者必须尊重 sharing 并将请求作品的 notice 附入统一表达。B 的 Life UI 已收到完整契约：继续用 content/read、content/discover、content/video.observe、images/view/jobs/get/album 等现有操作和 Action 查询，不将 unknown 显示为成功，不新增重抽。
