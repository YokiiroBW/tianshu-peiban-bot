## Behavior

`StorageRuntime._checkout` sends the existing search_path, lock_timeout and default_transaction_read_only commands in their original order through one psycopg pipeline. Context exit confirms all three before checkout returns. Identifier quoting, timeout rounding/minimum, read-only on/off, pool borrow timeout and setting values are unchanged. The existing binding SELECT remains a separate statement after setup confirmation. Setup or binding errors retain their respective sanitized errors and exactly one return to the pool; rollback failure still closes the broken connection before returning it.

`PostgresConnection.pipeline()` is a thin contextmanager for current-session/transaction setup. It yields the existing wrapper and normalizes psycopg errors from entry, command execution and delayed exit using the existing StorageError/IntegrityError rules. It adds no commit, rollback, retry, task scheduling or connection release. A body exception still follows the caller's existing rollback/close path. The documented scope is SET/BEGIN/advisory-lock setup, without result consumption or business DML in the block.

For the existing Memory dialect, the caller can place `native('SET synchronous_commit=on')` and `execute('BEGIN IMMEDIATE')` inside the context. The latter already emits BEGIN and advisory-lock SELECT, so the lock must not be added again. Only **after pipeline exit** may the caller issue its independent metadata SELECT; combining the metadata read with the lock statement or executing it before confirmation would change the READ COMMITTED boundary. This product integration belongs to its assigned writer/coordinator.

Rows now use slots and try the existing normalized-position map with the exact requested key before casefold fallback. The map is still built so the first casefold-equivalent column wins: an exact request for a later duplicate never selects that later column. Integer/negative/slice indexing, Unicode casefold, key spelling/order/duplicates, missing-key errors, per-result shared metadata and already materialized rows retain their prior behavior.

A 512-entry LRU caches only the pure parameterized SQL-text transformation. It never accepts or stores parameter values or results. Unparameterized SQL bypasses the cache; literal/comment/dollar-quote parsing and percent escaping remain unchanged. No SQLite runtime branch or business query is changed.
