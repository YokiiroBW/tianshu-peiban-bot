基线 `deb88179c81cea1268a3648c568b2d1ce003f558`，独立分支
`codex/unified-plugin-venv-capacity-20261028`。只改原容量 guard、必要测试及本交接；
无 SSH、生产写入、guard arm/reset、容器/镜像/Platform 产品或数据库更改。

根现场确认唯一特殊项是
`/srv/tianshu/data/platform-plugins/plugins/8cd5057a3663bc0f9ef7258f27015c72e172beb75d0c20d0068a410e8b45406d/.environment/lib64`
指向原文 `lib`，link UID/GID10001:10001。漫画 alias 不在扫描 root，本次不为它放行。

## 根因与修复归属

Platform `services/platform/plugins/packages.py:205-225` 在 `.complete`/python 不存在或
complete checksum 不符时调用 `venv.EnvBuilder(with_pip=bool(lock)).create`。
源码没有按 `sys.executable` 变化主动重建的条件，不把这一假设当作已证事实。
Python3.12 `venv.ensure_directories` 在 64-bit Linux 即使默认 `symlinks=False` 也会创建
`lib64 -> lib`；它发生在 pyvenv.cfg 和产品 `.complete` 写入前。
因此不修改已验产品 wheel 或强改标准 venv 布局，正确接点为 guard 原 metadata 扫描。

`capacity` 新增 `service_profile` 关键字参数，`arm`/`sample` 传原 Config 同名字段，
无新配置或 schema。仅 `unified-one` 接受以下全部匹配：

- 相对 deployment root 恰为 `data/platform-plugins/plugins/<64小写hex>/.environment/lib64`；
- lstat 为 link，UID/GID均10001，readlink 原文恰为 `lib`；
- 同 `.environment/lib` 的 lstat 是真实目录，不能又是 symlink。

只计 link 自身 `st_size`，不 resolve/follow/重复扫描 target，也不用 link 采样自由空间。
lib 原目录仍由正常扫描计算。未要求尚未创建的完成标记，避免合法 EnvBuilder 窗口再误停。
包内容升级会产生新64hex目录，同一严格结构仍可纳管；未扩大其他目录/target/owner。
所有其他 symlink/特殊项继续原 `deployment_tree_invalid`；resident-nine、knowledge-ten
和 standalone 默认调用仍严格拒绝。存活 link 的 lib 缺失仍拒绝；整个目录/link 已消失
则沿原 FileNotFound rename/removal race 处理，下轮重采样。
