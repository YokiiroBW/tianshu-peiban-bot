# TS-353 原数据隔离克隆准备

仅本地交付准备工具；未 SSH、连接 PG、读取 admin binding、创建/删除资源、启动生产应用、切换或推送。根协调者是唯一远端写者，执行前审查并使用原 PG2 生命周期创建新的 UUID 库/角色，执行后沿该生命周期清理。基线为 TS-349 `561b173e17a044a94117f399e4b88c759607caef`，分支 `codex/single-container-clone-20261027`。

原根 `.runtime/group-modes-release-20261027/qa-preparation/pg2_lifecycle.py` 的 `prepare --work NEW --admin-binding-file CURRENT` 提供 `binding.private.json` 与 `state.private.json`；`status --work NEW`、`cleanup --work NEW` 沿原身份核验收尾。旧 `qa-preparation/LIFECYCLE.md` 记录当前 admin 来源为原根 `.runtime/memory-quality20-batch/private/admin-binding.json`，旧凭据轮换只更新此 active 文件。本卡只读该来源文档，未读取 binding 文件。该信息不进入工具源码或命令默认值，只有协调者选择当前有效绑定。

## 执行顺序

```text
python tests/deployment/single_container/linux_clone.py prepare
  --stage /NEW-PRIVATE-STAGE --binding /EXPLICIT/binding.private.json
  --state /EXPLICIT/state.private.json --snapshot /EXPLICIT/cold-snapshot
  --recovery-bundle /EXPLICIT/recovery-files.json

python tests/deployment/single_container/linux_clone.py verify
  --stage /NEW-PRIVATE-STAGE --binding /EXPLICIT/binding.private.json
  --state /EXPLICIT/state.private.json --snapshot /EXPLICIT/cold-snapshot
  --recovery-bundle /EXPLICIT/recovery-files.json
```

`prepare` 先核 owned PG 身份和 fresh template0 空库，再调用原 `postgres_backend.prepare_restored_files(snapshot,stage/clone/root)`。原函数核所有 kept copies 以及 authority/owner mount 不重叠，只复制文件并推进 binding epoch。namespace/service/installation ID/schema、guard/source bytes 不改。新 generation 只用于可丢弃 cache。clone 与 snapshot、生产 authority/mounts 必须独立，新 clone 目录必须不存在。

随后 6 archives 逐个通过原 `Tools.run` 只向 scratch DB 执行 `pg_restore --no-password --dbname=OWNED --no-owner --no-privileges --single-transaction --exit-on-error ARCHIVE`。不执行 CREATE/DROP，不恢复生产 DB；每次 archive 前重新核 owned identity。部分失败不重试、不继续、不自动 cleanup、不生成成功 receipt；协调者关闭本次连接/容器后沿原 owner cleanup，然后全新 UUID 重来。

`prepare` 和 `verify` 都用原 `Tools.fingerprint` 流式读取全部表/sequence，比原 manifest 的关系/行数/hash；3 guards 分别从 Memory、Knowledge、actor-memory 原 PG metadata 配对。39 SQLite 由原 `resident_snapshot.verify_sqlite` 在另一个新临时验证副本上 integrity/foreign-key 检查，避免 WAL/SHM 写冻结树。全部文件字节/mode/uid/gid 精确比原 inventory，只有原 binding epoch 可变且使用同一个新 generation。

安装在当前 Python 环境中的 storage wheel `StorageRuntime.inspect` 使用显式 scratch URL、原 namespace、`redis_url=""`，readonly 核每个 service 的原 installation/logical ready metadata，覆盖 25 domains；不创建 pool/schema/cache key 或应用/worker。结果列各服务实际读/hash的行数及非空表数，不输出行/标识内容。**这只是存储绑定与内容完整性，不能声称全部产品业务 ready 或旧绝对文件路径已可读。**

`stage/clone/receipt.json` 记录 manifest/binding/state/tool-config 输入 hash 和上述 proof；不存 URL、password、token 或原配置内容。`verify` 要求这些输入仍一致，并重新核数据。完整原始指纹检查必须在产品初始化/迁移之前完成。

## 原组约束迁移

独立 `migrate-platform` 先重新执行上述完整 verify，再复用原 `readonly_reply_connections.py`（hash `b663d467a9ab0c793bf4b3636919a65307d695936b48d08e82a1512df9fbfb47`）与实际安装 Platform wheel 的构造器 DDL literal、`BotObservation._migrate_reply_generations`。调用者必须显式提供 wheel 中该源文件的 SHA256；本次已装 d214ec 对应 `b5a4707f5aa5651366854539a5d3c6bcddd62a455fe4904fd8588c7bc8077247`，换 wheel 必须重核，不猜 pin。

```text
python tests/deployment/single_container/linux_clone.py migrate-platform
  --stage /NEW-PRIVATE-STAGE --binding /EXPLICIT/binding.private.json
  --state /EXPLICIT/state.private.json --snapshot /EXPLICIT/cold-snapshot
  --recovery-bundle /EXPLICIT/recovery-files.json
  --settings /EXPLICIT/clone-platform-settings.json
  --readonly-probe /EXPLICIT/readonly_reply_connections.py
  --observation-sha256 EXPLICIT_INSTALLED_SOURCE_SHA256
```

临时 migration settings 要把 database_path 重定位到 `stage/clone/root` 内原 Platform marker 所在目录，storage URL 等于 scratch binding，settings Redis 置空；`StorageOptions.from_settings(...,environ={})` 不读取或切换全局进程环境。只初始化一个 bot_observations handle，不 finalize 部分 registry，不起 app/Bots/媒体/回调/后台泵。原 probe 使用 readonly repeatable-read，核 reply_connections/reply_authors/sources 历史行 hash、原 connection_id PK、只移除确切 tuple UNIQUE；执行两遍并保存 idempotent proof、marker 原 bytes 不变。第二遍须无额外目标约束可移除。

迁移改变合法 schema 后不能再把全部新 schema fingerprint 与迁移前 manifest 强制相等；此阶段用原历史行/约束 proof 和 25-domain inspect，不声称执行了新业务。新输出为 `stage/clone/platform-migration.json`。该命令不是幂等任务重试器：失败/已存在输出须由协调者检查实际状态，不能盲重跑 `prepare` 或覆盖 receipt。

## 装配与尚待根执行

`clone/root` 保留原配置、私有 env 和数据的冻结字节；TS-352 导出的候选 settings/ownenv 在另一个新 assembly 目录改 scratch PG 和 Redis，仅挂新 clone 数据目录。Redis 需要 settings 与自己的 env 两处都空，因为空 env 会回退 settings；原配置不改，只保存引用 hash。候选容器 `--network none`，只挂 owned Unix PG relay，无 admin、模型或 QQ 连通；漫画用 synthetic fixtures，不挂生产 RW/NFS 媒体。

原 prepare_restored_files **不复制 controls-backup**。若 Knowledge 文件根等原外部非媒体数据在 controls 中，须显式复制到新目录再绑定。原 manifest.external_controls 的 JSON key 已排序，但 `controls-backup/<index>` 保 caller 顺序；不能按排序后的 key 下标映射。用该 source 对应完整 `control_inventory` 匹配唯一 archive index 后，复用原 `resident_snapshot.copy_control`；歧义必须以原快照调用顺序/源码确认。工具 receipt 明确该项未复制、尚需映射，不宣称外部文件可读。生产媒体与 ACL 不动。

之后仍需真实候选 wheel 读取非空 Knowledge 原件/目录/书籍/媒体记录、旧绝对路径及 OneBot identity 等功能；25-domain readonly inspect 或 SQLite integrity 不替代这些验证。此次 initial snapshot 也不替代最终切换前的停写 fresh cold backup。协调者只在全部隔离功能、异步联动和资源验收通过后考虑 maintenance、final backup 和切换。
