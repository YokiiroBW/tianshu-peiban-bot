# BOT fixed integration review (2026-09-28)

## Decision

The fixed Companion A and NoneBot N changes are acceptable as local integration
candidates. Platform P is **blocked from integration pending two fixes**: its
connection enable check can admit two reply owners for the same physical
conversation and actor, and its asynchronous bot event route performs blocking
SQLite work on the aiohttp event loop. Both defects were reproduced against the
fixed P snapshot. Do not treat the isolated integration candidate as approval to
merge P until these findings are fixed and the relevant joint checks pass again.

## Blocking findings

### P1 — Binding IDs bypass the single reply-owner guard

In `worktrees/BOT-P/tianshu-platform/services/platform/bots.py:355-368`,
enabling a connection compares the complete `channel` dictionaries and only
rejects overlapping actors when those dictionaries compare equal. The channel
dictionary also carries the Core `binding_id`, so two slots can describe the
same external QQ group and thread while having different channel dictionaries.
The inequality then short-circuits the overlap check.

I reproduced this with two enabled connections for the same QQ group, actor, and
author account, but different Core binding IDs. Submitting the same SDK event ID
through both connections yielded two accepted admissions and two dispatches.
This is not stopped by event deduplication: the event key includes
`connection_id` (`bots.py:110-114`, `477-493`), and the internal message/idempotency
keys are also minted or derived with that connection (`489-516`). The two
connections can therefore start duplicate Core turns and send duplicate replies
for one external message.

The enable guard needs to compare a canonical physical destination identity that
excludes the Core binding, then reject overlapping actors for that destination.
Add a regression fixture with identical external destination and actor but
different binding IDs; verify only one connection can be enabled and only one
dispatch can be admitted.

### P2 — Bot event handler blocks the service event loop on SQLite

`worktrees/BOT-P/tianshu-platform/services/platform/server.py:434-439` directly
awaits `platform.bots.event()` for `/internal/v1/bot/events`. That coroutine uses
synchronous SQLite calls, including `BEGIN IMMEDIATE` at
`services/platform/bots.py:449-494`, and opens another synchronous write section
at `535-549`. The connection timeout is five seconds (`bots.py:131-136`). Other
bot operations are run through `platform.local_work.run()` at `server.py:440-447`,
but event admission bypasses that worker.

I held a write lock on the isolated bot database for 0.4 seconds while submitting
an event. An event-loop timer scheduled 50 ms later ran 387 ms late. Under lock
contention or slow storage, this can stall unrelated HTTP requests and probes for
up to the SQLite timeout. Move each synchronous database section to the bounded
local worker, closing its transaction before awaiting source dispatch; preserve
the existing async dispatch between the two database sections. Add a contention
test that confirms an unrelated loop callback remains responsive.

## Fixed changes accepted as candidates

### AstrBot adapter A

A keeps event filtering and reply routing behind the Platform HTTP contract. Its
trigger remains limited to configured text prefixes and local conversations;
non-text, reply, media, and third-party mention events pass through. It writes
the durable event intent before stopping a matching event. Outbound sends use the
selected native adapter client and report success only when the adapter returns
a numeric message ID. The final CA configuration fix builds a validating SSL
context from the configured CA file while retaining certificate and hostname
checks. The supported AstrBot 4.27.3 adapter surface matches the implementation:
[`aiocqhttp_platform_adapter.py`](https://github.com/AstrBotDevs/AstrBot/blob/v4.27.3/astrbot/core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py)
and
[`aiocqhttp_message_event.py`](https://github.com/AstrBotDevs/AstrBot/blob/v4.27.3/astrbot/core/platform/sources/aiocqhttp/aiocqhttp_message_event.py).

The A focused test run passed **12 tests**, including a private-CA success case,
wrong-CA and hostname-mismatch rejection, and loopback HTTP against fixed P. It
was run with the companion Python 3.12 environment; a first attempt under an
unrelated Python 3.13 runtime was discarded because its installed aiohttp API did
not match the test environment.

### NoneBot adapter N

N keeps the OneBot v11 adapter behind the bot sender port and chooses the sender
by the destination binding ID. Existing QQ/TG senders continue to serve
non-selected bindings, and the web sender path remains intact. Its plugin uses
the NoneBot lifecycle and message matcher hooks; send receipts use native
OneBot `send_group_msg` / `send_private_msg` results. The reviewed adapter calls
match the documented
[OneBot v11 bot API](https://onebot.adapters.nonebot.dev/docs/api/v11/bot/).
N's delivery journal records unknown outcomes without retrying an uncertain
send, and its Platform client asks P for reply status through the HTTP boundary.

The focused N route suite passed **83 tests** with **2 environment-dependent
joint tests skipped**. Re-running those joint tests with fixed P and the root
contracts configured passed **2/2**. Across the two commands this is 85 passed,
zero remaining skips.

- The isolated integration candidate was clean at the reviewed commit. Its
  supplied combination run recorded **20 passed, 1 skipped**, with a separate CA

  part of this review.
- Synthetic P reproductions confirmed both findings above: two dispatches for
  one SDK event when binding IDs differed, and a 387 ms event-loop timer delay
  under a 400 ms SQLite lock.

These checks support local adapter and contract compatibility only. They do not
establish installation on a production AstrBot/NoneBot host or behavior with a
real model, account, chat service, or NAS deployment. Re-run the cross-connection
single-owner case and the event-loop contention check after P fixes, then repeat
the fixed adapter-to-P joint acceptance before integration.
