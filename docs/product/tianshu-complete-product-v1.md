# 天枢个人 AI 平台完整产品与架构蓝图

> 历史蓝图：当前职责、网页范围和技术优先级以 [整体架构 V2](../architecture/tianshu-system-architecture-v2.md) 为准。原始需求仍保留，实时通话/共同观影已移出网页，受管文件由 AssetLibrary 最终归档。

天枢面向个人家庭网络、日常社交和自主开发，提供有持续生活的多角色陪伴、可追溯的长期记忆、家庭设备与服务器管理、跨编码工具的项目工作台，以及资料搜索、下载和归档。产品采用统一入口，保持清楚的运行边界；以完整体验决定架构，现有代码与旧冻结设计作为可复用资产评估。

建议保留三个主要产品边界：天枢平台、天枢记忆、陪伴核心；NoneBot 提供消息接入，协议网关承担独立的模型转发。每个产品内部采用模块化单体和必要的后台工作进程。Home Assistant、Chat Audit Core、GsCore、ComfyUI、RSSHub、Komga 等通过适配器协作，不重复实现成熟系统已经负责的功能。

完整目标分为五个工作区：角色的家、人物与记忆、家庭与设备、项目开发、资料与订阅。模型线路、任务、消息通知和设置提供统一入口；角色的情绪与关系、资料整理和运维任务呈现不同的业务界面。

本蓝图提出目标行为与候选设计，不表示这些能力已经实施、打通或达到性能目标。现有系统保持可用，代码取舍、兼容测试及分期开发均在完整目标之后安排。

## 1. 使用者、设备与完整功能范围

默认一位平台管理者；其他 QQ/TG 账号可以与角色交流。每个账号自动建立人物档案，同一账号在群聊与私聊中使用同一人物编号；跨平台或小号关联通过明确绑定完成。主要用户按角色设置，亲密表达与实际操作能力分别配置。

| 功能域 | 完整目标 |
| --- | --- |
| 陪伴与人物 | 私聊、群聊、画像、好感度、主要用户、人格、共同世界、自然参与和主动联系 |
| 角色生活 | 作息、日程、当前活动、心情、长期兴趣、个人目标、穿搭、阅读和创作 |
| 小屋与客户端 | 2.5D 家、闹钟、床、衣橱、书架、上锁日记；语音/视频通话、共同观影与移动端 |
| 记忆与知识 | 当前情境、情节、事实、关系、未决事项、人物/群画像、角色小知识库及原聊天追溯 |
| 资料与娱乐 | GsCore、群聊娱乐、漫画/小说/音乐/视频搜索下载、元数据整理、归档、Komga 与 RSSHub |
| 家庭与服务器 | 群晖 NAS、Windows/Ubuntu、OpenWrt 路由、代理、远程节点、Docker/Dockge、智能设备与游戏服务器 |
| 身体与活动 | Notify for Xiaomi 数据、趋势与生活关心，适配可获得的数据种类和更新频率 |
| 项目与模型 | 本地 Git 可视化、多编码体协作、短交接与知识沉淀、总错题本、模型线路及原生协议透传 |

家庭设备包括群晖 NAS、两台笔记本、游戏台式机、OpenWrt 京东雅典娜路由器、平板、主手机、已 Root 备用手机、Xbox Series X 和小米智能设备。它们先作为资产登记，再按各自能力提供功能；不能仅凭连入局域网就获得每台设备的内存、进程或完整遥测。

生图笔记本现有接口报告为 RTX 4070 Laptop GPU、约 8 GB 显存，ComfyUI 0.19.3。该数据来自一次只读状态查询；没有进行新生图或性能压测。图像、语音、视频和代码任务需要按设备资源排队，而不是让每个角色各自抢占 GPU。

## 2. 人物档案、关系与群聊认知

建议的数据中心是稳定的人物编号 person_id。AccountIdentity 保存平台、账号 ID、昵称历史和头像引用；PersonProfile 保存基础认识；PersonSpaceProfile 保存某人在特定群/私聊中的局部风格；ActorPersonRelation 保存某个角色与此人的关系和好感度。

这能让数据库按人物和场景缩小候选、稳定关联记忆，也便于缓存。真正的加速仍依赖索引、查询范围、预生成的小画像和上下文预算；一个编号不会自动消除向量检索、模型调用或网络延迟。

| 资料 | 示例与目标行为 |
| --- | --- |
| 基础档案 | 昵称、头像、平台账号、主要用户标记；头像本地缓存并按变化刷新 |
| 共享基础画像 | 普通兴趣、称呼、语言和表达习惯；可追溯到来源 |
| 场景画像 | 技术群中严谨、游戏群中活跃；不因此拆成两个人 |
| 角色关系 | A 与此人的共同经历、信任、好感、约定；B 有自己的关系账本 |
| 群画像 | 群主题、常见话题、语气、活跃时间和成员关系；与某个人的私密档案分开 |

好感度可以显示和人工调整，变化有来源与限幅；重复消息不能重复加分。主要用户可获得专属关系背景和亲密表达，普通用户默认友好。群聊可使用相同的关系认识，但表达强度由群场景策略限制，不把私聊亲密内容直接带入群内。

Chat Audit Core 已有群名和头像缓存、机器人账号隔离、消息与人物资料读取能力，适合作为头像与原始资料的来源；新的统一人物索引仍需跨观察账号和平台做归一化，不能把其 robot_id 当成被聊天者的人物编号。[^1]

## 3. 记得同一个人，同时守住私聊边界

建议只向管理者展示少量清楚的可见范围：可跨场景使用的基础印象、原会话内的详细经历、仅本人/指定角色可用的私密资料。后台负责执行范围过滤，普通聊天无需逐条配置权限图。

| 情形 | 期望回应 |
| --- | --- |
| 同一个人在群里问自己的普通爱好 | 使用获准共享的基础画像，保持连续认识 |
| 本人在当前群明确提起一件私聊事项 | 根据本人当轮表达，披露直接相关、必要且允许的部分；不展开全部私聊过程 |
| 群成员询问另一人的私密事情 | 不读取或披露其私人证据，不能仅删除姓名后复述 |
| 问题与私密信息有关但当前不适合展开 | 可以说明适合转到私聊继续，不以虚假“完全不知道”制造割裂 |
| 私聊中确认事项已完成 | 内部关闭过时跟进；不因此向其他群说明私聊完成细节 |

“脱敏”不能只是删除姓名。位置、时间、家庭关系和具体事件组合仍可能识别个人。跨场景投影优先采用允许的字段和概括主题；具体故事留在原范围。本人明确披露不意味着其他相关人的私密信息同时获准公开。

召回要先确定当前发言者、角色、房间、用途和允许范围，再排序。当前窗口、缓存、日记素材、检索工具和最终提示词都遵守相同边界。群成员没有因为熟悉度高而获得平台管理权；角色也没有因为“懂技术”的人格设定而自动获得 NAS 权限。

多角色各自所知也需明确：世界发生一件事、A 亲历、B 听说、C 未知，是不同状态。FANToM 的信息不对称对话可作为验证思路；不能把全部历史交给模型后，仅要求其假装不知道。[^2]

## 4. 陪伴引擎与角色生活

每个角色拥有稳定身份、价值观、偏好、表达样例、当前状态、与各人的关系和持续目标。人格保持可辨认，同时允许兴趣与关系随有依据的经历变化。好感度、心情、熟悉度与任务权限是不同变量。

运行采用三个循环：即时对话处理当前互动；生活循环推进日程与目标；后台整理沉淀经历和认识。简单聊天不等待完整日程推演或反思。普通群消息先筛选相关性与回应角色，获准观察不等于每条都调用模型。

日程有基准作息与可配置的偏移范围，允许本日安排调整，但不让模型无限拖延睡眠。活动有计划、开始、完成、取消与来源；随机性只在合理候选之间选择。角色刚完成午饭，不能在下一次推演中又无缘由吃一次。

情绪参考“事件如何影响目标、是否符合预期、原因与可控性”的评价方式。新信息可以改变心情；一次误会不永久改写人格。角色的自主性体现在关注点、创作、阅读与适当分享，而非后台不停自言自语。Generative Agents 与 EMA 提供可借鉴机制，不能直接证明数月陪伴的效果。[^3][^4]

当前工程参考中，MaiBot 的回复必要性规则适合用于群聊参与；HDSI 的生活与行动窗口适合参考主动联系的原因。新核心吸收这些机制，不要求深度绑定它们的内置记忆或强制每轮写长篇剧本。[^5]

## 5. 2.5D 小屋与多端体验

小屋是角色状态和功能的可视化入口。房间里的位置、物品和活动来自真实业务状态；同样的功能也提供普通列表与表单，手机、键盘操作和查找大量资料不必依赖点中画面里的小物件。

| 物件或区域 | 功能与互动 |
| --- | --- |
| 床与闹钟 | 基准起居、今日日程、睡眠状态；显示已调整的时间和原因 |
| 衣橱 | 衣服、配饰、参考图、标签、适用场景、当前穿搭；筛选和选装 |
| 书架 | 阅读收藏、小知识库、创作项目与作品版本；点开阅读、检索和续写 |
| 日记本 | 按日期阅读角色日记；以关系与心情形成给不给看的互动 |
| 书桌 | 当前作品、正在查的资料、进行中的任务及结果 |
| 角色本人 | 当前活动、对话、语音/视频房间和自拍入口 |

实现上优先考虑等距 2D 素材与 PixiJS，配合常规 Web UI。若需要完整寻路、场景互动和游戏式碰撞，可评估 Phaser；首期不必承担完整 3D 世界、物理模拟和复杂建模成本。这是实现取舍，不限制完整产品中的房间功能。[^6]

上锁日记包含两层：谁可以访问日记的业务权限，以及角色是否愿意分享的互动状态。可以通过对话获得本次解锁口令/凭证，并设置有效期；口令不写入公开群和模型通用上下文。它不是对 NAS 管理者提供不可破解加密的承诺。

Together Companion 已有浏览器房间、语音、观影与可视交互可复用；Reality Companion 可复用配对、设备和移动网关逻辑。本次所读 Reality 源码树没有 Android 工程，README 也说明不随插件发布 App；独立客户端源码和可移植范围仍需对应确认。移植重点是将 AstrBot 人格/TTS/记忆依赖换成天枢接口，而不是重写房间体验。[^7][^8]

## 6. 原始档案、短期情境与整理记忆

建议分三层：Chat Audit Core 保存原始聊天和媒体；陪伴核心保留活跃话题、回复链与当前窗口；天枢记忆保存 Episode、Claim、人物/群画像、关系、事项和知识。整理记录指向原消息，不通过复制全部原文制造另一个无限增长的档案库。

| 层 | 主要用途 | 关键约束 |
| --- | --- | --- |
| 原始档案 | 查原话、上下文、媒体、引用与时间 | 覆盖采集、断线、媒体过期、备份与保留策略 |
| 当前情境 | 知道正在回复谁、话题进展、刚才说了什么 | 有界窗口，角色/房间分别组织；清理不破坏原档案 |
| 整理记忆 | 长期认识、往事、关系、未决事项 | 带来源、时间、归属、可见范围与纠正状态 |

Chat Audit Core 当前可按机器人、房间、发言者、时间和关键词搜索，并支持原消息邻域读取。现有管理员搜索 API 不应直接暴露给每个角色；需要受当前人物、房间和用途限制的查询入口。QQ 采集可复用，TG 需要通过规范化外部摄取路径补适配并验证。[^9]

长期保留是产品策略，不是“除硬盘损坏外绝不丢失”的技术保证。未观察到的消息不会自动出现；配置排除、断线缺口、未缓存媒体、逻辑误删和备份故障都需要可见。当前工程具备备份/隔离恢复流程，但仍要做恢复演练。[^1][^10]

建议新的整理记忆采用关系库与真实语义 embedding，人物/场景硬过滤、关键词与语义混合检索，必要时重排。原文可回读，摘要和向量可重建；完成/取消与明确纠正先更新，避免等待整段总结才生效。

## 7. 记忆引擎比较与选择

| 方案 | 可借鉴优势 | 本项目的代价与边界 |
| --- | --- | --- |
| 自有轻量记忆层 | 易于准确实现统一人物、群私聊边界、事项与 Chat Audit 引用 | 提取质量、检索、冲突与评测要自己完成；不能只靠关键词和一段摘要 |
| Hindsight | retain/recall/reflect、事实与经历、归纳、现成 SDK 与 PostgreSQL 部署 | bank 和默认提取流程不能自动代表群聊权限及多角色关系；仍需映射与同数据评估 |
| EverOS | Markdown 可读、跨客户端、记忆与知识页，便于迁移和人工检查 | 文件与索引同步、多人归因和细粒度披露需要核验；不能每轮全读 Markdown |
| Graphiti | 时间与实体关系、混合检索，可用于复杂关系问题 | 引入图数据库与更多提取/索引负担；不应在关系收益未证明时成为全链路必需组件 |

这些比较依据项目当前公开说明，不采用厂商自报排行榜作为最终选型依据。[^11][^12][^13]

建议对外先固定天枢自己的语义：人物、场景、原文引用、事项和纠正。内部以小而完整的关系库记忆实现作为基线，Hindsight 进入同数据对照；EverOS 用于检验可读资料和跨编码工具体验。若成熟引擎在归因、隐私、质量及成本上明显更好，可替换整理/检索实现，而不让所有客户端重写。

评估从原始消息开始，比较无长期记忆、原文检索、整理记忆和候选引擎；固定模型、允许读取的数据、时间截止点与预算。LongMemEval 适合检验跨会话、时间、更新和无依据时不答，群聊还要增加同名、引用、转述与信息边界用例。[^14]

## 8. 日记与创作的内置写作流程

“在提示词前加一句写得有逻辑”不足以支撑长期创作。Re3 采用计划、持续补入故事状态、候选选择与事实修订；DOC 强调细化提纲和生成时的对齐控制；DOME 将动态提纲和记忆结合。这些研究支持对写作过程做编排，而非依赖一次自由生成。[^15][^16][^17]

日记采用轻流程：当天素材 → 选择一至三个有意义的片段 → 确定关注点 → 成稿 → 检查事实、人物视角、隐私和重复表达。材料少时可以短写，不为凑字数虚构用户行为。允许比喻、感想、轻微幽默和开放式结尾，不强制每天按时间流水账。

长篇创作采用作品设定、阶段大纲、章节目标、人物当前状态、前文必要摘要与少量相关片段。完成章节后更新故事状态，再审校对话动机、因果、时间线和未解线索；只修订发现问题的部分。2026 年关于长故事一致性错误的研究提醒：文风流畅与设定一致是不同的评估项。[^18]

建议内置版本化 WritingRecipe：日记、随笔、资料笔记、小说章节各自有模板、输出长度与检查项。基础写作规则、角色声音、任务要求、可用事实和风格偏好分层装配，界面可查看和调整。普通日记默认一次草稿加轻量检查；需要修订才增加一次定向改写，避免无限反思消耗。

写作评价分别看事实一致、因果清晰、角色声音、可读性、新意和重复率。模型自评只能辅助；用固定素材的盲评和连续多日样本选择模板。论文的故事评价不能直接保证某个中文日记风格最好。

## 9. 写作提示词配方草案

### 日记配方

你正在为指定角色写今天的私人日记。保持角色的措辞、价值观与关注点。只把提供的已发生事件写成经历；用户说法、角色推测、未完成计划分别保持原性质。不要新增现实用户没有做过的行为、未确认关系或不存在的工具结果。

从素材中选择少量值得记住的片段，形成一个自然的关注中心。可以写感受、比喻、细节观察或自我矛盾，但要让原因和转折可理解。不要逐条抄时间线，不重复昨日的开头、天气描写和总结句式；没有足够素材时简短收束。写作中新增的世界事件只能作为候选说明，不自动改写正典。

输入包括：角色声音、今天已知事件及来源编号、当前关系、角色自己的生活状态、近期日记摘要和本次长度/风格偏好。正文只输出日记；来源编号、检查结果及新增推测存为内部元数据，读者不看内部处理字段。

### 长篇章节配方

依据作品设定、当前章节目标、人物所知与前文状态推进故事。每个重要行动应有动机或前文铺垫；不要为了推进剧情让角色突然知道未获知的信息。允许在章节目标内创造细节，不随意更改已有姓名、地点、能力、时间与关系。对新设定给出可追踪的候选变更。

成稿后检查：本章是否完成目标、是否出现前后矛盾、人物行为是否符合动机、是否重复解释、是否留下计划中的悬念。只针对确切问题修订，避免整章反复润色导致风格漂移。

以上为系统配方草案，不是经实测定稿的万能提示词。之后需要用相同素材比较不同模型与配方版本；创作正文、世界状态和用户现实记忆保持分离。

## 10. 本地 Anima 工作流的实际接入

本地 PC_SELFIE 与澄汐 API 工作流均保留 Anima 基础模型、Qwen CLIP/VAE、画师选择、角色选择、LoRA、分辨率、采样和输出；与旧 README 的部分描述相比，实际 JSON 才是本次依据。[^19][^20]

| 已观察节点 | 当前作用 | 新接入应保留或扩展的部分 |
| --- | --- | --- |
| 31 / 32 选择器 | 固定画师与角色描述 | 配置版本、角色绑定；日常请求不重复改写身份 |
| 35 Simple String、36 Prompt Router | 动态文本被分成服装、姿势、背景和其他描述 | 兼容旧四段格式；新增显式字段映射，避免一个字符串包办所有能力 |

现有 Prompt Router 按旧陪伴插件的段落标题分流；直接把新格式丢进去，可能全部进入 extra_prompt。新适配应有 WorkflowProfile，显式绑定节点/字段，能够保留完整图，而不是重新实现各自定义节点。[^21]

主自拍图目前是文本 1、图片 0，没有参考图输入；本地另有 img2img 图，但不能据此认为主自拍已经支持衣服参考、局部重绘或多图身份控制。完整目标包含这些能力，应为不同图建立能力声明并补合适的 LoadImage/编码/重绘或参考路径，再实测效果。

“完整支持本地工作流”应意味着可导入和保留图、探测节点、明确参数绑定、执行/取消/恢复、读取结果和诊断缺失节点。模型只填写业务参数，复杂图编辑仍由工作流编辑器完成。ComfyUI 的队列与历史接口支持这一执行边界。[^22]

## 11. 衣橱、自发自拍与多图像后端

衣物记录包含名称、类别、颜色/材质、季节/场景、提示词、参考图、来源和使用记录。上传衣物图片后，视觉模型提出结构化描述；可一键确认或修正。角色可检索款式并将其加入候选衣橱，再按配置自动收藏普通款式或等待确认。

今日穿搭先由天气、活动、偏好、最近穿过的衣服和衣橱选择形成 OutfitPlan。随机只用于合理候选，不在睡觉、运动和正式场景间无条件抽签。手动要求更换衣服优先；今日状态只在任务真正完成后更新。

“看看自拍”“今天穿什么”路由到当前角色的图像能力；主动新衣分享和生活照片使用同一个任务系统、配额和来源记录。GPU 排队期间聊天继续，图生成完毕后重查人物、计划版本和发送对象，避免把过时任务结果当作当前穿搭。

支持 ComfyUI、NovelAI 和 GPT Image 三类后端，但不把它们伪装成完全等价。Anima LoRA 和画师标签不能直接保证在 NAI/GPT Image 中保持同样身份；需要各自的提示编译、参考素材与能力清单。GPT Image 的生成/编辑与对话图像工具是不同接口，NAI 的参考能力也应按实际模型/API验证。[^23][^24]

同一张图片保存角色、服装、工作流/模型、来源素材与任务记录；图片是表现结果，不替代衣橱和计划状态。图库可交给已有资产系统管理文件和预览，避免再写一套通用文件管理器。[^25]

## 12. GsCore、娱乐、订阅与聚合下载

GsCore 保留原业务与绑定数据。NoneBot 已有连接插件和简易早柚协议实现，可以复用消息入口；自然语言调用再封装必要的能力、参数及结果。功能命令与闲聊明确分流，同一命令不触发多套机器人抢答。[^26]

群聊娱乐以 ZeroBot-Plugin 为功能参考，按需求选择现成 NoneBot 插件、移植小模块或封装独立服务。Go 插件不能直接安装到 Python NoneBot；无需为了几个娱乐功能同时运行整个重复消息入口。[^27]

聚合下载分成统一流程：标题/链接 → 来源搜索 → 同名与版本消歧 → 下载任务 → 完整性检查 → 元数据与封面 → 暂存区整理 → 发布到目标目录 → 触发阅读/资料系统更新。漫画、小说、音乐和视频使用各自来源适配器，任务与归档规则共用。

| 类型 | 首选复用方向 | 必须补齐 |
| --- | --- | --- |
| 漫画 | 自有 Download Hub、Suwayomi 与 JM 后端 | 持久任务、取消/恢复、并发去重、原子发布与入库确认 |
| 小说 | reader/阅读源能力 | 明确所指 reader 版本，验证阅读源兼容与导出协议；来源脚本在隔离后端执行 |
| 音乐、视频 | 影视复用自有 MoviePilot 插件；其他来源单独适配 | 稳定来源 ID、格式、音轨/字幕、封面、元数据与重复检测 |
| 订阅 | RSSHub/RSS/Atom | 天枢仍负责订阅配置、轮询/游标、去重、筛选、推送与归档任务 |

Komga 接收完整文件后扫描/分析元数据；采用受管暂存目录、校验和同文件系统原子发布。扫描请求被接受不等于已可阅读，任务应回查入库结果。RSSHub 提供内容源，订阅状态与投递仍由天枢维护。[^28][^29]

已核实 Forgejo 的 astrbot-plugins/c5483960 中 Download Hub：按名称并行搜索多个 Suwayomi 源、选择章节、SQLite 归档去重、系列别名、ComicInfo、PDF/CBZ 和 Komga 扫描均有实现，并集成 JM 数字 ID 后端。之前本地同名目录读到的 feed_monitor 不能代表该远端。[^30]

迁移优先提取现有客户端、打包和归档规则。当前搜索/选择状态存在内存，归档目录索引不是持久任务队列；CBZ 直接写目标路径，需补原子发布、同任务互斥及失败恢复。MoviePilot 已有影视搜索、下载任务、订阅和通知模块，可另作连接器；不能据此认定小说与音乐也已接通。[^30][^49]

## 13. 家庭设备、智能家居与手环

智能家居优先接 Home Assistant，通过设备实体和动作调用统一控制灯、空调等；小米官方 Home Assistant 集成可以作为设备接入候选。具体设备覆盖、云端依赖和局域网支持取决于型号，接入时逐设备探测。电脑开机可用 Wake-on-LAN，但需网卡、固件和网络支持。[^31][^32][^33]

Notify 官方已支持向 Home Assistant 同步：Standard 通过 REST 更新实体，Enhanced 使用 MQTT Discovery。对已有 Notify 的环境，先走 Notify → Home Assistant → 天枢，是较短的接入路径。长期身体数据另存采集时间、来源、单位与质量，不把当前状态传感器等同于无限历史。HA Recorder 的默认保留策略也需要明确调整或独立归档。[^34][^35]

若需要未覆盖的完整记录，可再采用 Notify → Health Connect → 手机导出/同步 → 天枢。Health Connect 是手机端数据接口，后台读取和历史范围取决于权限与平台；需要移动桥，不能由 NAS 直接读取手机数据库。[^36]

所给 Body Monitor 支持结构化数据接收及事件交给陪伴侧调度，这个边界值得复用。它的“支持指标”不证明当前手环和 Notify 实际都能提供这些值；心率、睡眠、血氧、压力、HRV等逐项标注可用性。固定 z-score 阈值不能当成医学结论，目标是趋势、数据质量和适当生活关心。[^37]

手机、平板和 Root 备用手机可作为小屋、语音、设备桥及观影终端。摄像头、麦克风、健康和位置分别在首次接入时开通，日常使用不重复确认；关闭或撤销后立即停止对应采集。默认健康和精确位置不进入群聊。

## 14. NAS、网络、容器与游戏服务器

监控通过连接器提供真实能力：NAS/Windows/Ubuntu 的 CPU、内存、磁盘和进程来自节点 Agent 或系统接口；路由器提供网络与代理观测。每设备网速需要路由器可见的流量数据与采样，例如 nlbwmon；流量卸载和采集间隔会影响覆盖，不能把连接列表当完整带宽统计。[^38]

代理管理区分健康检查、刷新代理提供者、替换订阅配置与全局路由更改。Mihomo 已有代理提供者状态、刷新与健康接口；OpenClash 等上层配置管理仍需对应适配。替换订阅应先校验、保存上个可用版本，再应用并检测连通性，避免失败后同时切断管理通道。[^39]

Docker/Dockge 使用受管 Compose 项目。部署先形成镜像、端口、目录、卷和依赖计划，再按配置分配端口与创建目录，执行后验证状态。Dockge 识别既定 stacks 目录中的 Compose 文件；应选择一个写入负责方，避免它与天枢同时覆盖同一配置。不能假定存在稳定通用 REST API。[^40]

自有 astrbot_plugin_nas_ops 的现有代码已包含模板识别、可用端口选择、目录/卷规划、Compose 状态与日志、部署后容器及健康检查，可提取为设备执行能力。当前大量逻辑集中在约一万行的 AstrBot 主文件，仍需移出聊天对象依赖、明确执行结果和并发约束；不必原样搬入全部旧审批层。此次只读核对，没有实际部署或重启。[^47]

MC 与其他自建游戏服务器共用实例生命周期接口。优先评估 MCSManager 的启动、停止、重启、命令与状态能力；也可对现有进程管理方式做适配。RCON 主要管理正在运行的游戏进程，不能独自启动已停止服务器。玩家事件、世界信息或更深游戏互动需要后续插件/模组接口。[^41]

常用的开灯、空调、已登记实例重启等按预设自动执行；新增部署、改变网络、删除/覆盖数据等给出一次具体预览或确认。日志和任务结果可追溯，模型不能把请求成功提交当成设备操作已经完成。

## 15. 项目工作台与跨编码工具连续开发

项目工作台登记仓库位置、运行环境、分支、当前任务、变更、提交、测试、文档和交接。NAS 保存项目与远端 Git 是可行目标；多个编码工具不应同时写同一个工作目录和 Git index。

建议同一项目使用独立任务 worktree/分支；跨主机使用各自检出，通过 Git/Forgejo 同步。它们属于同一仓库历史，但拥有独立工作目录。切换编码工具可以继续同一个任务和工作目录的所有权；同时工作则分配不同目录，集成时解决冲突。[^42]

已有 astrbot_plugin_dev_handoff 提供项目、任务、历史、机器和交接入口，但它是通过本地 socket 调用独立 controller 的薄客户端。可以复用交接动作与结果展示经验，不能把这份插件认定为完整项目工作台后端；controller 的仓库和运行实现尚待定位。[^48]

共同能力包括：获取任务、读取有限恢复包、定位相关文件、记录阶段结果、提交变更与请求集成。通过 MCP、HTTP 或本地 CLI 适配各编码体；不同客户端能否自动恢复、执行和上报，需要分别验证。ZCode 的具体产品和协议尚需在接入阶段确认，不假定所有软件都支持相同钩子。

文档采用少量稳定对象：需求与验收、架构/约定、当前任务状态、关键决策、项目经验、交接检查点。原始代码与版本化文档保留在 Git；任务当前状态由项目服务维护。自动生成的 Markdown 是可读视图，不能与结构化状态分别独立修改而互相覆盖。

一次切换只提供当前目标、已完成结果、未提交变更、相关决定、剩余问题、下一步和来源引用。旧会话、日志和已关闭任务保存在可检索历史，不每次全量塞进上下文。真正的 token 控制来自按任务取资料和增量更新，而不只是不断压缩一份越来越大的总文档。

## 16. 项目经验、总错题本与上下文预算

项目内先记录具体问题：现象、环境与版本、根因、修复、证明它有效的证据，以及适用范围。只有可迁移、反复出现或代价较高的经验才进入总错题本；一次拼写错误、暂时网络失败和未经验证的猜测不必永久影响所有项目。

总错题本保留简短规则、适用条件、反例、来源项目和复核时间。过期经验可标为失效；同一问题多次复现是补充证据，不重复创建大量相同提醒。新任务根据语言、框架、平台和动作检索相关条目，不在每次启动时加载全部内容。

建议恢复包分三层：很短的项目入口说明、当前任务包、按需读取的历史证据。正文预算可配置，超出时返回可继续读取的引用。工具日志、完整 diff 和历史测试输出放在证据文件，摘要只记录结论和链接；测试失败时应能直接定位原始输出。

状态更新发生在有意义的边界：任务开始、完成一段行为、验证结果、关键决定和交接。无需为每个小修改再写计划、再写报告、再写交接。验证从相关检查开始，完整发布/恢复检查在需要它的阶段运行，不为普通开发重复执行所有门禁。

旧 Project Archive 的来源、修订和可恢复性思想可以保留，庞大的文本注入、重复验证与重型门禁不应作为新项目工作台的默认形态。框架与文档规范服务于实际协作，而不是让编码体维护越来越长的仪式记录。

## 17. 模型路由网关：原生协议优先

网关管理命名线路、上游地址/密钥、模型标识、协议能力、客户端配置、配额与健康。客户端使用固定入口和自己的线路配置；在界面切换默认线路，无须逐个修改局域网程序。

建议明确两条路径：原生透传默认保留协议、请求体未知字段和流式事件，仅做已声明的鉴权与线路选择；兼容转换只对明确支持的协议/模型启用。不能默认先把所有模型转换成 Chat Completions，再期待保留原功能。

| 必须保留或明确处理 | 设计要求 |
| --- | --- |
| 模型标识 | 逻辑别名与上游真实 model 分开；所有映射可见，不悄悄替换 |
| 思考参数 | Responses 的 reasoning.effort、Chat 的 reasoning_effort及其他供应商字段分别处理；不支持时明确报错 |
| 工具与结构化输出 | 保留调用 ID、参数、结果关联、schema、工具选择与顺序 |
| 流式协议 | 按原事件转发，避免缓冲到完成才输出；正确传递取消和错误 |
| 多模态与附件 | 图片/音频/文件、multipart、供应商引用和相关请求头按实际接口保留 |
| 状态与缓存 | previous_response_id、会话/文件 ID、签名或加密 reasoning item、缓存字段按来源线路管理 |

官方 OpenAI 文档显示 reasoning 参数位置与支持值依模型和接口而异；存在请求能够到达服务器但某功能不被对应接口支持的情况。因此能力必须按具体模型/协议声明，不能把所有思考等级硬映射成同一组值。[^43]

原生线路需要成熟 HTTP/SSE/WebSocket 实现与测试，不能简化成只转发 messages/model 的几行代理。LiteLLM/New API 可作为候选组件或转换后端，但必须验证实际版本；支持很多模型不等于所有参数都零损通过。[^44][^45]

自有 ai-routing-gateway 已有线路、客户端绑定、回滚和原生请求规划，但 HTTPS/SSE 数据转发与数据入口尚未实现。当前规划器还会用线路配置覆盖客户端 model 与思考强度。建议复用这些基础，重定参数优先级：保留客户端值、仅补默认值、明确强制指定三种策略；完整透传不能沿用静默覆盖。旧控制层的复杂度按本产品需求重新取舍。[^46]

## 18. 切线路、模型真实性与网关验收

“一键切线路”首先影响新请求/新会话。已有会话若依赖上游状态 ID、文件或签名内容，需要继续使用原线路，或由支持的客户端重建可迁移上下文。不能把某供应商的 response_id 直接交给另一条线路并宣称无缝续聊。

网关保存请求线路、模型映射、上游响应声明、能力探测和失败原因。它可以证明自己没有篡改指定字段，但不能仅靠模型自述或响应中的 model 字符串，证明第三方中转实际运行了哪个模型。对上游真实性的保障需要可信供应商与可核对的来源，不能伪装成协议代理已解决的密码学证明。

| 验收组 | 必测内容 |
| --- | --- |
| 原样转发 | 已知/未知字段、原生请求头、别名开关、模型名与思考参数到达录制上游 |
| 交互连续 | 工具调用与工具结果、结构化输出、多轮状态、文件/图片与引用 |
| 流式与失败 | 分块、取消、超时、上游 4xx/5xx、部分输出后断开；不能盲目重放有副作用请求 |
| 线路切换 | 新会话切换、旧会话粘性、同名模型的实际映射、回退是否可见 |
| 兼容转换 | 字段映射表、未支持参数的明确失败、不得静默丢参或降低思考等级 |

先用无费用的录制/回显上游验证转发语义，再对批准的真实线路做少量端到端测试。计费与思考 token 缺失时显示未知，不以响应快慢或有没有思考文本推断参数已生效。

LiteLLM 的 pass-through 是可用参考，但其文档将该配置中的认证能力标为 Enterprise。个人网关不能未验证就依赖它提供完整免费认证；可以由天枢入口负责客户端认证，并按版本评估转发组件。[^44]

## 19. 总体架构与数据归属

建议保留独立产品边界，同时减少基础设施种类和重复基础代码。先采用少量服务与模块化单体，不引入大量微服务、复杂身份联邦、全局工作流总线和独立图数据库。

比较三种部署方式：全部合成一个程序初期调用简单，但会扩大插件、媒体任务与设备执行故障的影响；每个功能都独立服务会重复身份、状态和运维工作；保留少量产品边界、内部模块化、共用基础规范更符合个人自用与持续扩展。该选择是基于本项目的工程判断，仍需通过实际运行验证。

| 运行单元 | 主要职责 |
| --- | --- |
| 天枢平台 API + Console | 管理入口、简单账号/连接配置、设备连接器、项目工作台、订阅与下载任务、资料入口、运行概览 |
| 天枢记忆 API + worker | 人物索引、整理记忆、画像/关系、事项、知识、Worldbook、按受众的检索与纠正 |
| 陪伴核心 + worker | 人格装配、当前状态、发言与生活循环、创作配方、工具选择、消息投递及客户端房间 |
| NoneBot 接入插件 | QQ/TG 事件规范化、账号路由、媒体与发送回执；不复制另一套人格与长期记忆 |
| 模型网关 | 原生转发、命名线路、能力/状态粘性、可选转换与用量 |
| 现有外部能力 | Chat Audit、ComfyUI、Home Assistant、GsCore、RSSHub、Komga、Suwayomi及游戏管理后端 |

一个 PostgreSQL 服务可承载自研领域的独立 schema/数据库和账号；领域只写自己负责的数据，通过清楚接口协作。是否独立部署 worker 按阻塞和资源需求决定，不把每个逻辑模块都变成网络服务。

项目服务负责项目当前任务与交接，Git 负责代码与版本化文档；记忆服务索引项目资料和经验，不成为第二个任务主库。Chat Audit 负责原文，记忆引用它；AssetLibrary 可负责文件预览和资产索引，下载服务负责获得和发布文件。[^25]

正常聊天直接调用记忆与模型服务，控制台维护不应成为每条消息的必经路径。运维、家庭控制、资料和项目工具由各自执行器处理，陪伴角色作为有能力范围的入口。一个动作只有一个负责执行和确认结果的服务。

## 20. 权限与流程怎样简化

产品界面只需少量概念：平台管理者、各角色主要用户、普通聊天者；每个角色开放哪些能力；哪些群启用观察和主动功能；某类资料可在哪些场景使用。能力配置一次，日常正常行为自动运行。

| 保留的约束 | 简化方式 |
| --- | --- |
| 私聊不泄露、人物不混淆 | 后台自动按人物和场景过滤；不让管理者维护复杂 Grant 图 |
| 服务和设备有身份 | 一次配对、可撤销连接密钥；普通家庭节点不要求手工维护完整 PKI 流程 |
| 动作可控 | 常用可撤销操作按角色预设执行；新增部署、网络变更、删除覆盖给一次具体确认 |
| 记忆可信 | 普通获准来源自动整理；敏感跨场景、身份合并、冲突和正典修改做例外处理 |
| 出错可追溯 | 任务/消息/配置变更有记录和来源；普通聊天不走十阶段运维审批 |
| 数据可恢复 | 一致备份、版本与恢复验证；不要求每次读取验证全部历史或全局签名链 |

旧系统中多套登录、逐会话手工开通、到处重复的身份票据、全历史健康检查及普通开发反复全量门禁都应重新评估。统一基础身份和常用设置，但不通过共享管理员密钥给所有角色来实现便利。

日记的互动锁、主要用户亲密表达和设备管理权限独立。这样可以让角色有自己的小秘密，也让“打开灯”方便执行，而不会让高好感度成为读取别人的私聊或修改路由器的万能钥匙。

## 21. 首批共同接口与故障规则

| 接口族 | 输入/输出重点 |
| --- | --- |
| 人物与连接 | 平台稳定 ID、人物编号、昵称/头像、角色关系与场景策略 |
| 事件接收 | 原消息 ID、观察账号、发言者、角色、房间、引用/编辑、时间、现实范围、持久接收结果 |
| 上下文与追溯 | 用途、允许范围、人物/时间、预算；原文/记忆引用、修订、可信度和降级状态 |
| 事项与世界 | 本次事项、状态、期望版本、提及记录；世界事件的参与者和各自所知 |
| 任务与能力 | 动作名称、目标、参数、期限、幂等键；真实状态、结果/错误、取消和重试 |
| 资料与作品 | 来源 ID、元数据、归档目标、作品版本、素材与提示配方版本 |
| 项目恢复 | 任务、分支/工作目录、最新检查点、必要决定、证据引用、未提交变更 |
| 网关与设备 | 线路/协议能力、状态归属；实体/实例与已登记操作，不让模型猜内部地址 |

接口名称为设计语义，具体路径在实现阶段确定。一次请求的幂等键限定动作、调用者和参数；参数改变不能沿用旧结果。异步接收成功、执行完成、消息送达和对方阅读分别记录。

Memory 故障时继续近期聊天并排队获准事件，依赖最新事项的主动跟进延后；模型/生图故障保留任务，不生成虚假完成；平台掉线后按时效判断是否补发。删除和纠正传播到派生资料与缓存，恢复备份时重新应用撤回记录。

健康检查区分进程、API、工作队列和外部依赖。数据新鲜度、缺失、未支持和失败分开展示，不用假零值或静态“在线”图标填满界面。

## 22. 完整体验验收与旧代码取舍

完整目标必须能通过以下场景：同人在群私聊保持认识；私密细节不串群；A/B 角色各自有经历；作息可以合理调整；衣橱驱动自拍；日记连贯且不抄流水账；找到资料后适时分享；已完成事项停止跟进；下载后可在正确库中找到；聊天控制家庭设备；容器/游戏操作有真实结果；更换编码体能继续工作；网关保留模型与思考语义。

| 资产 | 建议 |
| --- | --- |
| Chat Audit Core | 优先复用采集、媒体、搜索和备份；补受场景限制的服务读取与 TG 适配 |
| 本地 Anima 图与桥节点 | 保留工作流和素材；重做通用参数绑定，逐能力补参考/重绘图 |
| Together / Reality | 复用已授权客户端/网关/媒体体验；去除对 AstrBot 内部对象的硬依赖 |
| 原天枢记忆 | 复用可靠的来源、纠正、检索和恢复经验；不要求保留现有全部模型、校验层和 UI |
| 原天枢中控 / nas_ops | 提取现有端口、模板、Compose、日志与检查能力；去除 AstrBot 耦合，简化审批 |
| 项目 Archive 与 AssetLibrary | 复用可读资料、版本、文件预览与索引；避免复制全部业务或沿用不需要的复杂度 |
| Download Hub / JM | 复用已核实的搜索、章节、打包和归档；补持久任务、原子发布与并发去重 |
| MoviePilot 插件 | 提取影视搜索、任务、订阅及通知客户端；独立接入新平台 |
| dev_handoff 插件 | 复用交接入口和展示；后端 controller 尚待定位，不能视为完整工作台 |
| ai-routing-gateway | 复用原生请求规划与线路绑定；补实际传输并纠正模型/思考字段覆盖策略 |

开发顺序在完整目标确认后安排：共同人物/任务/连接基础；聊天与记忆闭环；小屋/衣橱/日记；家庭设备和健康；资料订阅下载；项目工作台；网关完整兼容与多端完善。各阶段都保留完整需求编号，不将晚实现功能从最终产品中删去。
