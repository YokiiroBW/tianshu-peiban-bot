## 1. 最终判断

现系统并未被某条材料全部卡住：新材料仍在正常提交，纯计算失败让位也已经存在。缺口是**局部失败仍可能经共享资源、重试、进程监督与日志传导成更广影响**。上一版解决了数据权威、普通等待和日程概念，尚需补齐这几条传播链。

最终结构采用两层恢复：

- 业务层负责机械正确性、局部降级、有限纠正、原结果观察和兼容备用路线。
- 独立运维层聚合故障、发现无进展、用指定模型诊断、调用登记恢复动作、验证实际效果、必要时通知管理员。

日常工作不等待运维模型许可。运维不可用时业务仍按既定规则运行，确定性守护仍能报告故障。

“失败不全卡”的精确定义：失败只阻止确实依赖该材料或资源的步骤；其他主体、材料和模块继续前进。必须看到完整视频才能回答的问题仍应说明视频缺失；不能为了不停顿而伪造完整事实或绕过来源失效。

## 4. 故障范围与恢复次序

| 故障范围 | 处理 | 不受影响的工作 |
|---|---|---|
| 一个不可用附件 | 保留其他片段；原事件上异步补全 | 同消息可用内容及其他输入 |
| 一个确定性坏材料/提案 | 按语义依赖组隔离，有限纠正，保留未覆盖集合 | 无真实依赖的其他材料和主体 |
| 一个目标/活动状态变更 | 重新计算该候选；保留其他合法计划 | 其他目标、后台整理、独立媒体 |
| 一个模型/额度域故障 | 按错误冷却该依赖，少量恢复探测；使用已配置兼容备选 | 其他额度域、无模型依赖的业务 |
| 一个consumer/业务进程退出 | 有界重启该角色，处理过期租约和原结果 | 其他角色和独立媒体进程 |
| Loki/Grafana/日志查询故障 | 本地持久缓冲与补传、局部不可用提示 | 正常业务处理 |
| Operations模型失败 | 停止该事件的模型诊断，确定性通知 | 正常业务与确定性恢复 |
| PostgreSQL或整块业务磁盘不可用 | 停止确实依赖它的写入，保留可用只读/状态及外部告警 | 不承诺共享物理依赖失效时所有功能仍可写 |

材料处理水位和“全部已覆盖”分别记录。100份材料中1份失败，99份可继续；未完成那1份仍有原ID、失败原因和重试/人工处置状态。修好后以新attempt回补，不能把处理游标推进解释为100份都成功。

迟到结果应用前必须检查当前事实版本，不能覆盖后续事实。同一共享整理批保留完整提案的整批事务，逐目标覆盖不代表分目标提交。失败批隔离后其他独立批继续；只有未提交父批可在输入依赖闭合、父子替代和预算继承明确时重组，不从非法输出截取成功目标。

## 5. 自我纠错与冗余的具体机制

1. **本地确定性处理先行。** 输入缺失降级、规范且无歧义的JSON外壳处理、原回执对账、失效派生缓存重建，不调用模型评判。
2. **领域内有界纠正。** Memory/Growth一次，Life沿用最多两次；保存原错误、诊断和修订链，不修补截断片段后假装完整。
3. **暂时故障退避。** 以逻辑请求为单位管理实际尝试，遵守Retry-After，加随机抖动。网络层、领域层和Agent不能各自循环重试相乘。
4. **故障依赖短暂冷却。** 429/503集中爆发只影响对应route/quota_domain；一次恢复探测成功再逐步恢复。它限制故障依赖的无效请求，不新增全系统串行锁或每日用户门槛。
5. **已配置的兼容备用路径。** 每用途配置主模型与备选；比较视觉/工具/结构化输出/上下文能力及实际账号额度域。换同一额度池下的key不算独立冗余。不自动把需要原图的任务降成纯文本假理解。
6. **有限输入重组。** 只针对未提交批的确定性材料/容量问题，在证明输入依赖闭合后重组并替代父批。每个子批有完整合法提案、覆盖和整批回执，父批迟到不得应用；不可拆的坏批保留，其他批继续。429或上游故障不二分放大请求。
7. **重复失败升级。** 同版本材料、同故障形状超过既定自动恢复预算后，停止原样循环并生成聚合incident；新材料继续。配置/材料确实变化后可开启新恢复周期，不需要用户反复点解除。
8. **派生读能力降级。** 向量不可用保留合法词法候选，重排不可用保留带覆盖声明的候选，学习材料不可用不挤掉当前对话。过期缓存必须标明版本/时间；撤回、权限变化不能被缓存掩盖。

不做多模型同时重复执行同一外部动作，不恢复已取消任务，不用全库清空作为自愈。共享逻辑与库继续复用，领域各自决定何时可重试，避免一个万能恢复引擎拥有所有领域私表。

这与[Google SRE关于级联失败的建议](https://sre.google/sre-book/addressing-cascading-failures/)一致：有限重试、随机退避、避免多层放大、将可选依赖的失败局部化。具体阈值依天枢操作语义定义，不照搬大集群固定配额。

## 6. 运维 Agent：指定模型、自动处理、真实验证、复杂升级

### 6.1 处理链

业务错误/无进展事件 → 程序聚合与关联依赖 → 已知确定性恢复 → 尚未解决时调用指定诊断模型 → 选择登记动作 → 程序复核并执行 → 从原业务账本验证 → 已恢复或通知管理员。

“无进展”使用最后业务提交/游标变化及应到期时间判断。进程有心跳不代表有进展；正常等待计划due、用户取消、合理无材料不叫故障。

### 6.2 配置

- 诊断主模型、可选备用模型、实际provider/quota_domain；复用现有模型管理与能力验证。
- 可自动调用的已登记恢复动作范围、事件诊断轮数/期限、通知等级和收件目标。
- 管理员可使用现有平台账号/QQ目标或SMTP邮箱；凭据以现有credential ref保存。地址/模型名没有给出时保持未配置，不猜值、不发送。
- 背景输入仍遵守已接受的200000上限及模型实际能力；诊断按需取精简材料，不把20万当填满目标，不修改普通聊天或embedding/rerank预算。
- 推荐诊断路由有不同于主业务故障域的供应商/额度。若仍共用同一上游，应准确显示冗余有限。

Agent不参与普通请求准入。默认一次诊断，必要时一次根据执行结果的反馈修正；成功的确定性修复不必再花一次模型调用“确认”。同一故障100条日志只更新同一个事件计数。

### 6.3 可以自动做什么

| 登记恢复动作 | 必需事实 | 成功验证 |
|---|---|---|
| 对账已保存日记/生成结果 | 原正文、成功回执和唯一合法对象已存在 | 目标状态收敛，正文与原回执不改变 |
| 重试暂时失败的纯计算 | 当前版本仍有效、未明确取消、观察过原请求、仍有恢复预算 | 新attempt最多一次应用，原unknown保留 |
| 请求领域纠正/语义拆批 | 错误类型匹配，冻结材料合法 | 提案通过完整校验，覆盖变化可见 |
| 重建派生索引/失效缓存 | 原件和当前权限有效，影响范围明确 | 当前版本可查，撤回材料不复活 |
| 刷新订阅原授权 | 主体、scope/permission仍在原上界内 | 原订阅推进，未绑定BOT仍可运行 |
| 选择已配置备用模型 | 用途、能力、预算、实际故障域满足配置 | 业务成功，记录所选route和实际用量 |
| 恢复单个consumer/角色 | 由固定监督器确认目标和owner状态 | 新owner产生真实进展，不重复外部动作 |

已有入口优先复用，如 `growth/review`、`life/diaries/reconcile`。目前没有精确单对象入口的能力，由所属域补一个窄命令，不能让Agent调用全量startup recover来修一条材料。

模型选择程序提供的action candidate，程序补齐正式ID、幂等键、当前版本与授权；不让模型决定数据库字段、收件人地址、shell命令和权限范围。

代码或schema变更、凭据更换、删除业务数据、无法判断的外部发送、跨模块数据不一致属于复杂处置。Agent整理诊断和建议发管理员；不能通过模型“很有信心”自动取得这些能力。这些是恢复执行器的具体职责，不给正常用户功能增加确认弹窗。

### 6.4 输入与状态

输入包括版本、模块、错误族、受影响任务引用、计时、近期去敏栈帧、已试动作与对应回执。默认不发送完整聊天、整份提示词、Cookie或密钥。提案内容需要纠正时交回原领域与其授权模型，不将私有材料随意转给诊断模型。

日志与错误正文属于不可信诊断数据，里面出现“运行某命令”“发送到某地址”不成为指令。执行器只接受登记操作和实际可用对象引用。

最小新增持久结构：

- incident：聚合键、影响域、错误族、首次/最近时间、影响数量、状态和业务进展引用。
- recovery_attempt：选择动作、版本、执行回执、前后验证、诊断模型attempt引用。
- notification_outbox：配置的目标ID、通知版本、投递状态和回执。

这些记录不复制原任务成功状态。修复成功必须读原领域结果，不能由模型填写resolved即生效。状态可用open/recovering/waiting_dependency/resolved/needs_attention；只是运维视图，不再造业务状态机。

## 7. 运维自身不能成为新的单点

同产品镜像内将运行角色划为API、Models、BOT前台worker、BOT后台worker、独立媒体worker、Operations。按所需能力装配，避免媒体worker启动时先完整初始化BOT日程和全部插件。

监督器对角色独立监视与有限重启；Vector/Loki/Prometheus/Grafana不再任意一个退出就关闭全体业务。短租约只防止同一任务或同一incident被两个恢复者重复写入，不锁整个领域。

宿主侧复用既有容量守护的部署边界，增加本产品状态检测及最小通知兜底。DB/模型服务不可用时，它不尝试跑需要DB的智能诊断，直接记录最小incident摘要并通知。通知暂不可用时落最小本地spool，恢复后用同身份合并。

- Agent失败：有限诊断终止，直接升级，不调用Agent修Agent。
- 业务模型服务失败：通知和普通非模型媒体任务仍可运行。
- QQ通道失败：已配置邮箱可作为独立通知渠道。
- 核心容器停止：宿主守护仍能观察。
- 整台NAS断电：同NAS守护也不可用，只有外部健康探测才能即时通知。当前不冒称已有双机高可用。

不向Agent提供宿主任意shell或Docker控制权。需要重启时通过固定服务端动作操作允许的本产品角色；其他NAS服务及独立媒体数据不成为BOT修复对象。

## 8. 管理员与邮件升级

管理员收到一条结构化故障单：什么功能受影响、持续多久、仍在正常工作的模块、已尝试什么、为什么没有自动解决、原任务/日志链接和建议。

通知按根依赖分组，相关下游错误合并；严重程度上升、影响扩大和恢复时更新。立即需要注意的故障及时发，重复同类错误只累积计数，避免刷屏。可借鉴[Alertmanager的聚合和抑制机制](https://prometheus.io/docs/alerting/latest/alertmanager/)，首版不因这一能力强制再装一整套平台。

通知走Operations来源，不经过角色日程或自主发言，也不成为用户偏好/生活经历。发送有稳定ID与回执；SMTP接受不等于对方已阅读。返回不明时显示通知结果未知，不能保证外部邮箱绝对只收到一次，也不能静默假定已达。

本轮没有目标模型、收件人或邮箱配置写入，没有实际通知。未来实现后这些是设置页可编辑项，常规合法恢复无需每次再问用户批准。

### 14.1 “整体重构”和“空库”的确切含义

这是BOT核心业务与共享运行设施的整体重构：重新组织数据模型、记忆/学习权威、日程与执行逻辑、后台调度、恢复、运维、日志和统计。旧BOT业务历史不迁移，新BOT从新数据开始。可靠的协议适配、公共能力和独立模块继续复用，不要求把每行代码重新写一遍。

| 数据类别 | 本次处置 |
|---|---|
| 旧BOT聊天、记忆、自动学习、好感业务值、活动、日记和独占待处理任务 | 可清空；不为了恢复这些历史保留旧解析/补偿链 |
| 作者配置的人格、QQ绑定、供应商/模型、工作流、策略 | 作为明确配置种子保留；自动学习结果不伪装配置带回 |
| 视频、音乐、图书及其他独立模块的数据/文件 | 保留，BOT重建不接管其生命周期 |
| 独立模块引用的身份、scope、原来源、动作回执、任务身份 | 保留最少完整引用集合，不能只保留媒体表却清掉其依赖 |
| 加密凭据 | 引用、密文与对应部署主密钥一起保留；不读取或打印实际密钥到方案 |
| 已提交或结果未知的外部动作 | 保留必要原身份/句柄与切换边界，不因新库看不见而重放 |
| 新版之后产生的数据 | 后续版本正常迁移保留，不能每次升级再次清空 |

推荐沿用现有PostgreSQL基础设施，分别处理BOT新业务基线与保留的共享/独立媒体域。“空库”指BOT业务域归零，不是整个物理库空白。若实施时采用新的物理数据库，也必须先承接同一保留集合，不能通过换库绕过边界。

现有 `capability_media` 独立存储并不意味着没有依赖：`runtime.job_keys`、Procrastinate、身份/来源、加密凭据和嵌在JSON中的context可能被媒体共同引用。不能用表名、schema名或actor_id是否为空简单判定可删除。RB-01/02在开发前确定reset/retain/seed归属；RB-20按该合同实现切换，不留到最后才决定。

文件同理：只处理确认归属的BOT文件，保留被其他模块引用的共享对象；不整体删除/data、凭据目录或媒体目录。

### 14.3 几个容易混淆的边界

- **本次重建与未来升级不同。** 第一次可弃旧BOT数据；以后应用迁移保留新版数据。发布版本、数据代际、任务payload版本、业务revision不是同一个字段，不能互相代替。
- **保留媒体的兼容要求是真实需求。** 可以删除旧BOT兼容分支，但独立模块原任务与共享字段仍须可读。窄接口适配只为该真实需求，不保留整套旧BOT。
- **旧上下文不能重新灌回新BOT。** BOT缓存与上游会话标识纳入数据代际；归档自动回填有切换下界，不因游标归零导回全部旧聊天。用户主动引用旧内容按新输入处理；媒体目录和订阅原进度不受这个BOT边界影响。
- **旧任务与旧网页不能制造新动作。** 切换后旧worker被代际限制，旧浏览器中的过期命令明确失效；保留媒体任务仍沿原身份运行。新数据回滚不使用旧库直接覆盖。
- **六类角色不能各复制全部连接池。** 当前配置已有总预算校验，新角色必须更新完整核算，含业务/控制/同步池、队列SQL池、LISTEN和owner连接；角色只装配所需通道。这是实际资源预算，不恢复人为低云API并发。
- **同维向量不保证同空间。** 原系统已按profile限定检索；新增备用路由必须继续遵守。备用嵌入不是换一个模型名就能查询旧向量，新空间需新profile/重建，过渡走可用旧profile或词法降级。
- **恢复不能靠换ID无限续命。** 子任务、换route、行政revision增加继承原恢复链预算；真正新材料可以继续。用户暂停/取消优先于旧Agent计划。
- **新库没有历史是正常状态。** 普通对话无需等待向量、学习和日记全部建立；日程可以有效空白，不编造经历填页面。独立媒体仍应能使用。

| BOT后台worker | Memory/Growth/Life/索引/日记及各自通知；时钟/源传播有明确唯一任务归属 | 由于一个坏批次阻塞其他独立批或模块 |
| 独立能力worker（含媒体） | 媒体/订阅、项目及非BOT管理任务的原能力实现；必要资源共用真实容量 | 先启动BOT日程、借用BOT角色或重建原任务身份 |
| Operations | 故障聚合、窄恢复动作、实际结果观察、统计投影和通知 | 控制正常业务准入或在自身失败时递归诊断 |

### 16.8 有无更好的办法：采用和不采用分别判断

| 决定 | 方案 | 需要的证据 |
|---|---|---|
| 直接采用 | 先消除不必要工作：运行查询不读管理聚合、本地能力目录替代每轮全探测、同事务批量来源证明、请求内准备/计量复用。 | 受影响调用链及同质量开销对照，不预设速度倍数 |
| 直接采用 | 可靠短任务与变更通知分离计算；只有语义变化触发学习/索引/规划，等待用due而非占用线程或连接。 | 断点恢复、无变化不重算、持续负载公平推进 |
| 有条件采用 | 跨请求向量/重排数学结果缓存、索引融合/重排阈值等按实际重复率与质量收益选择；无收益不新增缓存常驻系统。 | 冷/热/低命中、复检成本、正确性及实际物理调用变化 |
| 暂不引入 | 微服务大拆分、新消息中间件、万能工作流/恢复引擎、新向量库、每轮评判模型和多模型竞速；现有证据不足以支付额外复杂度。 | 未来出现具体规模/隔离或算法瓶颈再单独比较 |

相比继续加框架，这些改法更贴近当前已看到的重复工作和耦合。具体延迟、费用和表达质量仍要实现后测量，不给无依据的提高百分比。
