# R58：索引发现不再等待写锁

R58 已部署并通过启动检查。本次只改 Memory 的待建向量发现过程：读取待办及来源范围时使用一致只读快照，空闲索引不再为这段只读查询申请写事务。后续两次来源复核、权限、内容哈希 CAS、向量写回和 SourceAuthority 的原串行顺序保持。

Memory 代码提交：`3e3cf504b611e004443907307dc3d3c2b26e2af3`。Companion 及其他产品、模型和前端保持 R57；PC-12～17 的已部署实现保留。配置只发生既有同所有者 Gateway 启动租约续接；Memory 的 v1.1 合同路径、全部合同、配置数据和数据库结构保持。

实际验证：

- 新增用例在原 R57 安装镜像的私有及群两个范围均以 TimeoutError 复现：另一个写事务未结束时，空闲索引发现无法返回。候选 R58 同两例通过。
- Linux 实际安装轮子定向组 10 项通过，覆盖读连接释放、原生索引/排序路径、来源撤回后的晚向量不能复活、工作线程恢复与新争用场景。另有 4 个旧断言失败，已经在未改动的 R57 安装镜像复现相同失败：2 个仍期待旧 fact.value 的断言、2 个既有 lexical fallback 非空断言。未删改这些断言，也未把 14 项称为全通过。
- 实际 PG 执行代码中的事务语句，证明 repeatable read、transaction_read_only=on、当前事务 advisory 写者锁为 0；未建立第二个生产 Store/Core、未写生产数据。
- Windows 临时环境缺少 av，相关产品用例未运行，未为本任务安装媒体依赖。以上结果来自已有 Linux 镜像、合成来源与隔离临时库；镜像无生产挂载和外部网络。Ruff 与 diff 检查通过。
- 新 Memory 158 个安装文件、原 58 个应用文件及 87 个前端文件核对通过，业务 UID 可导入。部署后 6 个业务模块、5 个观测进程、认证就绪、TLS、网页与受影响模块字节通过。

R57 正常排空 124.00 秒后退出 0，才启动 R58。37 个挂载、15 个非目标容器保持；容量下限仍为 20 GiB。没有 DDL 或数据迁移，旧镜像与代码回退入口保留，未执行回滚。

查询长尾仍需分项看待。此前同一故障中，HTTP 约 15 秒截止后，第一次同步查询仍工作至约 30.17 秒，与第二次读取重叠。本次修复证明并移除一个不必要的写锁等待，不代表已经定位或解决那次 30 秒的全部耗时，也没有修改总超时、重试或授权策略。

已有采样的补充解读：先前“只见空闲”仅描述 Memory 事件循环线程。重新分析相同原采样中的 AnyIO 与索引线程，发现来源顺序等待及远端校验等待；没有重新采样，且不能把事后样本当成原故障调用栈。当前 12 次简单 SELECT 1 往返约 3.15 毫秒，相关域 15 组/38 文档；这些简单查询快速，仍不足以排除完整 context/query 中的复杂 SQL、其他锁或外部阶段。
