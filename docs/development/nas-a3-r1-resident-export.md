# NAS A3-R1 resident candidate export

This is a local candidate interface. It produces Dockge stack files and a lock receipt; it does not write a NAS path, start a container, or establish live acceptance. The only emitted state is `resident_candidate` with `pending_live_acceptance` and `release_ready=false`.

## Inputs and exact source

- Start from the `a47b70c28e3d71dca80023a98e8b5360694b27e5` coordination baseline. The resident OBS compatibility source is the fixed Git object `a194fa7b527ac2da0f13b8c3e95e76a1b836b4b3`: the baseline's three-network OBS template plus only its resident profile binding. The older `65b88a6d1c2b5047ca6bfb2f7f7484749eb14154` two-network source and its NAS result do not prove this new source.
- `release-manifest.json` remains `status=candidate`, schema 1.1, and pins that OBS commit. All four product images and five OBS images require `@sha256:<64 hex>` references before export. Synthetic test digests are not deployable evidence. Product source Git SHAs and the OBS source tree are locked in the receipt; OBS bytes are compared to `git show` at the fixed commit.
- Prepare a new bundle using the public `deploy/tianshu/release.py init` inputs or A1's first-install `prepare` wrapper. Keep credential values in the separate protected input file. The resident site has `project_name=tianshu-v2-resident`, `resource_profile={"kind":"nas-cpuset-resident-v1","cpus":[6,7],"pid_limit":"unsupported"}`, `public_web=true`, a matching RFC1918 IPv4 bind and `http://<same IP>:<port>` origin, and explicit nonoverlapping `auxiliary_subnets` for `egress` and `frontend`. All four internal TLS certificates are operator supplied; internal service traffic stays HTTPS. No A1 loopback API ports are accepted.
- Run the public `configure-observability` command against that bundle with a settings file, fixed root repository and fixed product Git objects. Give OBS its own explicit three nonoverlapping private subnets (`observe`, `storage`, `access`), loopback Grafana and Guard ports, four application log budgets matching the four actual product settings, and five pinned image digests. The OBS package exports nine total services as two projects. Configure does not start them.

Offline export example, after both preparations succeed:

```text
python deploy/tianshu/resident_export.py --bundle <prepared-absolute-bundle> --repository <fixed-root-git-repo> --deployment-root /volume1/tianshu-v2-resident --output <new-local-output-directory>
```

The new output directory contains `tianshu-v2-resident/compose.yaml`, `tianshu-v2-resident-obs/compose.yaml`, and a mode-0600 `resident-export.lock.json`. JSON is valid Compose YAML. Both stacks use absolute bind sources rooted only at `/volume1/tianshu-v2-resident`, and fixed, distinct Compose project names. The private receipt hashes the two Compose files, configuration, private env files and source, and records every image and mount. An incomplete write leaves `INCOMPLETE` and no valid completed receipt. Never import a compose file if its receipt, prepared bundle or actual NAS target differ. The output directory must be absent before export. The deployment root is a *declared* NAS path; the offline exporter cannot prove that remote path is empty or has the expected ownership. A1/live installation must fail on an occupied or mismatched target before copying any bytes.

## Lifecycle and live acceptance boundary

All nine services use `restart: unless-stopped`, a fixed memory limit and `cpuset=6,7`. CPU hard quota and PID limit are deliberately absent because the observed NAS controller does not provide those guarantees. This profile is not a verified release profile; `preflight --release` still refuses it. Before maintenance, resolve the exact two project container IDs, disable their restart policy, read it back, then SIGTERM and wait for exit. Restore `unless-stopped` only when maintenance is complete and the reviewed stack is being resumed. Dockge must not independently recreate a stopped project during maintenance.

The new OBS source has `observe` and `storage` internal bridges, plus one noninternal `access` bridge used only by Grafana and Guard for `127.0.0.1` host ports. All six core and OBS subnets are explicit, private and nonoverlapping in the export lock. A live check must verify these port and network bindings, nine container image digests, effective cpuset/memory/no quota/no PID, private file permissions, bind source ownership, target emptiness, independent project names, authenticated readiness, and a four-source security event path through Vector, Guard and Loki with zero unexplained loss. The three-network OBS source needs its own NAS acceptance; the earlier two-network test cannot be inherited.

The application settings budget four source log directories at 1 GiB each. The exporter checks those budgets against platform/gateway settings and the fixed companion/memory baseline, plus Vector's 4 GiB disk buffer and Guard's 1 GiB storage reserve. Guard can refuse pushes with 503 at its storage threshold; Vector retries. This does not stop a full host volume, application source writes, or other NAS writers. Grafana 80% application budget and 85% disk high-water rules are alerts, with delivery still unconfigured. No source reclamation or 30-day retention is accepted. For a staffed trial, record the actual capacity of source, Vector buffer, Loki/WAL, Prometheus, Grafana, Guard and Docker log volumes; reserve and stop thresholds; polling or notification destination; latest stop deadline; and named stop operator. A declared threshold is not a protection until its consumer and stop action are observed in the live run.

The local Windows joint test runs real bundle initialization, exact Git OBS export, public configure with TLS handshakes, OBS binding, preflight and Dockge export using isolated contracts, product Git objects, short-lived synthetic certificates and synthetic image digests. It replaces only Linux UID/GID chown, which must be checked on the target host. No NAS write, stack startup, live throughput, full disk or retention test is claimed.
