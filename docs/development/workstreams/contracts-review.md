# 并行开发前的契约审查

日期：2026-09-14。状态：开发准备建议；没有创建业务接口、运行服务或完成业务验收。

依据：[整体架构 V2](../../architecture/tianshu-system-architecture-v2.md)、[接口目录](../../architecture/v2/interface-catalog.json)、[消息防抖专题](../../architecture/message-debounce-and-bundling-design.md)。本文细化并行开发流程，不改变 V2 的产品职责。目录中的 I01–I18 是能力编号，其中数项同时包含查询和命令，不能直接当作 18 条已经定型的 HTTP 接口。

## 1. 哪些约定现在就能共同遵守

建议保留四个产品工程目录：`projects/tianshu-platform`、`projects/tianshu-companion`、`projects/tianshu-memory`、`projects/tianshu-model-gateway`。NoneBot 薄桥接包放在 companion 工程中，运行进程仍独立。AssetLibrary 与 Chat Audit Core 保持自己的项目、数据和写入边界；对接前先核实实际版本与可用接口。

- 当前世界、角色、房间、轮次和发送状态由陪伴核心写入；人物、画像、长期关系、整理记忆和知识资料由记忆写入。
- 平台是网页的统一入口和能力协调者，不插入每条 QQ 闲聊的必经链。任务中心只保存投影。
- 网关负责模型运行请求，平台负责配置。提供商密钥不出现在浏览器、通用事件或演示样例中。
- 公共契约只承载边界字段、样例和版本，不能成为各工程共同修改的业务实现层。产品内部数据库结构不作为跨项目契约。
- 原始消息由 Chat Audit Core 长期保管；受管文件由 AssetLibrary 最终发布。短期可靠收件记录与长期归档状态分开。
- 网页不做实时语音通话或共同观影。QQ/TG 的语音消息能力仍保留，首个联调切片可以先只使用文字。

这些约定不要求增加服务网格、统一事件集群、复杂授权图或分布式事务。

## 2. 最先要补齐的具体缺口

下表是建议纳入首个契约讨论的事项。它们是设计缺口，不表示现有代码存在相应缺陷；本次没有审计这些工程的运行实现。

| 编号 | 目录现状与缺口 | 建议的最小约定 | 契约责任方 / 必须参加评审的调用方 |
| --- | --- | --- | --- |
| C01 | I01 接受 `conversation_id`，但未定义它与入站账号、平台群/线程、人物的关系 | 服务端建立渠道会话映射。消息去重键包含渠道绑定和平台消息 ID/版本。防抖收集键按发送者区分；双轮限制与发送顺序使用逻辑会话键，不能混用 | companion / platform、memory |
| C02 | I02 只有核心到 NoneBot 的下行；网页能输入但没有明确回复下行、重连和投递状态 | 核心保存权威回复及序号。网页通过平台读取快照并订阅核心投影；NoneBot 通过发送适配器投递。网页打开 SSE 不触发再次生成或向 QQ 再发一次 | companion / platform |
| C03 | I03 把查找、首次登记、账号关联揉在同一能力名中 | 拆成只读解析、幂等首次登记、经验证的显式关联。调用者不能把任意 `person_id` 当成已验证本人。昵称和头像只更新展示字段 | memory / companion、platform |

| C05 | I05 是已有记录修订；`conversation.turn_committed` 还未定义如何创建首条整理记忆、确认来源与防止重复累加关系 | 核心发出带来源和虚构标识的已提交事件；记忆幂等消费，内部生成候选并决定是否写入。候选提炼与已确认用户更正分开。初版不为此增加通用“模型任意写记忆”入口 | memory / companion |
| C06 | I14 的调用方只有平台自己，I15 又要求网关知道功能绑定与配置版本 | 增补网关读取已发布配置快照的内部契约，明确凭据解析责任和脱敏回执。配置版本固定在请求/轮次上；平台暂不可用时网关能否继续使用已验证配置需写成明确规则。第一版可先固定一个文字工作负载，不实现所有提供商 UI | platform / model_gateway、companion、memory |
| C07 | I15 的原生接口没有决定首个实际协议、流结束/错误、路由回执如何组合 | 先选已有测试条件的一种原生文字协议并锁定兼容样例。保留模型、工具、思考字段；不把自定义路由数据混入破坏原生客户端的响应正文。路由/用量可用关联 ID 在独立诊断记录中查询 | model_gateway / companion、platform |
| C08 | I17 列出投影中心，但各责任方的任务快照、取消和恢复端点未定义；事件游标不等于对象版本 | 首条贯通只定义对话需要的状态事件与快照，暂不做全功能任务平台。以后每个任务责任方实现自己的查询/取消；平台不伪造终态。分别定义事件 ID、对象版本、订阅游标及其作用 | platform / companion、memory，按切片加入外部责任方 |
| C09 | I06 允许现有 OneBot 归档接入，但跨系统原文定位与待补档追踪不明确 | 先核实现有归档入口和读取能力，共用原始渠道消息定位键；核心短期收件状态记录 `pending/archived/unavailable` 等明确归档结果，不因已收件就宣布永久归档完成。没有已验证的写入口时不虚造一个 | companion 与 Chat Audit 适配负责人 / memory |
| C10 | I18 有取消能力，但不能只用一个“取消成功”覆盖封存、生成、待发和外部已执行状态 | 明确目标轮次/意图、取消边界、已发送内容和已经执行的动作。普通续句永远不调用取消。已发生外部事实只回报结果，不承诺撤销 | companion / platform、NoneBot 桥接包 |

I07/I08 的网页管理调用清单没有列出核心内部日程/写作模块，不必为了补调用方而增加内部 HTTP 跳转。相同工程内部可以调用领域函数。I09/I12/I13 的网页操作、预览和计划确认也需要分别列清，但可在对应功能切片开始时完成，不阻塞首轮文字链路。

## 3. 首批契约冻结范围

“冻结”只指下面的边界可以被两边按相同版本实现，不是一次冻结全部数据库或所有远期功能。命名、字段与样例先在中央契约目录形成一个小版本；评审后由集成负责人记录已接受版本。本文本身不是接受记录。

| 契约包 | 必须明确的内容 | 本批不扩展到 |
| --- | --- | --- |
| 公共信封与可信来源 | 请求/事件 ID、schema 版本、时间格式、错误结构、服务认证与原请求来源、幂等键及同键异载荷拒绝、对象版本冲突 | 全组织身份平台、多租户授权图、所有产品共享基类 |
| 消息与轮次 | 入站事件、媒体引用占位、作者/引用/顺序、收集键/会话键/发送目标、接收回执、轮次阶段、取消与发送回执 | 全部 QQ/TG 事件、实时音频与观影 |
| 记忆最小读写 | 幂等人物登记、批量最小召回、完整语义组、当前范围/版本、显式更正、首个提交事件 | 全图谱、完整知识采集、完整关系演化模型 |
| 模型最小运行 | 一个工作负载的显式绑定、配置快照、一个真实协议的请求/响应/流、超时及未知结果、路由关联 | 多协议自动互译、所有模型能力、生产级成本报表 |
| 网页状态读取 | 一角色当前状态和文字对话快照、分页/订阅恢复、冲突与离线展示 | 全任务中心、日记全文、文件与设备实际执行 |

每个契约至少附：一份正常请求/响应、一份边界或失败样例、责任方、调用方、版本、关联验收编号。查询字段不能仅列名称；例如 `scope` 需要明确什么由客户端提出、什么由服务端收紧、拒绝时返回什么。

静默窗口的到期边界沿用已有专题：有效受理时间严格早于截止时间才进入旧组，等于截止时间先封存旧组。时间以服务端受理顺序为准，重投递不重置窗口。旧计时器检查组修订号。不能由各工程各自“差不多实现 5 秒”。

“两轮”必须在实现前说清活跃槽位的释放点、待发送是否仍占槽位，以及缓冲/已封存排队的容量与满载回应。只允许两个活跃轮次是既定约束，具体阶段表达与容量是待冻结参数。无论选哪个释放点，T2 必须可以在 T1 发送结束前进行独立工作，第三轮不能偷偷变为第三个活跃轮次。

对版本冲突、未知结果和来源授权要提供负面样例；模型、网页或调用服务的 payload 不能直接声称自己拥有管理员范围。初期采用少量服务凭据及显式来源验证即可，具体认证方案由首个可联调契约选择，不要求外部客户端学习一套复杂权限语言。

## 4. 最小可联合验证的两条路径

### L0：完全本地的协议贯通

使用脱敏固定消息、确定性时钟与可控模型替身：

`消息夹具 → companion 入站/收集/双轮调度 → memory 人物与定向召回 → model-gateway 替身上游 → companion 回复记录 → NoneBot 发送替身 + platform 只读文字视图`

目的不是证明“会聊天”，而是证明四个工程按同一契约互通。平台不成为入站到生成的必经服务。替身必须运行相同的请求/错误契约，不由前端写一套永远成功的数据假装联调。

| 场景 | 可观察结果 | 对应架构验收 |
| --- | --- | --- |
| 私聊与群聊中出现同一个不可变账号 | 得到同一人物 ID；不同平台同昵称仍是不同身份，未经验证不能绑定 | A01 的最小样本 |
| 0 秒、2 秒、6 秒三条续句，窗口 5 秒 | 第 11 秒只封存一个有原始消息边界的组；重复投递不重置窗口；截止时刻同刻输入按既定边界进入下一组 | A03 |
| T1 模型/发送被延迟，T2 输入已封存 | 记录可证明 T2 独立工作先于 T1 发送完成；发送仍按序。T3 排队，T1 不被普通新消息取消 | A03、A04 |
| 公开兴趣与私聊秘密同时匹配，证据包含“晚上不喝咖啡” | 群请求只拿允许内容，否定不丢失，零项返回合法；更正后旧向量和缓存不能恢复旧结论 | A02、A05 |
| 模型超时、服务重启、重复入站、发送回执未知 | 未执行动作不伪装成功，发送未知不盲目重放，恢复状态能解释；断开平台不破坏已有 QQ 核心路径 | A04、A05 的恢复子集 |
| 网页断线后重新订阅；修改后的调用方仍使用上一兼容版 | 重取快照或恢复游标，不重跑模型；契约拒绝不兼容的必填变化 | A15 的文字范围与兼容性子集 |

L0 通过只能证明协议与调度行为，不能写成 A01–A06 全部通过。特别是替身无法证明真实 QQ 的回执和 GsCore 的独立调用能力。

### L1：小范围真实渠道闭环

L0 稳定后，用登记好的测试 QQ 会话、一名角色、一个经验证的文字模型线路、最小记忆存储和现有归档读取/接入能力验证同一条路径。真实设备控制、NAS 整理、容器部署不加入这次验证；它们不是文字陪伴正确性的前置条件。

增加一条已注册的只读直接功能指令，确认它由唯一处理者回应、不会同时进入陪伴生成；对真实 GsCore 的验证须待适配能力盘点完成。没有接入 GsCore 时，使用示例命令的成功不能代表 A06 已验收。

记录首字、整轮、防抖、排队、召回、上游模型、发送等待各阶段的时间和调用次数。5 秒窗口是可调配置，不能把它算作模型性能退化；自有 p95 500ms 仍是待测目标。先用结果定位问题，不提前以臆测性能数字驱动服务拆分。

## 5. 并行分工与交付顺序

| 工作流 | 先独立交付什么 | 等待的边界 | 联合完成的判据 |
| --- | --- | --- | --- |
| companion | 确定性入站/调度状态机、持久收件和回复记录、NoneBot 薄适配器与发送替身 | C01/C02/C03/C10，记忆及模型客户端样例 | 相同夹具可切替身或真实服务，双轮与有序发送行为一致 |
| memory | 人物登记与最小范围查询、语义组/更正夹具、提交事件消费 | C03/C04/C05，来源与范围约定 | 隐私和语义边界用例能失败于错误实现，旧索引不覆盖权威版本 |
| model-gateway | 一个原生协议、配置快照消费、确定性替身上游和透传夹具 | C06/C07，平台发布配置形状 | 模型字段与流语义保留，失败/未知结果可核对，无静默换模型 |
| platform | 已确认视觉的页面壳、设计令牌、文字/状态投影、最小配置发布与脱敏视图 | C02/C06/C08，当前角色状态投影 | 读取真实服务状态并显示离线/恢复，不维护另一份角色事实 |
| 集成负责人 | 版本锁定、共同夹具、边界验证脚本、组合启动说明 | 各工程提供真实启动与验证命令 | 在单一记录的版本组合复现 L0，再推进 L1 |

小屋样片可作为 platform/companion 的独立探索支线，仅先冻结状态参数的读取样例；不把 Three.js 具体素材格式塞进记忆或网关契约，也不阻塞 L0。选定渲染路线后再冻结正式资源与环境接口。

每个并行任务限定自己的工程和工作目录。公共契约与集成清单由指定责任人写入；其他工作流提交建议，不能边实现边同时覆盖中央文件。跨工程功能以成组变更交付，不能仅凭单仓测试成功宣布整体已完成。

## 6. 轻量变更流程

1. 提出变更时说明具体消费者、触发行为、旧新样例以及是否破坏兼容；记录到当前契约变更单，不为每个字段写长篇设计。
2. 对象责任方和直接调用方共同看样例。产品目标已授权且只是兼容实现细节时，由集成负责人定稿，不反复向用户申请例行审批。
3. 新增可选字段保持旧消费者可工作。删除字段、改变语义或变成必填，发布新主版本，并明确过渡期与切换顺序；不靠“大家一起更新一下”隐藏破坏性变化。
4. 先更新规范样例，再同步生产者与消费者的契约校验。迁移期支持的当前版/前一版要明确列在版本矩阵中，不能无限兼容历史版本。
5. 检查每项改动是否仍符合唯一权威写入者、范围和幂等要求；跑实际存在的窄验证，再跑受影响联合路径。具体命令由各工程真实脚本提供，准备阶段不虚构已经存在的测试命令。
6. 集成记录只保留本轮目标、版本组合、实际验证结果、阻塞与下一步。决策正文和旧记录按需链接，避免把所有历史重复写入每份交接。

任何模拟通过、静态 schema 检查、真实渠道联调和生产验收必须分栏记录。模型替身通过不等于真实模型语义兼容，截图通过不等于界面连接了真实状态，接口目录存在不等于运行端点存在。

## 7. 开工门槛与本轮结论

并行准备可立即进行：工程清单、版本盘点、工作目录隔离、视觉组件提取、样例编写和 L0 替身设计互不阻塞。业务实现前最少需要 C01–C07、C10 的首版约定，C08 缩减为首个状态投影，C09 先完成实际接口盘点和降级约定。

开工记录应能回答：谁签发人物/会话 ID、谁回复消息、什么状态占用两个槽位、网页怎样接收回复、记忆如何首次写入与纠正、网关怎样获得配置、未知发送结果如何恢复。答案不齐时，各工程只能做独立原型，不能声称已经开始可靠的联合业务开发。

其他 I07–I13、I16–I17 的完整能力按生活、资产、设备、项目等切片补齐。无需在第一轮并行启动时实现全部 I01–I18，也无需为每项能力新建服务。
