## 3. 权威、身份与执行边界

| 事实 | 唯一归属 | 其他模块可以做什么 |
| --- | --- | --- |
| 模型 attempt 的物理结果、发送证据、用量和原始回执 | Models | 通过公开 status/result/reusable_result 读取并保存观测；RPC 失败或本地排队状态不能覆盖它。 |
| 恢复 lineage 的总次数、计算/连接预算、依赖冷却、短租约 | Runtime RecoveryPolicy | 领域在自己的事务中调用公开端口；预算可用不等于业务获准继续。 |
| 当前材料、选择的 attempt、业务结果、取消/退休、下一步 | Memory / Growth / Life / Conversation / Capabilities 各自领域 | 本领域重读后判断并以自己的 CAS 提交；不让 Runtime 或 Operations 代做业务转换。 |
| 物理唤醒任务及其租约 | 现有 JobQueue / Procrastinate | 接受领域同事务入队；不把任务 succeeded 当成材料或活动已完成。 |
| Sources / Identity 的来源、范围和权限证明 | Sources / Identity | 沿用当前公开事务内校验和固定锁序；不因恢复放宽。 |
| 告警、覆盖与恢复证据 | Operations / Logs | 读取事实、调用领域窄口并核对结果；不直接更新业务表。 |

保持四种身份各司其职：

1. 业务对象 ID 和原材料版本：决定正在完成谁的工作。
2. 模型 attempt ID：记录一次真实物理计算；合法后继可以有新 attempt，但沿用原 lineage 和预算。
3. 恢复领取 token：临时执行权，过期不能继续提交。
4. 唤醒 job key：一次物理调度身份，不改变业务对象和模型身份。

新唤醒只携带稳定的原对象引用、原 Action 绑定和 data_generation。实际命令、原始输入、外部回执继续保存完整不可混并的原信封。观察时从领域持久记录取得原上下文并做受限刷新，不把观察身份刷新写回原模型请求。

## 4. 各领域采用同样的顺序，各自实现业务决策

这是实现约定，不新增统一的 apply/wait/retry/stop 业务引擎。

1. 原生任务唤醒所属领域；短事务读取当前指针、版本和原请求引用。
2. 事务外查询 Models 或 Actions 的权威结果，不持有业务连接等待网络。
3. 进入领域短事务，沿用 Identity / 完整 Sources 集合 / 领域行 / 恢复账本的现有锁序；重新核对当前 head、取消、来源、代际和材料版本。
4. 将同一次权威观测同步为领域本地投影，并用同一事务连接更新 Runtime 物理尝试记账。观察旧 attempt 可以补历史证据，但不能改变当前已选后继。
5. 领域根据新观测决定：使用原结果、等待、合法纯计算后继、有限输出纠正、本地重解析或明确停止。Runtime 只核验相应预算和领取条件。
6. 等待时同事务保留下次时间和原生唤醒；需要模型时先保存冻结请求和当前选择，提交后按既有 completion 通知续接。
7. 应用前再次检查选中 attempt、当前业务版本、来源和代际；业务写入与其完成证据同事务，或使用既有可查幂等回执。

Models 查询缺失、超时、queued/running 均不授权新尝试。纯计算只有在新鲜权威回执明确证明原尝试已结束为 unknown、仍满足既有重试条件时，才允许原预算内的独立后继；原 unknown 和未知费用保留。QQ 投递、发布和其他未知外部效果只对账原动作。

## 5. 两项公共基础能力，保持窄职责

### 5.1 可靠唤醒

直接复用 JobQueue.enqueue(..., queueing_lock=...)、当前资源行锁、原生任务租约与 RecoveryWait：

- 同一个观察工作使用稳定且可比较的载荷；下次时间不进入业务身份。
- 没有待执行唤醒时分配新物理 job key；已有 todo 时合并到最早合法 due。
- 正在处理时收到变化，允许保留一个后继，不取消 doing 任务。
- 提前运行、合并、无变化和依赖等待等非终态返回路径，仍须保留最早尚未完成的合法唤醒。
- 资源/依赖等待只使用真实 RecoveryWait 或已确认回滚的 DatabaseFailure；不泛化吞 409/503，不把提交未知当作本地可重试。
- 正常续接、启动恢复和 Operations 补唤醒调用同一个领域安排函数；不会再有一套仅运维可用的业务执行器。

不新建全局 work 表，不把所有工作迁到 recompute，不添加另一套 timer 或轮询服务。对原生 retry 与并发 todo 合并的边界，用定向用例确认不丢后继、不出现锁冲突。

### 5.2 明确“修复后恢复”的领取方式

现有计算预算 can_retry 只说明预算与 lineage 条件；一般 due 领取还要求 due 已建立。Growth 手动 resume 当前会安排领域 waiting，而 Runtime 对 OTHER 失败可能仍为 due=NULL；这是静态发现的衔接风险，尚未通过现场请求或回归运行确认。

对这种已知失败，不把错误一律改成 TRANSPORT，也不伪造来源版本：

- 领域先证明原失败已知、材料仍有效、故障已有明确修复，记录修复引用 repair_ref，并决定是否恢复。
- 真实配置/材料版本改变继续使用现有 update_version_on(..., resume_due=True)，沿用原 lineage 和预算。
- 同版本的解析器或程序修复，如现有端口不能合法领取，只补一个 Runtime 窄端口。输入限定 owner、原 lineage、expected_version、原 attempt、权威 failed 回执和领域 repair_ref；它只幂等登记一次修复后领取资格，遵守冷却/探针、原预算和租约。
- 原尝试仍 reserved/unknown、存在未替代的有效计算、已取消/撤回/换代或额度耗尽时，不签发该资格。同一 repair_ref 重入不能重复消费、清零次数或反复推迟 due。
- Runtime 不识别“反思/日记/活动是否完成”，也不提交请求；领域拿到资格后仍走正常处理器。

实现时先冻结这一窄合同并覆盖真实 RecoveryPolicy 调用链；不让各领域直接修改 Runtime 内部表。

## 6. 按领域修复

### 6.1 Memory：让观测、本地投影和恢复记账一致

在现有 consolidation / consolidation_retry 内收敛一个领域内部的观测落库路径：

- 核对原 step、model_attempt_id、冻结摘要、data_generation 和当前选择后，同事务同步本地 status、error_code、recovery_policy_state 与 Runtime 记账。
- choose 将此次新鲜 OriginalOutcome / ModelReceipt 直接传给后继判断，领域 status 仅作投影，不从它反推模型结果；观测落库后复核当前 head。head 或版本变化才重新观察，不继续使用更新前的 attempts 列表决定 original_state。
- 身份或当前 head 已变化时重新观察当前工作；仅对具体可解释的观测竞争延后，不吞所有 recovery_original_not_failed。
- 领域失败、暂时等待、已选后继和物理结果未知分别保留。一次状态对账竞争不能把原 episode 永久标为内容整理失败。
- 迟到旧成功只补历史；当前选中结果最多应用一次，保留现有 assert_attempt_applicable_on 和材料读集 CAS。

同时补正常恢复口：对于因已修复的本地续接错误而 failed 的准确原批，可重新核对最新权威回执、材料版本、提取游标、当前占用和原预算，再进入同一个普通处理器。当前已知目标为 memory_batch_5c7f0abf426d4339a8094b48f274a329，lineage 963e0087076f9abd4d990c46f2554bb91047f752fe90b20a6654c9caa56f4141；实施时重新读回。

## 10. 理论成立条件与进一步收敛

本方案覆盖已发现程序故障的机理，但实现正确、Life 具体冲突和 Growth 原错误归属仍需通过第 9 节的实际时序验证。不能凭设计文字承诺所有现象已经解决。

### 10.1 同时证明正确性和持续推进

正确性要求：

1. 应用业务结果时，原对象、选中 attempt、材料版本、代际及来源授权仍匹配；旧持有人、旧结果不能覆盖新 head。
2. 同一领域定义的业务提交身份最多应用一次；通知和物理计算可以重复。该身份不是通用素材哈希，合法的新时间窗口和新业务意图仍可独立成立。
3. 物理结果、费用未知不会因本地重试或业务恢复而被改为已知；预算和原尝试序号不因重启或恢复入口改变。

持续推进要求：

1. 每个合法可继续的对象，在持久记录中都有可查的当前请求、下一步 due 或等待/终止原因。不能以把全部对象标为终态的方式规避推进要求。
2. 尚未到达终态、且依照当前业务规则和原预算确应继续的工作，通知漏到、过早合并或某次入队遗漏后，仍能从领域记录被重新发现。
3. 一个旧 unknown、错误批次或长期无变化对象不阻止其他材料公平进入；预算耗尽等真实停止条件明确留痕。

推进保证有前提：数据库和所属消费者恢复可用、调度保持公平，材料在足够的处理窗口内保持有效。要承诺最终业务成功，还需依赖在原预算内返回合法结果。依赖一直失败时，合理结果是原预算内明确停止并保留证据，不是无限重试或虚构成功。

### 10.2 事件加速，领域持久状态负责补漏

进一步明确第 5.1 节的补漏归属：Memory、Life、Growth 在自己的后台处理进程内、Conversation 在 bot-foreground 内有界检查本域持久工作，正常事件、启动和短扫描均调用同一领域续接函数。Operations 仅提供额外检查，不是补漏唯一入口。

复用 MemoryWorkers.recover、Life 既有 clock / recover、Growth.recover 中适用的选择和安排逻辑，以及 Conversation 已有结果消费账本。现有 recover 不一定适合直接高频运行：将其中短小、只读到期元数据并补唤醒的部分收敛出来，复用已有进程有界维护周期按 role 挂载；Runtime 只负责调用时机和故障隔离，不判断领域工作应如何转换。

- 只按到期索引、稳定游标和有限批量查询；保留领取租约和公平轮转，避免每次都处理同一组旧对象。
- 扫描只安排原生任务，不在维护周期等待模型、执行外部动作或持跨域大事务。
- 维护触发不能仅依赖“上一次业务处理成功后再安排下一次”，否则异常分支仍可把补漏链一并截断。
- 停用 Operations、漏掉一次结果通知或缺少一次业务后继入队，原领域仍能在自身恢复后发现缺口；数据库/进程本身永久不可用时不承诺进展。
- 检测时间取决于扫描周期、批量、公平游标和积压；没有测量前不承诺固定秒数。

当前 Procrastinate 作业本身是持久化的；这项补强处理的是业务分支从未正确安排后继等逻辑缺口，不把已有队列说成不可靠。

这种各领域独立反复检查当前状态、只做必要转换的方式借鉴控制器对账思路，不引入 Kubernetes 或新的工作流依赖。[控制器设计说明](https://kubernetes.io/docs/concepts/architecture/controller/)强调各控制器分别管理自己的资源。[PostgreSQL NOTIFY 文档](https://www.postgresql.org/docs/current/sql-notify.html)也将通知用作提示读取持久表中变化的信号。

### 10.3 外部未知的不可消除边界

当客户端发出请求后超时，“上游已完成但回包丢失”和“上游尚未执行”可能呈现相同本地现象。缺少上游幂等键或原结果查询能力时，本地不能同时保证任意外部动作既绝不漏做又绝不重复。

因此：

- 本地业务提交可用事务、CAS 和幂等回执约束为最多应用一次；这不等于外部模型只调用一次或只收费一次。
- 已声明并核验支持的上游幂等键、provider_handle 或结果查询应复用原身份；不能仅因本地有请求 ID 就假设上游提供相同保证。
- 无法确认的外部效果保持原动作对账；合格纯计算允许原预算内后继，但原费用未知与可能重复计算如实保留。

这一取舍与 [AWS 关于幂等重试的说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)一致：重试安全需要服务端幂等合同，且去重记录与业务变更须具有原子性。

### 10.4 用现有测试验证不变量

在第 9 节的现有定向夹具中，明确断言提交唯一性、旧 head 隔离、预算不重置和可继续工作仍能被发现。重点注入“回执已读但尚未落库”“观测同步后 head 改变”“业务事务提交后处理器中断”“唤醒被提前合并”“租约到期后旧执行者返回”等中断点。

这提供可检查的证据；不新增形式化平台、独立工作流引擎或全项目测试门禁。若有限时序验证仍显示合同无法成立，再据具体反例调整对应领域边界，不以再造总状态机作为默认下一步。
