## 根因链与设计选择

本次故障由多个边界共同放大：近期生成的来源图达到快速路径深度边界；新增回执使其退回重复遍历；校验发生在持锁事务中，产生资源等待；Life 的直接应用入口继续重试同一结果；资源重试解除队列去重锁后，维护扫描又能安排新观察；结果消费者自己的失败预算耗尽，却没有程序修复后的本地对账合同。

上述各环节有源码或对象级证据，但没有逐条证明所有现场慢 SQL 和失败事件都由同一边界触发。修复应覆盖这些已确认合同，保留对未知成因的准确表述。

选择在现有 Sources、ActionResultEvents、ResultConsumer、JobQueue 和领域对账上演进：

- 每个业务对象自己的结果应用串行，不同对象和角色继续并行；共享的是权威证明和执行机械合同。
- 同一终态回执只有一种领取、应用和记账路径，领域业务代码仍归 Life/Memory 等原所有者。
- 唤醒只是要求重读当前状态，任务成功、被覆盖和业务完成分别记录。
- 来源证明的业务语义不变；移除无环图对递归栈深度的技术依赖，是本批有意的预算模型调整。
- 历史预算不重置。程序修复后的本地对账需要明确且有限的执行资格，所有新旧物理尝试均可追溯。
- 原结果 unknown、费用 unknown 和来源不完整都不从“后来有成功”推断为已知。

本批必交付：来源求值、终态结果入口、可靠唤醒、必要的重复校验收敛、修复后原结果对账。跨事务缓存、来源存储大迁移和统一业务调度器不在本批。

## 1. Sources：消除整图退回昂贵递归的断崖

当前归属：`sources/proofs.py`、`sources/rbf_source_proof_reuse.sql`、`sources/functions.sql`、`sources/service.py`。

现状不是完全没有缓存或批校验：已经有同调用的子图证明复用、分批和函数局部 jit=off。问题是高度超过 64、支持边带范围或其他安全条件不满足时，整个证明可能退回反复遍历共享依赖的旧递归。当前按根引用数切批，也不能限制单个根展开后的边数和实际工作量。

修法：

1. 在现有 Sources 权威内扩展证明求值，对无环图采用迭代的子图求值与显式工作量预算。普通无环图不再依赖递归栈深度 64；节点、边和实际求值次数有界，超预算给出准确可诊断的结果。
2. 保持每组引用的 AND、支持组之间的 OR、disclosure、权限范围、片段撤回和来源版本语义。带范围的引用检查自身范围后复用子图证明，不因一条带范围边使其余共享图重新按路径展开。
3. 对循环、无效范围及异常数值保留明确的短路和错误语义；必要的兼容求值必须有工作量上限，不能把未知或预算不足当成来源有效，也不能简单把所有含环来源判为无效。
4. 改进必须以新的命名迁移生效；迁移注册和共享装配由协调者单写，不修改已发布迁移的历史含义。

求值过程明确为：

- 同一权威快照内读取精确引用及闭包，并在采集时检查节点、边和输入规模，不能仅在巨大 JSON 构造完成后才考虑预算。
- 将来源局部有效性、每条边的 locator 检查、支持组结构分别表达；无环部分按依赖顺序迭代求值，共享子图只计算一次。区分 require_access=true/false，不能只按 source_id 缓存一个布尔值。
- 普通无环图的求值工作量随选中节点、边和引用状态增长，不再随路径组合数增长。深度 65、128 等本身不构成业务无效。
- 循环部分保留路径相关的语义，尤其允许独立有效的替代支持组退出循环。对必须兼容的求值使用显式工作量上限，并复用已证明路径无关的子图；不得因一个复杂分支使整图重新无界递归。
- 返回结果保持 allowed/denied 与预算不足的区别。预算不足不能被映射为来源撤回，也不能无限缩根批次、无变化反复重试；每次调用的所有子批共享一次总工作预算。

优先保留现有数据库内来源权威及 check_groups/check_many_on 公开入口，避免将授权证明搬到新的客户端执行器。新增计数上限由隔离定向用例选定：沿用现有节点保护并明确边数/工作量上限，必须覆盖现场拓扑与增长用例；不在此凭单次快测编造吞吐容量。

仅提高深度、statement_timeout、连接池大小或重试次数不能交付这一项。

## 2. Life/Conversation：收敛同一结果的应用入口

新增确认的内部缺口：

- `conversation/results.py` 通过分消费者 claim、领域回调和同事务完成证明应用 Life 结果。
- `life/worker.py:reconcile_activity` 以及动作返回、承诺对账等路径也会调用 `capability_result`，进而直接执行相同 `_activity_result` / `_commitment_result`。
- `life/rbi_result_fence.py:DirectResultFence` 只提供 Action-head/代际检查，完成回调明确不写 Conversation 消费证明；直接路径也不使用该结果的同一份消费者执行预算。

因此，即使结果消费者因预算耗尽停止，Life 的领域观察/维护仍可能重新尝试同一业务应用；直接应用成功后也不能自动说明消费者账本已经完成。现有领域 CAS 会阻止不少重复提交，但不能免除重复尝试的校验成本，也不使两个入口自动共享预算。这是源码确认的入口和记账缺口，不据此宣称每一次现场重入均已追踪或发生了重复业务提交。

18:38—18:40 原对象只读复核补充了现场关联：这五个 Action 均为 succeeded，五条 delivery 仍 pending；其登记的 20 个 conversation.result job 全部 failed，没有开放的结果消费任务。同五个活动在 18:04:57—18:35:12 巡检区间出现 56 条 failed 事件，属于 56 个不同的 life.activity_reconcile job；另有 256 条 deferred_for_retry 重排事件，不与失败相加。18:38 定点仍有 31 个 todo、2 个 doing 的观察任务。该证据验证了“结果消费停止而同对象观察任务持续调度”的缺口，不证明这 56 次失败均由同一 Sources 深度边界造成。原件为本地 `.runtime/rbi-execution-20261106/monitor-reconcile-events-20261106T1034Z.json`、`monitor-original-objects-20261106T1034Z.json` 和 `monitor-result-jobs-20261106T1034Z.json`。

修法：

2. 复用 ActionResultEvents 和既有结果唤醒实现，给观察者一个窄的公开端口：根据最新持久化 Action head 确保原结果事件与唤醒存在。Life 不拼造事件信封，不直接写 Conversation 内部表，不创建另一套队列。
3. Actions 当前只发布 succeeded/failed/cancelled/unknown 结果事件，不能假设 pending/running 已有消费者。pending/running 的领域控制状态更新、404 后继续观察仍由 Life 持有，不能误当作消费完成。原 Action 续接后的终态回执走上述共同入口。
4. 恢复期限到期后对已消费失败结果作出的继续阅读/跳过等决定，是新的 Life 领域续接，不是再次应用旧回执。沿用原 Action/receipt 引用、当前活动 CAS 和受限唤醒，保留取消/暂停及 commitment 能力；必要时从通用结果处理函数中提取领域续接分支，不能靠重入整个旧结果处理来实现。
5. ResultConsumer 仍调用 Life 的业务回调，Life/Goal/Memory 与消费证明同事务提交；不将业务决定移到 Runtime 或 Operations，也不全局串行化各角色。
6. 先核对已经直接落账的原对象：若准确原回执、业务结果和相关证据已齐备，只对账补齐消费证明；证据不足不冒称完成，也不再次执行外部动作。
7. pending/running 控制更新和结果应用之间发生 `result_head_advanced` 时，保留 fence 的拒绝：先让旧事务回滚，再重读同一 Action。确认属于同代际、同 Action 的真实头部推进后，按新 head 补共同消费者唤醒并明确返回交接状态，不重跑整个 activity_step，不再次 invoke，也不把它直接归为永久业务失败。刷新次数有界，持续竞争则保留准确后继；若消费者已预算耗尽，明确返回对应 blocked 原因，不能虚报已安排恢复。head_regressed、同版本回执冲突、来源失效等仍按其真实错误处理，不吞所有 409。

## 3. Runtime/Life：修复资源重试后的唤醒堆积

18:53 定点只读查询确认：同五个活动有 27 个 todo 的 life.activity_reconcile job，27 个的 queueing_lock 均为 NULL，均匹配当前 Action 和代际，均执行过，原生 attempts 为 1 至 34；另有 3 个 doing，其中 2 个也没有 queueing_lock。证据为本地 `.runtime/rbi-execution-20261106/reconcile-queue-shape-20261106.json`。

对应源码：JobQueue 的 release_if_retry 在资源重试前调用 `_release_retry_queue_lock`，会清空原 doing job 的 queueing_lock；`_coalesce_pending` 只寻找仍有该锁的 todo。解除锁虽避免原生重试和并发后继之间的唯一键冲突，但同时使历史重试脱离合并范围。不能只修 Life 的一次调用而留下这个机械放大条件。

修法限于明确登记、可从持久状态恢复的唤醒任务：

首批明确登记 life.activity_reconcile 与 conversation.result 的相应持久态唤醒合同；resource_recovery=true 本身不等于允许合并所有任务。普通外部命令、已派发模型尝试和投递不自动纳入。

1. 为唤醒保留不可变逻辑身份，绑定 task、data_generation、对象标识和冻结载荷摘要。Life 使用活动与原 Action，结果消费使用原结果身份；due、观察次数、临时 owner token 不进入身份。
2. 逻辑身份保存在现有 Runtime/原生任务元数据中，不能依赖会被清空的 queueing_lock。复用 Procrastinate 原生队列和可用的按对象执行锁，不增加业务 work 队列或第二套计时器。
3. 资源重试、正常入队和维护补唤醒都能认出同一逻辑身份。至多一份有效执行和一份有效待办；保留原生 job_id/attempt 历史，不要求删掉旧任务行。
4. 待办合并保留最早合法 due 和已确认的依赖等待下界；不能每次维护都把未来任务提前为立即执行。当前工作进行中允许保留一个后继，不撤销仍有效的执行者。
5. handler 在昂贵来源证明和网络调用前检查原身份、当前选择和执行资格。已被覆盖的纯唤醒快速退出，记录 covered_by；它的物理任务结束不冒充业务完成。不能把外部命令或未知效果的物理执行当普通唤醒合并。
6. 对既有无锁重试，由领域依据准确原对象/载荷通过 Runtime 窄口归属并正常收敛；不在全库按相似参数猜身份，不直接删除 27 个 job，不取消 doing 中可能有未知效果的工作。
7. 唤醒接管与原生 retry 的实际持久化必须在交错用例中验证，包括断电在解除锁之后、retry 保存之前的情况。若只做到“不再报 AlreadyEnqueued”，仍不能验收。

具体复用方式：enqueue 继续接收原 queueing_lock 逻辑键，在现有 job_keys 元数据持久保存原逻辑键与冻结载荷摘要；原生 queueing_lock 只承担原生待办唯一约束，不再是查找同类工作的唯一来源。按对象执行锁使用 Procrastinate 的 lock，当前 fair_claim_job 已识别这个字段。重试后原生去重锁为空的任务仍可按元数据识别和收敛。元数据缺失的历史任务只能由所属领域按原信封和代际核实后归属，不能由 Runtime 猜业务身份。

这里的“至多一份”指有效逻辑工作；历史物理任务可以存在，但不得同时获得同一对象的执行资格。Runtime 只识别已登记的唤醒身份与覆盖事实，不判断活动、规划或记忆的业务终态。

## 4. Sources/Life：减少持锁后的重复证明

`prepare_event_writes` 会证明输入和原 Goal context；Life 锁住 activity/goal 后再次校验，新增回执后又进行校验，Memory 观察还有相关来源消费。集合重叠时会反复展开图。

修法：

- 先合并同 context、同精确引用的准备工作；不同 context 和 locator 不混合。
- 在同一事务、相应来源与身份锁仍持有、且相关数据未被本事务改写时，复用 Sources 签发的事务内证明；新增来源后补算必要变化。
- 证明明确绑定事务、权限上下文、引用与来源变化。不能按连接对象长期缓存，也不能跨事务复用旧布尔值；新增来源、别名/版本、范围或权限变化使对应证明失效。
- 复用之前必须确认所依赖的全部权威读集都受到保护，包含 disclosure 所涉及的依赖范围 epoch；不能仅因锁住了 viewer 的 scopes 就推断覆盖所有依赖。缺少相应互斥锁时，先补充正确锁序，或采用能够保护到提交的版本/CAS 写屏障；单纯在提交前再读一次 epoch 仍可能竞态，不足以授权缓存复用。无法证明时保留该处新鲜校验。
- 保留既有锁序、Action head fence、领域行 CAS，以及 Life/Goal/Memory/消费证明的原子边界。先优化证明工作，不把未经版本校验的旧快照当作提交依据。
- 不先重写来源存储。生产者复制完整祖先集合的构造另按语义审查，只有证明等价后才收敛；不删除原账本依赖来换速度。

实现取舍：先让无环图的最坏路径有界，并收敛同 context 的重复准备。事务内跨调用证明复用只在读集保护可证明时采用；不能为了省一次约 0.2 秒校验，引入尚未证明正确的权限缓存。没有安全复用条件时，保留新鲜校验并验证总事务时间。

本轮不将整图证明移到写事务外再裸提交。机械领取使用独立短事务，释放领取锁后再进入领域事务；不把新的 Runtime 行锁长时间带入来源和 Goal 锁序。来源、Action、领域行、完成证明继续按既有规定顺序取得。

## 5. Runtime/Conversation：正式支持修复后本地对账

现有 `rbi_execution_budget.py` 将已经确认的 failed 事实保留，`resolve_execution_on` 只解析 started/unknown；`ensure_on` 在四次真实失败后不再安排执行。这一停止行为有效，但缺少程序修好后完成原本地消费的正式路径。

修法：

1. 保留现有结果身份 `(generation, action_id, receipt_id, result_revision)` 及其消费者进度键、原事件、原执行事实和普通失败预算；不把 consumer 塞入新身份以绕过现有共享预算。修复资格再明确限定本次允许处理的 consumer。先读当前真实证据，再决定需要补证明还是执行未完成的本地事务。
2. 对确由已修复本地缺陷造成、失败历史完整且不存在进行中或提交未知执行的对象，登记一次明确的修复执行资格。绑定已生效修复版本、缺陷引用、原事件摘要、目标消费者与原失败历史摘要。
3. 首次修复批对每个准确目标消费者最多授予一次本地修复执行资格，沿用原结果身份并链接原历史。普通预算保持耗尽；repair 执行和普通执行在账本中可区分，总执行与失败次数完整可查。仅凭不同 SHA 或随机 repair_ref 不能反复签发；必须引用已登记、生效且覆盖该缺陷的修复，同一缺陷修复重入返回同一资格。任务参数不能自行授予资格。
4. 资格消费、原生任务安排、执行领取和完成证明使用现有队列与 Runtime 机械端口。没有资格时不能只换 job key、新建业务身份或伪造版本绕过预算；不能把旧 failed 改成 wait 来获得额度。
5. 只允许消费已存在且确认的原回执，不派发模型、不调用外部 Action；QQ 或其他外部效果未知时仅核对原效果。来源失效、代际改变、头部推进时按原领域终态处理。
6. `candidates`、`inspect`、`invoke`、`verify` 对普通预算耗尽和修复资格给出一致结果。目前候选/inspect 未充分表达预算限制，不能再将“候选可查看”混为“可以执行”。

本方案明确新增的是本地修复资格合同，并非声称当前已有可用接口。沿用现有 execution facts/binding，新增机械修复绑定；不新建平行业务身份。登记修复、领取资格和 begin_execution_on 使用同一冻结合同，不能由部署脚本直接更新内部表代替。

登记和领取由已授权的协调/运维发布恢复流程自动完成，不新增用户确认弹窗或逐条审批。域负责证明目标确实属于该已修复缺陷，Runtime 只核对可信修复登记和机械资格；不能靠传入一个 repair_ref 字符串自我授权。

修复执行期间，已确认回滚的池/锁等待维持同一资格并退避，不签发第二份资格；明确的本地执行失败消耗该次资格。若提交结果未知，停止再次 apply，先用同一消费者 proof 和业务读集对账：有证明则完成，无证明但尚不能确认回滚则保持 unknown，确认未提交后才按该资格的既定状态处理。不能把所有 57014 QueryCanceled 一律改成免费等待；需区分服务器语句限时、主动取消、维护超时和提交阶段。

修复入口有两个阶段：先只读核实是否已经提交，必要时在短事务中补齐可证明的消费状态；只有确实还没有应用且资格有效时，才运行原领域回调。不能仅凭 activity.state=completed 推断 Goal、Memory 和原回执均已提交。

## 6. 增长治理与两项次级疑点

### 来源图的持续增长

本批首先保证现有图及新增回执可处理，同时检查 Life 回执构造处把全量继承来源同时当直接支持的行为。把真实直接依赖与完整追溯集合区分，能够证明等价的场景通过精确父来源保留追溯，避免每轮复制全部祖先。

仓库已有 EvidenceSpec / EvidenceSetRef / register_evidence_on，可以表达 required、alternative_supports 和 generation_dependencies，但当前支持边仍是 SourceRef，不能声称接入一个 evidence_id 就自动压缩既有图。优先复用这些合同；若确实需要存储扩展，单独限定生产者和新数据路径，不把大规模旧图迁移作为五条结果恢复前提。

任何收敛都要证明撤回传播、disclosure、范围和来源版本等价；不能做通用“删传递边”，也不能用 EvidenceSetRef 代替实时授权证明。旧图保持可读、可诊断、可追溯。

### Growth 谱系重载

现场曾有 `growth_recovery_lineage_missing`；关联批后来完成且 outcome 为 historical_only，不能把它列为当前仍卡死的批次。

静态发现 `growth.py:current_material` 的“同 material_key 已有 active_batch”分支只返回 true，不将持久化 batch 的 lineage/recovery_version 等同步回本次调用的局部 batch。后续成功或失败记账却使用该局部 batch。并发读到无批次、准备时另一个执行者已提交同批次时，存在可达的缺字段风险。

先用两个原生执行者交错准备同一 material 的定向用例确认；若复现，在 Growth 原事务内取回并校验权威批次，采用其冻结请求/谱系继续观察。不得补造新谱系、重复 reserve 或吞掉 lineage_missing；若版本或当前选择变化，退出并观察新的当前工作。不改模型路由。

### Memory 索引恢复覆盖

索引恢复已有 `record_attempt_on` 和 `backfill`，不能再建一套统计系统。backfill 挂在 index_jobs.recover 后部，该扫描失败会阻止本轮到达统计补齐；当前轻维护主要处理 consolidation，不足以证明索引投影持续覆盖。

根据现场 producer 水位及实际索引对象做定向确认，再决定是否将现有有界 backfill 接入 Memory 自身维护并独立隔离失败。补齐前保持 partial/unknown，不用进程 ready 或某两个索引对象有向量替代全覆盖证明。这项不阻塞前四项修复和五条原消费者的恢复。

## 7. 公共接口、状态与所有权

| 边界 | 复用/扩展位置 | 关键约束 |
|---|---|---|
| 来源证明 | Sources.check_many_on / validate_persistence / prepare_event_writes 及新命名 SQL 迁移 | 保留数组/分组含义；预算不足单独返回错误，不假装 false；事务内证明绑定完整权威读集。 |
| 原终态结果补唤醒 | Actions 的窄公开端口，复用 ActionResultEvents | 从持久化 head 构造原信封，校验 generation/receipt/revision；Life 不拼造事件或写 Conversation 表。 |
| 可靠唤醒 | JobQueue.enqueue 的现有 queueing_lock 合同与资源 retry 适配 | 不可变逻辑身份不能随原生去重锁丢失；只对登记的持久态唤醒合并；身份不包含 due。 |
| 原结果修复 | ResultRecovery.recover_result / inspect / verify 扩展修复引用 | 只处理原目标；当前 head/来源/CAS 变化则按真实终态退出；不能重新派发外部动作。 |
| 修复执行资格 | Runtime 执行事实和领取窄口 | 原普通预算不改；修复版本与缺陷登记可信；一次资格幂等，任务参数不能授权自己。 |

必须分别表达以下事实，不用一个 succeeded 覆盖全部：

| 现场状态 | 应有处理 |
|---|---|
| Action pending/running，尚无终态事件 | Life 维护控制状态和观察 due；不登记终态业务完成。 |
| Action 终态回执存在、消费者未完成 | 唤醒共同消费者；观察者不直接再次 apply。 |
| pending/running 控制快照在写入前已被新终态推进 | 旧事务回滚，按权威新 head 交接；不重跑外部 invoke，不把正常推进误判为永久步骤失败。 |
| 原结果 execution/effect 为 unknown | 保留 unknown；消费者可以记录“已观察未知”，不表示外部效果已确认。 |
| 普通消费预算耗尽 | 保持 blocked 原因，停止旁路重试；登记有效修复后才允许受限本地对账。 |
| 业务与消费 proof 已原子提交，但任务应答丢失 | 读原证明收口，不重复 apply。 |
| 回执头已更新、来源撤回、对象取消或换代 | 核对真实终态，按 superseded/invalidated 等处理；不为了恢复旧记录强行应用。 |
| 已消费失败回执之后恢复期限到期 | Life 作新的领域续接决定，用当前 CAS；不再消费同一旧事件。 |

## 9. 必要验收

1. 先冻结 Sources 证明语义、观察/结果应用端口和本地修复资格三个边界；已有备用路由不动。
2. Sources 求值修复与 Life/Conversation 入口收敛分别实现；事务内证明复用在同一接口上组合。公共入口、迁移注册、配置和最终集成保持协调者单写。
3. Runtime 可靠唤醒/本地修复资格与 Conversation 原消费者对账共同实现，随后串行集成必要装配。Growth/索引疑点先复现再列入实际改动，避免泛化本批范围。
4. 定向验证使用真实 PostgreSQL、真实 Sources 和真实结果消费者，按现场拓扑生成无业务正文夹具，覆盖 64→65→更深的稠密图、新回执在同事务可见、权限/片段撤回/OR 短路，以及观察和消费同时唤醒时只应用一次。
5. 覆盖四次失败后无普通重试、一次修复资格重入不增发、提交回执丢失先读证明、终态或头部变化不重放。复用未变有效结果，不重新跑全部 472 用例。
6. 发布后按新版本重新读取五个原目标并执行正常领域对账；名单见下。每个对象都核实领域结果、相关 Memory/Goal 记录和消费者 proof。若存在合法终态变更，以准确终态和证据收口，不强行应用旧结果。
7. 最后用自然巡检确认新增结果也完成消费，且不再由 Life 观察旁路持续应用同一已停消费者。仅一次 SQL 变快、容器就绪或任务 succeeded 都不是业务完成。

补充本批明确回归范围：

- 来源使用现场规模的无正文拓扑夹具，验证普通无环、带范围、权限 epoch 改变、片段撤回、替代组短路、循环有退出/无退出、缺来源、节点/边/工作量预算。Source 公共读取与 Memory 撤回/本地检索调用也有定向覆盖，不能只测 Life 的 Sources stub。
- 旧用例中将 66 节点退回旧递归或将技术深度限额视为预期的部分，按本次明确的预算合同修改；权限、撤回、范围和短路语义的既有断言继续保留。不能以删除这些断言换取深图通过。
- 观察/通知/维护同时到达；原 job 资源延期时已有后继；锁解除后进程退出；旧 context/载荷；新 Action 替换、generation 改变；当前 doing 不被错误取消；旧无锁纯唤醒被覆盖后廉价退出且不丢最早合法 due。
- 对新回执、Goal、Memory 与消费者 proof 注入失败，证明全部回滚；丢失提交确认时只读对账，证明业务最多应用一次。
- 在 activity_step 得到 pending/running 快照后、fence 前使原 Action 变为新终态：旧写回滚，新版本被准确交接并最终取得消费 proof；原 Action 不被再次 invoke。再分别验证同版本冲突、头部回退、来源变化没有被这个分支误吞。
- 性能目标以隔离 PostgreSQL 上现场规模的新回执场景单次校验保持亚秒级为起点；实际记录取图、求值、持锁与并发等待时间。该目标尚未验证，不用原图一次 0.232 秒推算倍数收益。
- 新增最少量现有日志字段：证明节点/边数、快路径或兼容路径原因、工作预算、语句取消原因、逻辑唤醒/覆盖关系、修复执行与原身份。sql_errors=0 不能再被解读成没有查询取消。不记录模型正文、凭据或来源内容。
