## NR-04：按用户更正分离排队与执行时钟

17:31 发布 `6ea07c98` 后，自拍检查已通过真实 Go 调用返回 7 项可见场景判断，并识别旧图“预期台灯关闭、实际亮灯”的冲突；原请求和原图片未改写。记忆原分区 pending 已降到 0，历史未知 12 条及另一分区 2 条继续隔离。智乃旧 fenced JSON 原结果已经成功应用，没有重发原尝试。

原任务复核进一步定位两个具体故障，纳入同批收口：

- 显式继续活动时，新 Action 采用合法的当前执行上下文，但 Activity 仍保存旧上下文。重启后少了一项原动作范围，Actions.get 正确拒绝访问。修复在冻结 Action 的同一事务保存确切执行上下文；想象活动的完成计时器同样保存。旧任务仅由协调者使用原冻结 Action 的已授权上下文排一次既有 reconcile，不扩观察者权限或添加兼容接口。
- Growth 后续模型请求在供应商配额暂满时，因独立的 30 秒排队上限被取消，实际 dispatch=not_started；RPC 异常也可绕开领域可见状态。RPC 修复确认原冻结请求后只读原 ledger，成功继续完整校验，已知终态/等待/未知分别保存，不重发未知。

用户明确要求排队不消耗模型执行时间，否定单纯延长等待作为修复。已撤回临时将 Go 等待上限改为 180 秒的配置，也撤回 Growth 自设 120 秒的局部方案。统一合同如下：

1. `ModelRequest.execution_timeout_seconds` 冻结供应商执行时长；`business_deadline_at` 仅表示实际日程、主动消息、操作窗口等业务到期时间。普通后台整理没有虚构的业务截止。
2. 模型配额和准备槽等待不消耗供应商执行时长。Broker 获得执行名额后，才建立执行截止 `min(开始时间 + 执行时长, 业务截止)`，并在原 ledger 记录实际时间。Client 的 HTTP/stream 不在排队期间按执行时长提前取消。
3. `max_queue_wait` 和作者配额的 `max_wait_seconds` 可为空，普通新请求默认没有短排队 TTL；队列容量、用户取消、交互保留槽和供应商实际并发限制保持。明确配置的排队过期可独立生效，不能吞掉执行时长。
4. 原冻结请求和未知尝试保持原 ID、内容、时间语义；只读原结果、来源重检、CAS 与隔离规则保留，不通过延寿或重新创建尝试掩盖未知。`RequestBudget` 本身仍是绝对预算，不改变其他业务通用语义。
