# 并行开发流程与工作区

日期：2026-09-14。用户已授权启动并行准备，先规划开发流程。本轮完成目录、源码副本、任务图与协作规则，不启动生产服务，也不开始大规模业务编码。

## 1. 项目集中，产品边界保留

根目录是协调 Git，不是把所有产品改成一个软件。推荐并已用于本轮准备的结构：

```text
tianshu-peiban-bot/
  docs/                       产品、架构、开发计划、当前交接
  contracts/                  跨产品公共合同的唯一发布入口
  projects/
    tianshu-platform/         平台 API、网页、小屋渲染、连接器
    tianshu-companion/        陪伴核心、生活状态、NoneBot 薄桥
    tianshu-memory/           人物、记忆、资料库、检索任务
    tianshu-model-gateway/    原生模型协议、请求、线路、用量
    assetlibrary/            现有资产项目的独立集成检出
    chat-audit-core/          现有原文归档项目的独立集成检出
  references/                 旧平台/记忆/网关和插件源码快照
    overlays/                 旧检出的未提交变更包
  worktrees/<任务编号>/      每个并行任务独立工作目录
  output/                     已有设计图与本地验证产物
  scripts/                    工作区准备、状态和一致性检查
```

四个 V2 项目从轻量开发骨架开始，旧项目仅按能力复用，不继承不需要的复杂结构。AssetLibrary 与 Chat Audit 保留已有实现和历史；NoneBot 是独立运行入口但源码放在陪伴项目，小屋是平台网页模块，不另外变成业务服务。

HA、ComfyUI 的运行环境/模型、GsCore、RSSHub、Komga、NapCat、游戏服仍是外部软件。需要的自研插件和客户端代码作为参考检出放在本目录，不复制 NAS 资源、数据库、容器卷或生图权重。具体 reader、独立移动客户端等尚未定位来源的项目仅登记待定位，不伪造空仓库代表已取得源码。

现有开发目录仍保留。复制以明确提交为基线，工作树差异与未跟踪源文件作为覆盖包保存，不自动套用到 V2；忽略文件不复制。这样新工作区可以研究现有最新修改，而不会干扰别处正在进行的工作。导入版本与差异见 `workspace.json`、本地 `references/source-inventory.json`。

## 2. 并行之前先补齐接口缺口

I01–I18 是能力目录，不能直接当已冻结 OpenAPI。首批合同由 TS-001 负责，至少明确：群内分人收集键与整个会话两轮调度键的差别；活跃槽位释放条件；网页回复下行；身份解析与验证关联的区别；初次记忆写入；模型网关如何读配置与凭据引用。

每个合同的生产者和消费者都要确认语义与夹具；未冻结条目可以做模块内部实验，但不能各自发明对外协议再到最后拼接。变更只找一个协调人裁决，普通实现不逐步请求用户审批。取舍和未决点集中在合同任务，避免复制进每份项目文档。

## 3. 第一批与后续批次

默认协调者 + 3 个工作者，不把全部项目同时启动为写任务。任务依赖与状态以 [tasks.json](tasks.json) 为准。下面的“可并行”仍要求每任务独立检出。

| 批次 | 工作内容 | 门槛 |
| --- | --- | --- |
| 本轮准备 | TS-000 工作区与流程，三条规划线并行审查 | 来源与目录检查、工具测试、计划引用可用 |
| 首批 | TS-001 契约；TS-010 平台脚手架与设计令牌；TS-040 模型协议/旧代码复用验证 | 都从本轮提交开始，各自写入范围独立；先不连生产账户 |
| 第二批 | TS-020 陪伴基础、TS-030 记忆基础；平台内 TS-011 小屋样片或 TS-012 连接器基础 | TS-001 的首批契约完成；平台内部先由 TS-010 建立入口与依赖，避免三人同时造 package.json |
| 本地贯通 | TS-050：真实本地核心/记忆/网关/接入代码，用确定性模型与渠道替身 | 验证防抖、两轮、最小召回、重启与回执，不宣称真实 QQ 或上游已通过 |
| 测试账户贯通 | TS-051：测试 QQ/TG、实际模型、归档证据 | 本地联合检查通过；具体测试账号和线路已配置且授权，不接管当前生产 BOT |
| 生活与功能扩展 | 多角色生活/日记/自拍；HA；AssetLibrary 归档；项目接续 | 每条能力按对应真实状态闭环，客户端媒体功能不阻塞网页与陪伴 |

TS-040 先核对原生协议和旧网关复用，真实对外接入实现必须消费 TS-001 发布的配置/请求边界；不能以“可开始调研”冒充“不受契约依赖”。TS-020/030 的详细里程碑 C1–C4、M1–M3、CM1/CM2 见 [陪伴与记忆](workstreams/companion-memory.md)；平台 P0–P3 等细分见 [平台与界面](workstreams/platform-ui.md)。这些是分线编号，不再复制成另一套冲突的总任务状态。

## 4. 同仓库也不能共用正在写的目录

`projects/` 是协调检出，工作者在 `worktrees/TS-xxx/<项目>/` 写代码。根 `contracts/` 任务也有独立根仓库 worktree，其产品、参考和视觉路径通过主工作区位置解析，不能在根 worktree 再复制一整套项目。

跨项目依赖绑定明确合同版本与基线提交，禁止从另一个编码体正在变化的工作目录导入代码。开发端口、数据库、临时目录、浏览器缓存与测试账户在任务开始时登记在不入库的本机运行配置，先检查冲突再分配；本轮不占端口、不创建业务数据库。

平台中 UI、小屋、连接器可以并行，但路由根入口、依赖锁、设计令牌、迁移主线、公共客户端只有一名集成人写入。其他工作者先给自己的模块导出和最小集成说明；集成人集中挂载。不要靠要求大家“编辑时小心点”代替隔离目录。

## 5. 日常开发闭环

1. 协调者选择依赖已满足的任务，核对目标、基线、允许改动范围和验收证据。
2. `workspace.py start` 创建独立分支/worktree，记录占用；默认从当前协调检出的明确 HEAD 开始，不包含其他未提交修改。
3. 工作者读短交接、所需合同和局部实现；首个脚手架任务核定真实安装/检查命令及工具版本。
4. 实现一个完整行为，再审查 diff、做有意义的验证。单元替身、服务联合、真实外部接入分别标记，不互相冒充。
5. 工作者交付本地提交或可审查 diff、短交接、实际测试结果与未完成项。根任务仍是待集成，工作者不能自行宣称整个阶段完成。
6. 协调者在协调检出串行审查/合并，按消费者依赖做集成；所有必需检查与可观察行为满足才标 done。失败回到同一任务修正，不另建无归属副本。

分支、工作目录和本机租用记录在 `.runtime/workspace-leases.json`；它不是自动互斥锁，跨工具需遵循同一入口，不能防止绕过流程的手工操作。任务完成后的清理先确认已合并、无未提交内容；本轮工具不提供递归删除或自动推送。

## 6. 文档与 token 控制

当前事实只放一份 `CURRENT.md`，目标是几百字加引用；完整设计不逐轮重写。任务交接目标不超过约 40 行，必要长日志单独保存文件引用。已结束交接归档，恢复时按需读，不能每次把整个项目历史塞回模型。

项目经验记触发条件、原因、修正和验证；有跨项目重复证据才晋升总错题本。早期先用版本化 Markdown/JSON，不为了省 token 提前实现一个知识管理框架；未来天枢项目页与记忆接入可读取这些短记录。

## 7. 验证命令与完成定义

本轮真实入口是 `python scripts/workspace.py check`、`python scripts/workspace.py status` 与 `python -m unittest discover -s tests/workspace -v`。这些只检查工作区、任务依赖、源码副本和隔离规则。

新四项目没有可运行应用，安装/格式/类型/单元/集成命令由首个任务从实际 manifest 建立。已有项目保留真实命令来源：AssetLibrary 的 AGENTS/CI 分层文件；Chat Audit 的 pyproject 和现有 CI；旧代码的历史测试记录不等于新工程已通过。

实际功能完成必须同时具备：有具体用户行为、代码/契约可追溯、故障边界明确、必要验证通过、消费者可集成、未完成项如实记录。静态视觉不等于完整页面，模型替身不等于真实模型，源仓库检出成功不等于其应用构建成功。

## 8. 本轮交付边界

所有能够明确定位的自研项目和直接复用代码都集中登记/检出到本目录；参考源码、当前产品骨架和现有集成项目区别清楚。工作区初始化可产生本地协调提交，未推送远端。开发流程规划完成后，下一步是首批任务按就绪状态进入实现，而不是默认启动所有服务或同时重写所有项目。
