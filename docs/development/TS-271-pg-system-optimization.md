# TS-271：PG 数据流调研与系统优化

用户要求继续上网研究 PG 运行原理及类似数据流的优化方案，再系统优化。沿已有共享存储与原生业务流程实现；保留权限、来源、完整组、撤回、CAS、独立 guard 和持久性，SQLite 性能不能下降。本聊天已有并行和 gpt-6.1-sol/max 授权继续适用，不创建新聊天。

基线是根 ffbffe05、共享 0.1.3/019b954、Memory 完整 e5e1b39（运行 4447bb4）。本卡只拥有独立 workspace 检出的 packages/tianshu-storage、tests/storage、既有 scripts/benchmarks/pg-read-performance 的新增诊断及本号文档。TS267 仍拥有 Memory 业务实现，本卡不写 Memory，不混入 Q18 合同或行为。源历史和工作目录都必须明确，不恢复已完成卡。

先用 PG17、固定 psycopg3.3.6 官方资料和原作者工程案例解释端到端成本，再采用有证据的改动。重点确认每次连接的会话设置和新鲜绑定读取能否沿协议顺序批发：业务连接只能在全部设置/读取确认并核对身份后交出；绑定按目标 schema 限定，参数和标识符分别绑定。第一候选在同pool配对中变慢后，允许仅两个完全限定的内部checkout模板沿原驱动阈值复用计划，业务SQL仍prepare=False；这不复用任何绑定行或来源/权限判定。失败归属、清理/回池、缺表/缺绑定、只读与跨 schema 复借必须验证。初始化检查不被强行搬入业务管线。

不移动 Store 锁后元数据读取，不扩大 setup-only pipeline 或 read_batch 的业务合同，不在缓存中存放权限/来源判定，不跳过六次 fresh revision，不改事务隔离或提交持久性，不盲增连接数、去掉约束/索引或照搬批量导入参数。不新增平行队列/存储框架。SQLite 分支保持原实现，新的通用能力只有实际调用和相应验证后才采用。

协调者独占凭据、NAS、隔离库、镜像/资源生命周期和根记录；调研子代理只读，后续共享实现子代理只写本卡 runtime/tests/接口说明，版本/固定 wheel 由协调者冻结。网络只采用主要来源，结论区分已实施、实测支持及待后续证据的假设。

复用 TS265 的公开合成夹具与原生 API：同 NAS/SSD、同基础镜像/依赖闭包、每次一个有界客户端，三轮交替 PG/SQ 基线与候选。短 field、关键词、来源同步、撤回、写入和零预算保留；SQLite 增加相同物理初态、交替先后的真实写入控制。诊断与正式采样分开，不能拿带 profiler 的时间计算提速；完整 wall/CPU、SQL 等待、校验/guard/commit 分布和未达标/异常保留。每次实际写和重开验证，不能以回滚或幂等命中替代提交。

使用新 UUID 测试库/低权限角色/合成目录，客户端不挂生产业务或媒体，不访问 Redis、真实模型、QQ。前后检查生产足迹并清理所有本批资源。只本地集成，不推送、部署、迁移或改线上 PG 参数。交付本号研究、实测样本、准确版本和 handoff；其余原根修改全部保留。
