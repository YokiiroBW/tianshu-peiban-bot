# 来源文档校验与短召回：采用边界

本批从 Memory 冻结完整历史 `4dbb8163524af55822d492cfdfda740090b569e9` 继续，共享存储仍为 `0.1.3 / 019b954`。此前连接层 `0.1.4` 候选的反证见 [TS271](pg-system-performance-2026-10-21.research.md)，本号没有恢复它。生产、媒体、Redis、模型及 QQ 均不参与本批业务流。

## 复用现有校验器，准备规则而非记住判定

此前 profiler 显示来源召回的大部分客户端 CPU 落在完整合同校验；本项目原有 Contracts 已缓存顶层 validator 和静态引用解析，继续加一层相同缓存不会解决逐层准备成本。这里沿既有 `_prepare_validation`，使用 jsonschema 公开的 `extend`、`validator_for` 和构造器，为同方言、解析上下文唯一、整棵没有引用的静态字典子树复用官方 validator。每次仍对当前输入重新执行官方校验，保留原有分支短路、首错停止和错误顺序；错误、format 结果、来源、授权和 owner head 判定从不缓存。[公开扩展 API](https://python-jsonschema.readthedocs.io/en/stable/creating/)、[验证协议](https://python-jsonschema.readthedocs.io/en/stable/validate/)

不能把任意子树拿出原解析上下文：存在引用、动态关键字、未知方言、歧义 base、外链及布尔 schema 时保持官方路径。registry 身份替换会清掉全部准备对象。专项对照完整错误顺序、路径、schema/instance 身份、context/parent、format cause、registry 替换和并发输入，防止只验证合法文档而漏掉错误语义。

最初 `5b50579` 对全部文档启用准备。虽然纯校验更快，SQLite 普通真实提交的 120 对配对中位仍约 15% 不利，区间较宽；这既不证明因果，也不能当作没有退步。因此未采用该版，保留其 15 次 / 2660 个正式采样和所有配对反证。

返修 `226d9c8` 仅在实际来源模块 `sync-sources`、`sync-batch` 惰性建立来源类和子树缓存；普通 Memory、profile 和含候选写入的 `sync-workflow` 使用原 `static_ref` / 官方 `properties` / `items`。两条路径的顶层缓存分开，同 URI 经普通 alias 也不会串入来源缓存。其 124 项专项通过；正式业务、240 对写入及 3300 对读取全部保留。普通冷态纯校验仍存在不利波动，不能用热态微测代替 SQLite 写入证据。

最终 `eb65763` 再消除普通准备路径上不必要的来源函数/LRU 分配：六个来源 helper、两个子缓存及官方 properties/items 取值进入同一个惰性来源工厂。walk 结束后只捕获解析上下文唯一的节点 ID `frozenset`，等价于原 `len(contexts.get(id(node), ())) == 1`，不长期持有完整字典及每节点集合。原普通回调、`Contracts.validate` 和模块选择 AST 与 226 相同；registry/roots 保持节点生命周期，歧义仍回到官方路径。专项 124 通过，独立只读增量复核未发现 blocker。唯一固定纯校验探针保留所有 block，普通冷 wall -0.74% / CPU +1.79%、普通热 wall -0.14% / CPU 持平，来源完整8次校验组 wall -5.66% / CPU -6.54%；不能直接用跨阶段差值证明分配是旧回退的因果，也不据此宣布 SQLite 不下降。

本号没有改来源网络调用、六次 fresh revision、锁后独立 SELECT 的新快照、当前授权和撤源检查、CAS、guard 或持久性设置。新的同库来源诊断只切换 `Contracts.validate`，每次核对实际 3 次 owner 调用、6 次 fresh revision、8 份完整文档验证、内容和状态不变；owner 为隔离合成实现，这个计数不是生产网络请求。校验 CPU 是进程 CPU 的子集，不能相加；该诊断单列，不能混入无 hook 的正式延迟样本。

## PG 短查询的有界消融没有通过采用条件

原 `exact_groups` 按 scope/state/category/exact 键筛选候选；512 只控制 lineage 的集中读取和超量后的完整回退，没有候选 LIMIT。先 lineage 准入后正文的顺序保持。研究过取消 lineage 物化、用 `count(*) OVER ()` 给候选携带总数，以及两者组合。[PG17 CTE 物化规则](https://www.postgresql.org/docs/17/queries-with.html)、[窗口函数语义](https://www.postgresql.org/docs/17/tutorial-window.html)

窗口计数必须发生在 lineage join 前，防止多来源放大计数。无分区和排序时各候选总数相同，标量子查询的 `LIMIT 1` 只取这个总数，不截断候选；空集时该标量为 NULL，最终仍返回空集。最初直接在行上写 `WHERE exact_count<=cap` 的计划仍扫描一条 lineage，故未采用；改为标量 gate 后，人工超量 probe 的 lineage/source `Actual Loops=0`。这只是该计划和该输入的观察，不是所有计划的通用保证。

在有 PG 原生写入历史的 365 组隔离夹具上，保留全部 150 轮逐 index 配对。wall 比为候选除旧版，低于 1 才更快：

| 形态 | wall 配对中位比 | 三个 50 轮 block | CPU 配对中位比 | 更快轮数 |
| --- | ---: | --- | ---: | ---: |
| 仅 lineage inline | 1.0600 | 1.0406 / 1.0681 / 1.0708 | 1.0068 | 45/150 |
| window + lineage 物化 | 0.9800 | 0.9913 / 0.9781 / 0.9756 | 1.0033 | 87/150 |
| window + lineage inline | 1.0439 | 1.0491 / 1.0569 / 1.0190 | 1.0074 | 55/150 |

最好形态仅约 19µs SQL wall 改善，CPU 没有同步改善，初始总体 p50 的表观优势也未在配对消融中稳定重复。它没有减少基础候选扫描次数，不能据此声称端到端短召回更快。本批停止这一方向，`recall_index` 和 SQL 完全保持。probe 的选定类别为 165 个候选，人工 cap32 的超量情形不能替代真实 513 组边界；后者仍由既有原生专项验证。

## 以冻结版本的业务证据决定采用

226 版独立使用正式轮次 61/62/63：PG / SQLite、旧 / 新共 36 次，5280 个采样，完整封存，不改标成最终版。最终 eb 版用独立轮次 81/82/83，针对短召回和来源校验共 24 次 / 4560 个采样；普通 Memory 从空库经原生业务写入到 365 组后读取，来源同步正式套件则原生写入 300 组（原始 `seed_groups=300`），不用导入快照冒充原生写入历史。两套均核对读取、来源同步、撤回、零预算及普通写入的实际结果。前版 12 次 / 720 个来源变化写入样本单列；最终分配修订不重复相同 SQL 写流的完整12轮，另以原生PG130专项和SQLite240对真实提交验证，不能把226的来源写延迟当最终eb的结果。

最终版 SQLite 再从四个封存 300 组模板逐对复制完全相同物理初态，执行独立 240 对 / 480 次真实提交并关闭重开，保留 WAL/FULL、guard、ledger、增长和内容验证；24 对预热单列。读取再用同一未变文件做独立 3300 对逐操作交替。来源 CPU 诊断使用独立封存的 300 组写夹具，PG 为导入历史，并非正式来源套件的同一物理初态；因正式 SQLite 来源关键词出现 +2.35% 耗时，新增关键词配对验证，每后端三个场景各60对、共180对/360个诊断样本，9对预热单列。前版两场景120对独立保留；不把诊断绝对延迟混入无 hook 正式业务。

NAS 外部安全维护期间发生首次保护停机；24轮正式测量在恢复后完成，每客户端前后生命周期检查均通过。随后另一次证书重载中断写控制 block21，已完成32对正式/8对预热样本原样保留，不能混入最终240对。再次恢复并核验后，以独立 block31/32/33 补齐控制；没有为保持旧观测而恢复外部维护修改，也不宣称整个批次生产镜像和生命周期完全未变。

报告须保留全部样本、尾延迟、原失败、非采用候选和 NAS 后台负载。顺序轮次的上浮不能直接归因代码，配对区间跨 1 也不能单凭这一点宣称无退步。最终采用及未达到的场景以 [实测报告](validation-recall-performance-2026-10-22.md) 为准。所有生产就绪和配置证明只覆盖实际采集字段，不以合成测试代替生产验收。

## 普通写入反证与定位约束

最终240对真实写入中，普通提交60对的逐对耗时比中位数为+8.03%，95%配对重采样区间为[1.0110,1.1322]，客户端CPU为+3.58%；三个block的wall中位差异方向一致。来源完整流程虽然约快3.69%，也不能抵消普通提交的退步。3300对短读接近持平以及两后端来源校验CPU收益，都不是采用普通写入退步版本的理由。

静态调用链确认，写控制stream仅构造一次Contracts，四个case交错复用，来源已经预热；普通提交只走common/identity-memory合同，不经过来源callbacks。唯一一次无计时CPython3.12对象结构观察发现，来源工厂预热后保留1080个唯一上下文ID的frozenset、614个既有schema引用的子树映射，以及本次输入用到的48个子validator；普通校验前后来源缓存大小没有增长。这些映射没有复制614份schema，也不保留输入或授权判定。对象被GC跟踪只说明存在可见保留关系，长期对象会晋升，不能据此推断每次回收扫描它们，更不能直接解释+8.03%的耗时。[CPython3.12 GC接口与跟踪规则](https://docs.python.org/3.12/library/gc.html)

因此定位只追加一个独立、带观察hook的真实写入block，复用同初态/持久性/重开协议，将validate CPU、其外CPU和GC观察分开记录；不强制回收、不调阈值、不禁用GC。校验和GC CPU都包含在进程CPU内且可能重叠，不能相加。带hook样本不混入240对无hook结果，也不能用诊断较快或单次区间跨1覆盖已有反证；缺乏因果证据时停止微调，保留候选供研究而不进入产品运行树。

该block共80对真实提交（另8对预热），普通提交20对的wall差中位+3.325ms、进程CPU差-0.128ms、校验CPU差-0.0168ms，双方均没有观察到GC；普通完整流程逐对CPU差中位约+1.80ms，校验只约+0.020ms。这些是逐对新减旧差值的中位数，与各侧p50相减不同，方向也可能不同。来源两类写入的校验CPU仍有改善。这个诊断不支持将普通wall差归因校验缓存或GC，也未完成等待/文件系统归因；不能以新诊断CPU持平消除240对普通写入不利。最终eb候选不采用，PG短field仍慢于SQLite的目标亦如实保留；没有把没有证据的缓存/GC调整继续装进产品。
