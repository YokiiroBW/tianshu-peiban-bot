# PostgreSQL 运行链路研究与优化候选实测（2026-10-21，TS271）

本批完成主要来源调研、分层诊断与隔离优化试验。连接层候选没有通过性能验收：正式短field耗时增加约41%，同池对照的少量wall收益伴随CPU增加；顺序模板也没有稳定业务收益。SQLite候选配对的普通提交和来源同步提交亦出现变慢证据。因此不合入0.1.4原型，本地共享继续0.1.3，生产保持原版本。研究、可复现工具和全部正反证据本地交付；没有实现所有PG场景至少持平SQLite。

三轮完整来源同步＋关键词 PG 为 298.914→305.537 ms（+2.22%），候选 PG/SQ 为 0.992×。普通短 field 为 4.050→5.713 ms（+41.05%），候选 PG/SQ 为 2.099×。这些是交错独立容器结果，不把全部差异归因于代码。

本批 original/optimized 的 Memory 都是完整 `e5e1b394a8f6d318dda4d9280587e599fd64c653`、运行源码 `4447bb4cad78877f4ecee0766081d08396cfa227`，98 个包文件一致。只有共享存储从 0.1.3 / `019b954195b4d3afc9e754c3cbd1c0cdd1e225ce` 换为 0.1.4 / `16700d966e88fd9b2b80473105713e5b21f5764d`。固定 wheel SHA256 为 `8de3bbca2c49618b79f2194fbfee1b0232a351911b6fdad1fdfbc019c3ba973f`，8 个共享包文件逐一核验。候选 Memory wheel 只修改 Requires-Dist 元数据及 RECORD 来装配 0.1.4；产品源码、manifest、vendor 和 lock 均未改。两侧 pip check 通过，相同基础镜像和依赖闭包。TS267 的 Q18 业务及新合同未混入。

## 原理与实际改动

PG 请求经过客户端协议、解析/重写、规划、执行与返回；pool 复用连接不会自动消除命令等待。结合 [PG17 查询链](https://www.postgresql.org/docs/17/query-path.html)与 [psycopg 原作者的 pipeline 工程案例](https://www.psycopg.org/articles/2024/05/08/psycopg3-pipeline-mode/)，候选复用原 Database.connect / StorageRuntime._checkout，把逐次会话设置与新鲜绑定 SELECT 放进一段内部 raw pipeline，全部确认和身份核对后才交出业务连接。案例使用 UNLOGGED 表，不能照搬它的持久性或速度比值。

只有两个内部模板恢复原驱动自动准备阈值：函数、表与等号操作符全部限定，计划复用不缓存参数、绑定行、来源或权限。schema 派生的不可变 SQL/quoted path 用 256 项有界缓存；每次仍重设 search_path、lock_timeout 和读写模式。初始化及业务 native/read_batch 保持 prepare=False，避免扩大临时表与未限定名字的语义。保留设置失败、绑定 SQL 错误、元组不符的归属和单次回池。依据见 [PG17 PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html)。

没有移动 advisory lock 后的新语句、CAS、六次本地 revision 读取或 guard-before-commit。六次是本地新鲜读取，不是六次远端 RPC；常见单 batch 远端序列仍为 Core snapshot→Platform current access→Core head。来源全部准入后才读正文，完整组、revision/epoch、撤回和授权 corpus 的 BM25 语义保持。PG fsync/synchronous_commit/full_page_writes 和 SQLite WAL/FULL 保持；不以异步提交或删校验换速度。

每轮交错四组合，先后顺序改变，每次一个活跃有界客户端；同 NAS/SSD、CPU affinity 0–7、shares128、512MiB。NAS 不支持 CFS quota，shares 不是硬 CPU 限额。保留后台负载变化，不清 OS/PG 缓存、不改全局参数、不称物理冷启动。独立容器的随机 ID、页布局、进程 hash seed 和后台调度可影响结果，因此另做同池及同物理初态控制。

300 个完整组、30 个合成来源；SourceAuthority 的远端 owner 响应来自公开内存夹具，仍运行原生合同、来源同步、撤回、权限、guard 与业务事务，不包含真实 HTTPS、上游或模型延迟。全部语义内容签名一致，提交真实落账并重开核验；没有用 rollback 或幂等命中充当写入。

第一候选 trial405（两个模板仍 prepare=False）被否定：借连接配对耗时增加 27.67%，授权 field 增加 2.38%；样本、wheel 和源 hash 全部保留。trial406 恢复限定模板计划后接近持平；trial407 再消除重复 SQL 标识符构造后只有有限 wall 改善，客户端 CPU 仍增加。这些是独立因果研究，不混入正式 5,280 个样本，也不代表远端来源同步或高并发收益。区间按 block 内完整 pair 重采样 3,000 次，仅描述本次负载。

## SQLite 相同物理初态写入控制

三 block、四 case 每 block 各 10 对，共 120 对/240 次正式真实提交；另 24 对/48 次独立预热提交。每对 DB、guard 和合成状态初始字节/hash 一致，复制和目录 fsync 在计时外；路径、namespace、pool4、clock 与 hashseed 相同，先后顺序各半。每次核验持久增长、ledger、guard 变化和重开后的 quick_check/FK/完整组签名。

SQLite配对出现变慢证据，不能宣称无退步：普通提交、来源同步提交。SQLite分支AST虽与基线相同，装配/进程/物理写入和背景因素的贡献尚未分离，不能把差异全部归因SQLite业务逻辑。原型不满足性能验收，未采用；实际运行树保持原样。

## 下一层优化及交付边界

按实测证据依次推进：首先消除 Contracts 的重复 validator evolve/descend 与资源构造；其次只在同一快照、无 DML 依赖的读层继续使用现有 read_batch；写入先把 trigger、WAL、guard fsync 和 commit 成本单列，再决定是否做保持原错误与完整组边界的集合写入；锁与并发须先梳理 schema advisory lock/外部 guard 的共享关系。每一块都要有权限、撤回、CAS、持久性与 SQLite 对照。具体调用链、类似工程方案、反例和停止条件见[研究文档](pg-system-performance-2026-10-21.research.md)，这些后续块未冒称已实施。

原型共享修改和相关测试留在隔离实验分支，不合入根运行层；交付只集成基准工具、研究与报告。Memory业务属于另行进行的TS267，未写入它的代码、产品pins/vendor/lock，也未把Q18行为冒称已测。本地共享保留0.1.3/019b954，生产Q15、PG参数与现有服务均未更新。

被否决原型的验证有效结果：共享119项＝93本地＋26原生PG；其中最终受影响文件本地34项、原生26项重验，其余59项沿用适用结果。产品相关249项＝最终原生PG102项＋未受影响的本地/替身147项。首轮31个本地basetemp setup错误、产品55个TLS路径setup错误均未执行测试主体，修正临时目录后仅补相应节点；第二候选1个prepared缓存测试oracle修正后补验，运行行为未因此改变。原失败、修复及XML hash保留；最初本地输出只有工具摘录，不伪造完整XML。本轮未重跑完整SQLite套件，既有完整结果见上批报告。新增工具Ruff与diff检查通过。

本批 UUID 测试库/角色、合成目录、容器及四个新测试镜像标签已清理。十个核心服务的生命周期、镜像与挂载、五个 TLS live/ready、配置 hash、guard/capacity 和 129 个非目标容器的已采集字段前后保持。未挂载、读取正文或写入生产业务/媒体库；未访问 Redis、模型、QQ。足迹对比限于记录字段，不是全量业务或媒体内容校验。
