## 2. 交付目标与不能省略的工作

目标是固定视角、插画质感的精细房间：大窗与纱帘、窗边阅读人物、书架与衣橱、右侧床铺、前景书桌，淡木色/乳白/雾紫，柔和日光和局部暖灯。禁止自行变更布局、人物风格、家具类型或色调。

“一致”以实际浏览器画面与主图逐项对照为准，不以“都有床和窗”判定。动态场景不能诚实承诺与生成图片每个像素相同；构图、资产轮廓、人物形象、材质细节、光照气氛与 UI 层级必须分别达标。出现无法兼容的原图细节，须列出具体差异与修正稿，不能默默降低标准。

这是资产制作与渲染共同完成的工作。必须交付可编辑资产源文件、纹理、可运行 GLB、动画和来源/使用权记录。生成一张更漂亮的图片，或把概念图铺成背景，都不构成动态小屋完成。若资产制作能力不足，应明确为该阶段的阻断，不能用新的程序几何占位替代成品。

## 3. 锁定实现路线

沿用 React/TypeScript 页面和已有 Three.js 0.186.0，正交固定镜头；本次不升级引擎、不引入第二套常驻场景引擎、不增加 NAS 图形服务。图形在访问网页的设备上计算。

采用精制轻量 3D 场景与绘制纹理结合的路线：房间、家具、角色使用建模工具制作并导出 glTF/GLB；木纹、布纹、书脊、画框与植物叶片有专门纹理。固定视角允许将细节预算集中在可见面，但门窗、窗帘、角色等可运动部分必须保留真实可动结构。Three.js GLTFLoader 的加载能力参考官方文档 https://threejs.org/docs/pages/GLTFLoader.html ，具体兼容性在项目锁定版本中验证。

资产制作采用 Blender 工作流。执行阶段已核官方便携 Blender 4.5.14 并完成环境 GLB 导出；MPFB 2.0.17 的真实网格/骨架导出也已试证，但美术产能不能由工具可用推导。家具可由受控脚本辅助建模，但必须通过相同美术门槛。角色需专门模型、贴图、骨骼和动作，不以球体小人验收。

静态接触细节可使用适度 AO/贴图增强；不得把强烈午后日光、角色投影或灯具亮斑烘焙进全天使用的底色。动态日光和两盏局部灯各有真实遮挡；柔和间接光采用受控补光近似，不能宣称浏览器实现完整物理全局光照。纱帘透光/阴影需单独样片校准，透明材质设置本身不证明透光正确。

角色采用与原图匹配的动漫风格 3D 模型及材质，与房间共用光照和接触阴影；先完成同构图阅读姿态，再做眨眼、呼吸、翻页等小幅动作。若无法匹配原图风格，停在资产返修，不临时切成风格不同的通用人物。行走、换装与更多活动安排在基本外观达标后；不能将新增自拍图片当作可换装资产。

## 4. 资产与场景规范

| 交付物 | 必须包含 | 视觉验收重点 |
| --- | --- | --- |
| 房间壳和镜头 | 相机位置/目标/正交范围、地板、窗洞、墙厚、固定构图 | 主图房间轮廓、地板可见比例、窗/床/桌相对位置 |
| 门窗与窗景 | 独立窗扇轴、窗框、玻璃、分层天空/城市/树影 | 窗外有空间层次；玻璃关闭仍透光 |
| 双层窗帘 | 纱帘、遮光帘各自网格和顶部锚点、开合及风摆范围 | 有褶皱和透光层次，不像平面板 |
| 家具及软装 | 衣橱、书架、沙发/扶手椅、床、书桌椅、床头柜、圆边桌、地毯 | 倒角与接缝、床被褶皱、坐垫厚度、家具比例 |
| 饰物 | 书本、相框、花瓶、盆栽、杯子、文具、日记、闹钟 | 按原图组织，细节有主次，不随意堆放 |
| 人物 | 发型/脸/服装/阅读坐姿、书本、骨骼、遮挡关系 | 不是灰模；手与书、脚与地面、身体与座椅接触正确 |
| 灯具与材质 | 独立发光部位、光源、材质参数、纹理色彩约定 | 光只影响合理范围；白天不灰脏，夜间不全屋泛黄 |

每个资产有稳定 objectId、版本、尺寸单位、原点/运动轴、命名节点、材质与贴图清单、动画名、热点锚点、来源和授权记录。manifest 必须检查缺失节点/纹理/不匹配版本，不能静默跳过家具。美术源文件与网页发布资源分开管理，大体积源资产的存放方式在执行卡中确定。

## 5. 高内聚、低耦合边界

| 模块（拟议） | 唯一职责 | 禁止承担 |
| --- | --- | --- |
| RoomPage / 页面布局 | 标题、角色选择、日程侧栏、聊天入口、环境抽屉 | 在页面中拼几何、逐帧修改业务状态 |
| RoomStateAdapter | 将核心快照和命令映射成前端状态，处理版本/确认/离线 | 生成材质、读取其他产品数据库 |
| RoomPreviewController | 本地时间与灯窗预览，退出恢复权威状态 | 写日记、触发日程、冒充已保存 |
| RoomAssetLoader / manifest | 加载、校验、缓存、释放资产 | 业务权限判断 |
| RoomScene | 组织资产节点和热点锚点 | 网络请求、持久化、角色决策 |
| EnvironmentController | 时间、日光、局部灯、帘摆参数求值 | 逐帧调用模型、决定真实生活时间 |
| CharacterPresenter | 根据活动状态选择姿态和动画 | 自行改变日程、心情、衣服事实 |
| RenderHost | 相机、画质、帧调度、上下文恢复、资源释放 | 管理用户登录和日记授权 |

物件 ID 与核心已有接口先核对，再冻结最小 DTO；不在规划中虚构接口已存在。前端提交意图，核心保存状态，确认前显示待生效。多客户端、手动保持和重新进入均取核心权威版本；预览始终隔离。NAS 仍负责静态资源和既有服务，不新增“房间微服务”。

## 6. 页面还原

桌面版以原图为准：房间占主区域，右侧今日安排/当前状态，顶部生活导航，底部轻量文字交流入口，物件热点打开相应面板。调试滑块放到环境预览抽屉，不占据日常页面主体。保留非画布列表入口、键盘操作及减少动态模式。

遵循 V2 当前范围，概念图旧麦克风/实时通话不能据此重新引入。日程、心情、衣服和自拍没有真实数据时显示准确空态，不照抄图中的示例内容冒充实际状态。手机采用场景优先、详情下方展开，不把整张桌面界面缩小。

## 7. 阶段与明确停止条件

1. **R0 视觉规格冻结**：从主图记录归一化家具锚点、人物包围框、房间轮廓、镜头、色板、UI 布局；输出资产清单与对照标注。主图负责几何，四时段图负责环境，不重新随意设计一套概念。
2. **R1 真实浏览器静态样片**：完成房间全部主要资产和阅读人物，在锁定镜头下还原午后主图。提交浏览器原始截图、同尺寸原图并排/半透明叠加、差异清单。灰模仅内部定位，不能作为本阶段交付。此门槛不通过，不进入全面动态扩展。
3. **R2 环境样片**：同一资产连续昼夜、两盏独立灯、双层窗帘与窗扇、风摆衰减；交付四时段实际截图和连续录屏。原图局部存在不物理一致之处时，保持视觉目标并记录可解释近似，不伪造物理效果。
4. **R3 产品页面与生活接入**：接回角色/日程/衣橱/日记等已支持入口、权限和核心状态；补齐阅读待机动作，预览与真实状态明确分离。未具备的业务接口列为待办，不在前端造假。
5. **R4 性能与部署验收**：桌面/移动端实际设备测量、资源加载失败/图形上下文恢复、多客户端/后台恢复测试；固定代码与资产版本后再走已有受控部署更新，保持容量守护的容器身份约束。禁止直接在 Dockge 重建来绕过部署流程。

资产制作与页面布局可在 R0 后并行，渲染人员消费版本化资产接口，业务接入人员只写适配层；共享入口单写者。当前仅规划，未派发新任务；正式任务需独立 worktree、明确文件白名单、资产交付清单和上述阶段门槛。

## 8. 可执行验收标准（建议值，非已取得成绩）

- 固定视口、DPR、时间、镜头、资源版本和动画时刻；比较房间裁切与整页两种画面，不能通过改截图缩放掩盖差异。
- R0 标记窗中心、书架/衣橱/床/桌角、人物头脚等至少 12 个锚点；R1 主要锚点偏差目标不超过房间裁切宽高的 3%，不得缺失主要家具或改变相对次序。该数字仅辅助构图，不能代替美术判断。
- 构图、人物、家具细节、材质、光照、页面布局六项分别判定；任何一项仍明显是占位或风格不符，整体验收不通过。不得用加权平均掩盖人物不合格。
- 像素差异/相似度用于定位问题，原图是生成图，不设一个相似度分数冒充“美术一致”。对最终实际浏览器样片做用户视觉确认；具体可看的样片准备好后再确认，不提前反复征求抽象批准。
- 环境行为按原环境设计九项验收，额外检查动态物体没有烘焙残影、四时段相同房间没有资产漂移。
- 初始性能预算：首屏可见资源压缩后不超过 15 MB，后续角色动作分批加载；桌面目标稳定 30 fps 以上，移动端中档目标 30 fps。R1/R2 在明确设备、浏览器、分辨率上记录帧时间分布、峰值内存、加载耗时与 draw calls，再据实校准。没有真实设备数据不能报告达标。
- 低档降低阴影分辨率、后处理和小装饰开销，保留主要资产、构图与人物；不能退回本次被否决的几何小人。无 WebGL 时可用已批准实际场景的静态预览与普通操作列表，并清楚标明非实时场景。
