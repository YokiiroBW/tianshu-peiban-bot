# 记忆系统复盘、研究对照与 Q13 收敛

本轮先发布已验收的 Q12，再复盘和改进。当前线上为 Memory `97f2b01`、Companion `ed4af8b`，新一轮 Q13 在 TS-220/221 独立检出验证；两者不能混称已部署。发布详情见 [Q12 回执](memory-quality12-release-2026-10-20.json)。

## 当前系统实际边界

原生 OneBot 接收经过真实账号/人物/角色/受众绑定的消息，Companion 收集等待 1500ms，取得短期对话、Memory 召回、画像及必要资料，经过当前来源/权限检查后调用日常聊天模型并投递；异步整理使用独立 OpenCode DeepSeek，候选由 Memory 核验来源、证据和对象后提交。更正、遗忘、来源失效和回执恢复都沿原有路径，不由模型决定身份或权限。

Memory 保存原始来源引用、事实原话/条件/否定、人物与对象实体、修订及替代历史，SQLite/WAL 和单写者仍是本次实际部署。结构化画像有独立确认和发布，自动抽取不等于确认。Companion 的当前对话窗口与长期事实分开：未送达助手稿不能冒充历史，来源撤回后旧上下文也不能继续使用。

本次只读查询实际检索设置：**keyword、rerank=false、candidates=40**。向量/混合检索和 RRF 的代码存在，但不能写成线上已经启用。其向量缓存目前为进程内派生缓存，冷索引需批量计算，尚无本轮真实嵌入模型验收。日常 Gemini 和自动提取模型未变。

后台队列已有持久任务、独立后台槽、前台优先但防后台饥饿、有限重试、提议/回执复用；不是每次整理失败都重跑整段聊天。检查点之间仍须新核验，不能把跨轮权限结果放入长期缓存来换速度。

“存得下”和“这次会拿来用”也不同：自动抽取的已知事实材料最多取近期 128 条且有 32KiB 预算；向量/混合路径单个已授权范围最多检查 4096 组；最终还受查询 limit、完整组预算和短期窗口限制。旧事实留在库里不保证每次都进入抽取对照或回答材料，需要专门做超窗口和大库评测。

## 是否一直在堆代码

从用户保存的 10 月 13 日提交到 Q12，只统计 `src/**/*.py`：

| 产品 | 起点 | 当前 | 新增 / 删除 | 净增长 |
| --- | --- | --- | --- | --- |
| Memory | 83 文件 / 22,996 行 | 90 文件 / 24,303 行 | 1,460 / 153 | +1,307 行（5.7%） |
| Companion | 68 文件 / 27,767 行 | 76 文件 / 29,717 行 | 2,125 / 175 | +1,950 行（7.0%） |

确实有删除与替换，但总体偏重新增。Companion 的数值还包含听书、陪读等业务，不能全部记作记忆补丁；Memory 增长主要集中在别称、对象、来源引用和召回规则。问题是同一知识开始出现在 Core 英文提示、中文来源提示和逐人原文副本里，维护和模型输入都付出重复成本。

Q13 沿既有模块处理：查询的主题、对象限定、引文锚点和时间偏好在一次请求中解析一次；匹配得到的时间优先级复用，不再对同候选反复解析。上下文保留现有原话位置，删除另一个逐人原文副本，增加稳定来源引用和顺序索引；人物/时间/群体语义统一放 `qq_identity.SOURCE_INSTRUCTION`，删除 Core 重复段。没有新增平行存储、框架依赖、迁移、权限缓存或规则引擎。

## 论文和成熟实现对照

只使用作者论文和官方仓库。源码固定提交、文件和哈希见 `.runtime/memory-quality13-research/sources.json`；下载代码仅阅读，未安装或执行。GitHub API 限流后使用浅克隆与稀疏检出；Letta 主仓当前已指向 letta-code，未把旧 V1 归档当现行实现。

| 来源 | 可借鉴的机制 | 与天枢的对应和差距 |
| --- | --- | --- |
| [LongMemEval，ICLR 2025](https://arxiv.org/html/2410.10813v2) | 将索引、检索和阅读分开评估；覆盖抽取、跨会话、更新、时间和未知问题；事实增强索引、结构化阅读有价值 | 天枢不能把“已送达”计作语义正确。应分别记录是否存下、是否取出、是否被模型正确使用；Q13 先消除阅读材料重复 |
| [LoCoMo，ACL 2024](https://github.com/snap-research/locomo) | 多会话长对话、问答与事件总结，有证据对话编号 | 可补长期跨话题、跨会话和事件轨迹评测；中文多人、多群、权限和撤回需要天枢自己的附加用例 |
| [Mem0 论文](https://arxiv.org/html/2504.19413v1)及[当前源码](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/main.py) | 论文为抽取和更新流程；当前 OSS 已采用检索旧记忆后的单次增量抽取、批量嵌入和多信号检索 | 借鉴减少模型往返与批量处理。论文旧算法、当前 OSS 和托管平台不同；不照搬广告分数，也不让助手猜测取得与人类事实同等权威 |
| [Zep 论文](https://arxiv.org/html/2501.13956v1)及[Graphiti 源码](https://github.com/getzep/graphiti/blob/3cc723cd292eb5c2ac5ea2c5539270b8e1b6389f/graphiti_core/edges.py) | 区分系统收录/失效与事实成立/结束时间；事实能回溯来源；混合检索后排序 | 天枢已有来源和替代历史，但事件时间、计划时间和事实有效期仍可能混用。应先明确时间语义并建对照用例，再决定是否需要图数据库 |
| [MemGPT 论文](https://arxiv.org/html/2310.08560v2)及[当前 Letta](https://github.com/letta-ai/letta-code/blob/e8073d4e475ab7f56e76f9aaeea81a7618a92575/src/backend/local/compaction.ts) | 分层记忆、按需调入上下文；现行本地实现有滑动窗口压缩和无法继续缩减的显式结果 | 借鉴窗口预算和分层读取。不能把摘要当原话，压缩不能丢失来源和更正依赖；天枢暂不增加一层自动摘要模型来掩盖重复输入 |
| [LangMem](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/docs/docs/concepts/conceptual_guide.md) | 区分事实集合、结构化画像、事件和行为规则，明确在线或后台形成记忆的取舍 | 天枢已有画像/事实/短上下文分工，应继续保持归属。后台抽取与用户明确记忆操作共用事实入口，不增设第二套账本 |

这些项目提供了值得研究的设计和测试，但本轮没有安装并跑其完整基准，不能给出天枢胜过某项目的分数。Mem0 主仓也明确托管优化与 OSS 不完全相同；模型、问题版本、上下文预算和评判器不同的得分不直接横比。

具体取舍：Mem0 的当前增量 ADD 思路有助于少一次模型往返，但天枢的显式更正、遗忘和来源撤权仍须生效，不能直接改成永远追加。Graphiti 的时间和来源建模值得借鉴，不意味着目前就需要增加图数据库。Letta 的文件记忆适合代理自主管理材料，不替代天枢的人物/群聊授权账本；LangMem 的命名空间也不能替代真实来源核验。当前优先消除重复材料和重复计算，后续新增能力由明确失败样例证明必要性。

## 本轮验证与后续顺序

Q13 的定量结果及最终提交补在 [Q13 交付](memory-quality13-delivery-2026-10-20.json)。排序基准是同机、768 条已授权候选、10 个相同查询的五次批次中位：411.6→347.2ms，约下降 15.6%；7,680 组限定/文本对照和排序 ID 一致。它不包含来源网络、模型或 QQ 投递，不能宣称端到端提速。

16 条候选的小库对照为每批 10 问 14.15→14.34ms，差异很小，没有小库提速结论。精简提示的首版出现未问日期、性别称谓和额外历史推测，保留原始输出；后续改写集中在同一个规则段，未叠加新的提示区块。是否接受最终候选以实际复测为准，不以行数下降代替质量验收。

按影响继续推进：

1. **收敛当前路径并保留失败样例**：先验收 Q13 单份原文和自然确认表达；语义失败与连接、抽取和投递失败分开记。
2. **补受控的语义召回**：基于现有检索接口，比较原查询、事实关键词、限定对象和受控二次检索。先证明中文改写召回收益，再决定启用现有向量能力；不能悄悄换模型或默认开启额外调用。
3. **明确时间模型**：观察时间、用户本地参考日期、事件计划/发生时间、事实成立/结束时间各有归属，支持未知。相对日期不能只依据 UTC 强行换算，旧记录不批量猜日期。
4. **长期事件与群体状态**：保留个人提议→采纳→待定→退出的证据链；先对长历史、多事件同词、同名人物和撤回建固定样例，避免每遇到一种表达就加正则。
5. **按阶段优化长尾**：单列收集、来源核验、准备、模型槽、模型首段、生成、投递和整理/回执耗时。数据库或缓存改造必须用这些数据定位，不能承诺换 PG/Redis 就使模型回复快一倍。另一个线程的存储规划不在本轮混入。

所有测试使用隔离账号和库；OpenCode DeepSeek 账本继续累计，额度用尽才按用户授权追加。日常 Gemini、真实用户记忆、QQ/通知以及现有媒体挂载保持。

本轮模型质量和耗时来自 OpenCode DeepSeek；没有调用日常 Gemini 做另一个评分。源码接线与线上一致，也不意味着这组模型回答质量就是 Gemini 的实测质量。
