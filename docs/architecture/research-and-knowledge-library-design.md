# 搜索、自动研究与资料库

日期：2026-09-13。用户要求：既能在后台手动提交网址或文件整理入库，也能让 AI 为任务或兴趣主动搜索，并把有价值的研究资料和结论持续保存，避免查完即丢。本文是目标架构及整理规则，未启动在线入库服务。

## 模块职责

需要独立的资料处理职责，但首期不必增加一个独立软件或一组微服务。沿用天枢记忆中的 Knowledge 资料域，并与平台的资料界面、搜索连接器和后台任务协作。

| 部分 | 职责 |
| --- | --- |
| 搜索与获取能力 | 连接搜索源、本地资料检索、网页获取及文件读取，返回结果与来源，不自行维护用户画像 |
| Knowledge 资料模块 | 接收资料、解析、保留版本、整理笔记、建立完整语义单元与索引、按来源查询 |
| 研究任务 | 由陪伴、Codex、Hermes 或平台任务提出问题、范围和预算，选择资料、比较证据并形成结论 |
| 天枢资料界面 | 提交网址/文件、选择资料库、查看整理进度、搜索资料、阅读原文与研究笔记 |

资料入库任务由 Knowledge 负责持久状态，平台展示其任务投影；下载、项目执行或角色生活仍由各自模块负责。原文件可复用已有文件/资产存储，数据库保存来源、版本、关系和可检索单元，不把所有二进制文件塞进人物记忆表。

对于 AssetLibrary 已管理的资源库，物理文件移动、改名及标签写回应由其正式操作用例负责；Knowledge 引用资产与版本进行解析，不自行操作其物理目录。音乐和通用文件的整理边界见 [NAS 文件整理协作](assetlibrary-nas-organization-design.md)。

## 三种入口，共用一条整理流程

手动提交网址或文件、AI 任务中的查阅与引用、角色按兴趣发起的研究，都进入：

接收来源 → 获取正文或文件 → 解析与质量检查 → 去重及版本识别 → 提取资料单元 → 形成带来源的笔记 → 发布查询视图与索引 → 关联项目或角色书架。

网页正文提取与文件解析先由相应解析器完成，模型负责理解、分类、主题摘要、重要论点及局限等整理工作。模型按固定输出结构工作，不自行决定数据库表结构，也不把原文改写后丢弃来源。

首期可优先覆盖可提取文本的 PDF、Markdown、纯文本和普通网页；扫描 PDF、复杂网页、Office 或视频字幕按已实现解析能力处理。未支持、正文不完整、识别失败分别记录，不能用页面标题或搜索摘要冒充已读全文。

## 手动加入资料

后台提供“添加网址”“上传文件”“加入指定项目资料库”入口，选择归属库和整理方式后提交任务。界面显示已接收、获取中、解析中、整理中、可检索、部分完成或失败，并能查看具体缺失部分和重试结果。

普通资料在已经配置允许自动整理的库内自动处理，不要求每篇文章重复走一套人工审批。来源无法获取、内容质量不足、归属不明、相互矛盾或需要跨范围共享时再进入待复核。自动收录只表示已记录并可追溯，不表示文章结论被证明正确。

模型分析所用的服务在统一模型配置中选择。私有库使用哪些分析接入商与材料范围应在配置时明确，不因为外部模型临时不可用就把材料发往未配置的备用服务。

## AI 搜索如何自动留下资料

在天枢自己的搜索/阅读接口中，自动记录查询任务、实际打开的来源、内容获取状态、选用理由及引用关系。任务结束时将有价值的来源和研究笔记归入相应资料库。

默认优先保存人工提交、AI 实际阅读并使用、最终引用或主动标记有用的资料。仅出现在搜索结果中的大量链接可以保留为有限的候选记录，不全部进行全文解析和模型总结。未获取正文时可先保存书签，但必须标明整理不足。

Codex/Hermes 若使用各自的内置搜索工具，不能仅因连接了 MCP 就宣称天枢能自动监听所有搜索。需要相应工具包装、可用生命周期钩子，或在研究阶段结束时调用统一的来源/笔记回写接口。拿不到正文或完整引用时只记录实际可获得的内容和状态。

相关来源通过稳定来源编号及版本引用去重，同一篇资料可被多个项目或研究专题引用。不能把既有库条目搜索出来、再作为新来源重复入库，也不能把模型自己的旧总结循环加工成越来越“确定”的外部事实。

## AI 主动研究的边界

角色或研究任务可以根据当前目标、获准兴趣和未完成事项提出问题，再在预算内搜索、阅读和整理。设置每次最大搜索/页面数、运行时间、模型用量、重复主题冷却和停止条件，避免后台无限浏览和反复总结同一内容。

入库和主动推送分开。找到了有用材料可以先保存，只有存在相关新信息、对象合适且时机允许时才推送。资料已进入共享库，不等于每个角色都亲自阅读过；阅读/学习事件和库中资源的存在分别记录。

AI 因某个任务查询一篇论文，也不等于用户长期喜欢这篇论文或某个领域。它先形成该任务的资料引用，不能自动写成人物偏好。

## 持久保存四类内容

| 内容 | 保存重点 |
| --- | --- |
| 来源记录与版本 | 标题、作者/发布者、网址或文件出处、发表/获取时间、内容版本及获取状态；可以保存的正文或上传文件保留快照 |
| 可引用资料单元 | 论点、方法、条件、证据、局限、接口定义等完整片段，带准确来源位置 |
| 研究笔记 | 本次研究问题、比较结果、推论、未解决问题和所引用资料版本 |
| 项目/角色关联 | 哪个项目使用了它、用于什么判断、哪个角色何时实际阅读、是否收藏到书架 |

“来源认为某方法有效”“我们据此建议采用某设计”“项目已经决定采用”是不同内容类型。前者属于来源论述，中间是研究推论，后者要有项目决定的依据；不能由模型总结自动把三者合并成事实。

不适合保存全文时，可保存来源链接、允许保留的片段和自己的研究笔记。引用始终指向实际读取到的版本；不能为只见过摘要的资料编造页码、实验数据或原文引句。

## 版本、质量与查询

来源身份与内容版本分开：同一网址内容变化形成新版本；论文的不同版本、同一项目的不同提交不可直接合成一份“最新内容”。标题相似不代表同一来源，转载与原始来源保留关系，不丢作者与出处。

来源可信程度、解析完整度、研究相关性和结论确定程度分别记录。可检索的资料可以保留不同观点；低质量片段、广告导航与重复模板不挤入默认召回。模型生成的摘要不能当作全文已经被完整验证的证明。

下次查询先检查库内有没有适用版本；软件接口、模型能力等易变化内容按时效要求补查，稳定的历史研究可复用已有引用。原有研究笔记继续固定旧版本，必要时提示有更新，不静默改变过去结论的依据。

调用者按当前项目、角色、受众与任务选择相关小块，沿用最小充分语义规则；条件、否定、因果和引用依赖一起保留。需要细节再读原文，不能把整个资料库或所有研究笔记一次性塞入模型。

## 与记忆、项目和客户端的衔接

Knowledge 保存外部资料与研究产物；人物记忆保存适用的个人认识和互动经历；项目工作台维护当前任务与交接。三者通过来源和项目编号关联，各自负责的数据不互相复制为主库。

项目内原始文档仍由 Git/源目录维护，资料库可索引和保存明确版本引用；不把资料库里的摘要当作可独立修改的另一份项目规范。Codex、Hermes 与陪伴核心通过同一组来源、查询与笔记接口使用资料。

最少需要“提交来源”“查询资料”“读取片段”“保存研究笔记/引用”“查看任务状态”几类能力；名称与实际 API 后续确定。所有入口保留真实来源身份，不以模型伪造用户事件触发入库。

## 验收要求

- 同一手动网址、上传文件和 AI 来源重复提交，不产生失控重复条目；不同版本仍可追溯。
- 搜索线索、读到的正文、研究推论和项目决定在数据与展示上保持区别。
- 本次引用的来源及其用途能在下次任务中被查回，不依赖原客户端还保留整段聊天。
- 获取失败或仅提取部分内容，不显示“全文已整理”；普通自动入库和异常复核有真实状态。
- 资料更新后可以查新版本，旧结论仍能回溯当时依据。
- 私有项目资料、角色阅读记录与通用资料不因去重或共享索引而越界。
- 后台研究受预算与去重限制，不拖住普通对话，也不因为“主动”就不断推送。
- 新模块按完整语义片段查询，不重复把整篇摘要或整份人物资料注入每轮上下文。
