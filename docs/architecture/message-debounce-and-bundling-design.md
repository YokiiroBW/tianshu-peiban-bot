# 连续短句防抖与结构化消息组

日期：2026-09-13。用户已明确要求：可自定义静默窗口；窗口内再收到消息就重新计时，静默达到窗口长度后再合并处理；合并必须保留发言的逻辑。本文是设计契约，尚未实现运行中的防抖服务。

后续确认：一轮窗口结束并进入处理后，普通新消息进入下一轮的独立缓冲，不能自动打断或重做第一轮。第二轮收集完成即可提前处理，不以第一轮发送完成作为处理前置条件；发送顺序与实际依赖另行协调。

## 放在链路的哪个位置

原始事件受理、去重、身份与会话定位 → 收集连续发言 → 静默窗口结束 → 形成结构化消息组 → 回应判断与角色仲裁 → 情境/记忆装配 → 生成、核对和投递。

原始消息收到后立即保存，不等窗口结束才归档。收集期间不逐条调用对话模型、不分别生成回复，也不把尚未说完整的片段直接固化为长期画像。窗口内可以做必要且有界的附件接收等准备；工具执行和最终意图判断等待消息组形成。明确停止/取消等控制事件按下述专用路径处理。

## 滑动静默窗口

令静默窗口为 W，最近一条有效活动的受理时刻为 last_activity，截止时刻为 last_activity + W。

- 首条消息创建待处理消息组，并设置截止时间。
- 同一收集键的新消息在截止时间之前到达，追加到组内，并将截止时间改为这条消息的受理时刻 + W。
- 达到截止时间仍无新活动时，封存一次消息组并提交后续链路。
- W = 0 表示关闭等待，仍保留结构化输入和去重。
- 到期任务必须核对消息组编号、修订号和最新截止时间；旧计时器不能触发旧版本回复。

以 5 秒窗口为例：

| 受理时刻 | 用户发言 | 新截止时间 |
| --- | --- | --- |
| 第 0 秒 | 我想要一张自拍 | 第 5 秒 |
| 第 2 秒 | 今天穿休闲一点 | 第 7 秒 |
| 第 6 秒 | 等等，还是换成睡衣吧 | 第 11 秒 |
| 第 11 秒 | 没有新增消息 | 将三条发言作为一个消息组提交 |

窗口按核心受理顺序和服务端时间计算，不依赖用户设备时钟。规则明确为“新活动时间 < 截止时间”才属于原窗口；恰好等于截止时间时，先封存旧组，再创建新组。封存后，普通新发言属于后续轮次，不因此使第一轮输入或草稿失效。

处理消息和计时器由同一个会话所有者有序执行。到期封存时先核对已受理输入，不能让陈旧的回调跳过已经收到的续句。不以平台原始发送时间回填已经关闭的窗口；延迟抵达的消息进入新输入，保留原发送时间作上下文。

## 配置如何提供

| 设置 | 设计 |
| --- | --- |
| 启用连续发言等待 | 私聊、群聊分别设置默认值，具体会话可覆盖 |
| 静默窗口 | 自定义秒数；5 秒是用户给出的配置示例，不静默改成别的值 |
| 最长连续等待 | 可关闭；关闭时严格等到静默满 W。若显式开启，则同时计算首条消息后的最长截止时间 |
| 立即提交 | 客户端按钮或明确配置的指令，可提前封存当前组；普通句号和模型猜测“说完了”不提前结束窗口 |
| 同会话处理并发 | 用户已确认最多 2 个进行中的陪伴对话轮次；会话内多角色共享上限，并受全局模型/设备限额约束 |

启用最长等待 H 时，实际截止为 min(last_activity + W, first_activity + H)。默认方案不强加 H；避免无休止等待的上限是可选配置，不能悄悄改变用户要求的滑动等待语义。达到 H 关闭时记录“时间上限关闭，可能尚未说完”，不能把这一情况伪装成用户已完成完整指令。

消息数量或字节的资源限制另行处理：分片持久化、限制内存和施加有界排队。必须提前封存时标明原因及续接关系，不截掉一半内容、不因为达到容量上限就执行可能尚未被完整表达的动作。大组超出模型输入预算时按完整逻辑段分步处理，保留未处理部分。

## 哪些消息属于同一组

默认收集键为“入站绑定 + 平台会话/线程 + 发送者账号”。person_id 可以关联长期认识，但不能让一个人在 QQ、TG、群聊和私聊中的消息合成同一段输入。

普通文字、表情消息、图片、语音和文件等用户发言可以重置窗口。投递回执、正在输入状态、群系统通知、后台任务结果及机器人自身消息不重置用户的静默计时。相同消息编号/版本的重投递不重置；不同消息编号的相同文本仍可能是用户有意重复，不按正文哈希直接丢弃。

多个角色共用接入时，统一收集后再按每条消息明确的目标分发和仲裁，避免每个角色重新等待一次完整窗口。若同组分别提及 A 和 B，保留各自目标，不把整组强行归给最后提到的角色。

## 合并是组成消息组

MessageBundle 保留以下最小结构：

| 内容 | 用途 |
| --- | --- |
| 组编号、修订号、收集键、关闭原因 | 追踪本次输入，防止计时器和生成结果重复生效 |
| 分配后的轮次编号、前轮依赖与结果版本 | 支持并行准备和有序发送；后轮新消息不会改变前轮输入修订 |
| 原消息编号与顺序 | 逐条追溯，不产生一条虚假的“原始长消息” |
| 各条发言者、受理时间、原发送时间 | 保留作者和时间关系 |
| 各条内容段 | 文本、图片、语音等按原顺序保存；附件描述不覆盖用户原话 |
| 各条引用、提及、目标角色与编辑状态 | 解释补充、不同回复对象、撤回和修正 |
| 必要的群内上下文引用 | 保留插话或被引用内容，不把它们改成当前发送者的新发言 |

向模型渲染时可使用分开的用户消息或带明确分段的单个内容载体，但必须保留顺序、作者和引用。不能用字符串无分隔拼接，也不默认新增一个模型先把全部短句改写成一句话。

上述例子的语义输入是：

> 用户连续发言，按受理顺序：
> 1. 我想要一张自拍
> 2. 今天穿休闲一点
> 3. 等等，还是换成睡衣吧

核心据此理解第三条修改了服装要求，但第一条的自拍请求仍在。不能简单地“只保留最后一条”，也不能同时按第二、第三条生成两个相互冲突的服装任务。

合并的规则包括：同一对象的明确补充与修正保留前后关系；不同引用或目标角色分段表示；显式转题可形成子段；不同任务分别保留。无法确认两条话是否互相修正时，保留原文与不确定性，由正常回应链解释或询问，不在收集阶段擅自定论。

图片后的“这个”、语音后的文字补充等，应保留原媒体和相邻发言供理解。存在多张图或多个可能对象时，不仅靠“最近一个”强制归因。媒体下载或转写完成不算新用户发言，不无限延长静默窗口；所需媒体尚未就绪时进入独立、有上限的准备等待。

## 群聊中的插话

每位发送者分别收集，B 的消息不重置 A 的计时器。房间另有按受理顺序维护的公共时间线。

如果顺序为 A1 → B1 → A2，A 的消息组仍只拥有 A1、A2，但保留 B1 的相关上下文引用；实际装配时按顺序恢复必要插话，并明确 B1 的作者和“背景上下文”身份。不能把 A1、A2 展示为中间无人发言的连续独白，也不能把 B1 当作 A 的话。

多个消息组就绪后，房间级回应调度器按目标角色、相关性与轮次处理。能共同回应时保留各作者形成一个回应目标，不能重复回答同一引用；不能共同回应时分别处理。其他成员持续发言不应让某人的已就绪输入一直重新计时。

## 生成期间收到新消息

采用“持续收集、有限并行处理、按序投递”的流水线。收集缓冲、处理中轮次与待发送队列分别维护，不能把整个会话锁住直到上一轮发送完毕。

- T1 封存后固定其消息成员、目标、轮次编号和本轮输入修订，继续生成及投递。
- 普通新消息创建 T2 缓冲，并按同样的静默窗口追加后续短句；T2 不重新启动 T1 的计时器，也不修改 T1 的消息成员。
- T2 窗口结束后立即成为可处理轮次。在资源允许时，与 T1 并行读取情境、查询必要记忆并生成候选；不能规定必须等 T1 发完才开始。
- T2 比 T1 更早完成生成时，先进入待发送队列。默认同一角色、同一会话的正常回复按轮次发送，避免后问先答或段落交错；T2 的存在不阻止已经就绪的 T1 发出。
- 只有实际依赖、资源限额或明确控制事件才产生必要等待。新消息本身不是取消、重启或丢弃第一轮的理由。

时间示例：下表假设有两个生成槽，两个问题互不依赖；生成与发送完成时间仅用于演示并行关系，不是性能实测。

| 时刻 | 第一轮 T1 | 第二轮 T2 |
| --- | --- | --- |
| 第 0 秒 | 收到 m1，开始收集 | 尚未创建 |
| 第 5 秒 | 窗口关闭，开始处理 | 尚未创建 |
| 第 6、8 秒 | 继续处理，不重启 | 收到 m2、m3，窗口更新至第 13 秒 |
| 第 13 秒 | 仍在生成 | 独立封存并开始处理 |
| 第 15 秒 | 仍在生成 | 候选已完成，等待发送顺序 |
| 第 16 秒 | 候选完成，开始发送 | 保留已完成候选，无需重新处理 |
| 第 18 秒 | 本轮发送完成 | 开始发送 |

T1 只拥有 m1，T2 只拥有 m2、m3。T2 的背景上下文可以引用 T1 的输入，但不能把它当成 T2 新收到的消息再执行一次。

## 处理可以并行，依赖不能猜测

T2 可先使用已知的房间时间线、必要人物认识和 T1 用户输入作为背景，并明确标记“前轮回答/任务结果尚未就绪”。不能把 T1 未生成或未发送的草稿当作用户已经看到的答复。

如果 T2 是独立问题，可以直接完成生成。如果 T2 问“把你第一条方案展开”，但 T1 方案还没产生，T2 先完成身份、意图和不依赖该方案的检索准备，只在需要该方案的步骤等待。T1 的稳定、已核对结果可供依赖时，T2 即可继续生成，不必等到 T1 所有消息发送完成。

依赖引用需要记录所依赖的结果及版本。T1 失败、取消、或其结果实际被修改时，T2 应调整相应部分或说明缺口，不能使用猜测的前轮答案。普通新轮次不会递增 T1 的输入修订，也不能用“当前最新消息编号大于 T1 的编号”直接判定 T1 过时。

共享角色状态与正式记忆按来源顺序、依赖和版本提交，不按模型完成先后覆盖。T2 先完成，不能让随后完成的 T1 把较新的明确状态覆盖成旧值。后台记忆仍以真实输入、执行结果和发送回执为依据，候选完成不等于已向用户表达。

操作同一设备、同一文件或同一任务时，副作用按目标和依赖协调。比如先开灯后关灯，不能因模型并发完成顺序而变成最终开灯。计算并发不代表所有外部操作都无序并发；已提交任务仍使用稳定编号和幂等约束。

## 并发上限、发送顺序与故障

用户已确认每个逻辑会话/线程最多两个处理中陪伴轮次，会话内多角色共享该上限，另外允许一个持续收集中的缓冲组。模型线路或本地设备只有一个生成槽时，T2 仍可提前做必要准备，生成阶段等待可用槽；此时不能宣称两个主模型请求已经同时运行。达到并发上限的已封存组有界排队，不静默合并或丢掉未回答的独立问题。

明确的群管理、GsCore 等直接功能请求可走独立分流，不占用这两个对话处理槽。其命令匹配、权限、限流和回复负责方见 [功能路径与职责](functional-routing-and-ownership.md)。自然语言请求仍先经过陪伴轮次，再调用同一功能执行者。

会话所有者只负责轻量的收集、编号、状态迁移和发送排序，不持有跨越模型/工具等待的整段会话锁。首轮已开始的工作保持优先级，后续工作受全局限流控制。共享 CPU、网络、模型额度或 GPU 仍可能相互影响，因此“不打断第一轮”是调度行为要求，不是物理耗时完全不变的承诺。

每个发送项带轮次编号和段落编号，同一回复的正常段落按序提交；无需等待对方读完或音频播放完。生成槽在计算完成后释放，不能因为草稿等待发送而一直占用模型调用容量。平台缺少可靠回执时，发送状态要记录不确定性，不能承诺跨平台的绝对到达顺序。

前轮遇到超时、失败或取消时，明确结束该聊天轮次并按策略说明结果，使后轮能够继续；不能用一次永久挂起锁死后续发送。没有需要发送的观察轮次也要明确关闭。回执不明时先核对既有发送记录，避免盲目重发造成重复。

生图、下载等长工具任务继续使用关联任务机制：第一轮可在确认已提交后结束当前聊天回复，最终图片或下载结果稍后作为关联结果事件发送。后轮不必等整个工具任务完成；若它确实依赖工具结果，则仅等待该依赖，且不占用闲置的模型生成槽。

## 取消、编辑、撤回与恢复

明确的停止按钮、已注册取消指令或可以可靠定位当前任务的取消请求走高优先级路径，先检查身份及能力范围，再停止待发送/待执行动作或向执行器请求取消。它们不等待普通聊天窗口；“等等”一类没有明确对象的自然语言、引用中的“取消”等词，不能触发全局停止。

窗口内的真实编辑更新对应原消息版本，并重新计时；撤回立即使该条内容失效，剩余组从本次撤回活动重新计时。全部撤回则取消该待处理组。原文归档保留编辑与撤回事件，重投递同一修订不能再次触发。

已经封存或开始生成后，对该轮原消息的明确编辑/撤回、针对该轮的明确取消，以及真实的权限撤销等，属于例外控制事件，可以使相关草稿或任务失效；它们与普通新发言创建 T2 不同。由受影响来源产生的记忆候选也需按版本检查，必要时更正派生资料。已经发送或实际执行的内容保留真实记录，不宣称自动回滚。

持久保存组状态、最后活动时间、截止时间、消息成员与修订。进程内用单调时钟管理等待，恢复时根据持久时间计算剩余等待；不能用上次进程的单调时钟值直接恢复。过期组在核对输入、会话状态、时效和幂等后最多提交一次，不默认重新等待完整 W，也不把断线期间所有旧消息集中补发。

## 对记忆与延迟的影响

Chat Audit 继续保存原始消息，消息组仅是本轮处理载体。普通画像和经历提取尽量基于已经完整收集的组及必要上下文，并保留每条源消息引用；不能把模型合并后的表述伪装为用户原话。即时的明确取消和纠正仍走短路径，重组不能重复记账。

5 秒配置意味着最后一条有效活动后，通常先等待 5 秒，才进入正常生成链路。从第一条发言算起，还包括用户继续发言所占的时间。若已启用最长等待、立即提交或控制事件路径，则按相应关闭原因统计。

端到端指标必须包括收集窗口。此前 500 毫秒的自研处理目标只适用于窗口结束后的正常处理部分，不能拿它声称配置 5 秒后仍会半秒内回复。分别记录首条输入时间、最后活动时间、窗口关闭时间、开始处理时间、首条实质回复和最终送达时间。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 0、2、6 秒连续发言，W = 5 秒 | 第 11 秒封存一次，三条原话全部保留 |
| 新消息恰好在旧截止时刻受理 | 先封存旧组，新消息进入新组；按明确边界执行 |
| 旧计时器触发或相同事件重投 | 不提前生成、不重置计时、不重复提交 |
| 群内两人交错发言 | 分人计时，保留相关插话的真实作者和顺序 |
| 后句修正前句、媒体加说明 | 保留完整关系，一次形成当前有效目标 |
| 窗口内连续转题或多角色提及 | 原组内保留子段与目标，不把所有话变成一个人的单一指令 |
| 第一轮处理期间收到普通新消息 | 独立收集 T2；T1 不暂停、不重启、不因新消息自动失效 |
| T2 窗口关闭时 T1 尚未发送完 | T2 可以开始处理；资源和依赖允许时并行生成 |
| T2 比 T1 更早生成完成 | 保留候选并按轮次发送，不重复生成，不阻止 T1 发出 |
| T2 依赖 T1 尚未就绪的结果 | 提前完成独立准备，只等待实际依赖，不猜测前轮答案 |
| 模型槽不足、前轮失败或无回复 | 有界排队或明确关闭轮次，不丢失独立问题、不永久阻塞发送 |
| 明确取消、编辑或撤回 | 正确作用于目标与版本，旧定时器和旧候选失效 |
| 可选最长等待或容量上限触发 | 记录关闭原因及未完整状态，不能把残句当成完整操作要求 |
| 服务重启 | 恢复剩余等待或核对后提交过期组，同一组最多提交一次 |

示例时序见 [设计示例](message-debounce-and-bundling.examples.json)。示例用于明确契约，不代表已经通过真实平台并发、计时器竞争或模型生成测试。
