# 天枢与 AssetLibrary 的 NAS 文件整理

日期：2026-09-13。用户希望天枢辅助整理 NAS 文件，例如将音乐按专辑归档，并接入正在开发的 AssetLibrary。本文记录目标协作方式与当前代码边界；没有扫描、移动、改名、删除或重写真实 NAS 文件。

## 分工与入口

天枢接受自然语言目标、选择已有整理规则并辅助处理模糊分类；AssetLibrary 管理物理文件、资产身份、元数据、整理规则、操作计划、执行和界面索引；Knowledge 只对需要知识化的文档保存来源与内容索引，不充当文件操作器。

典型链路是：用户/陪伴提出整理目标 → 天枢的 AssetLibrary 连接器 → 读取限定目录的资产信息 → 规则与元数据候选 → AssetLibrary 生成变更计划 → 按配置和权限执行 → 核对文件与索引结果 → 回报。

整理规则以 AssetLibrary 为负责方。天枢可以调用、选择或提出规则变更，不另维护一套相互竞争的移动/命名引擎，也不直接写 AssetLibrary 数据库或用任意脚本绕过其文件操作用例。没有 AI 时，AssetLibrary 的确定性规则、浏览和手工整理仍应可用。

## “入库”要拆开理解

| 行为 | 是否改变原文件 |
| --- | --- |
| 登记资源库、扫描并索引 | 只读取和登记，可保留原目录位置 |
| 补充 AssetLibrary 的元数据候选或逻辑视图 | 不自动移动文件或改写音频标签 |
| 物理归档、移动和改名 | 通过正式文件操作计划改变路径 |
| 标签写回、格式转换或内容编辑 | 单独的内容变更，不能夹带在普通归档中 |

因此，音乐可以先在原 NAS 目录被 AssetLibrary 识别和展示，再决定是否整理为统一物理目录。天枢记忆记录用户明确选择的整理偏好和任务引用；AssetLibrary 保存实际采用的规则版本和文件事实。

## 音乐按专辑整理

优先读取音频内嵌标签、已有目录关系及可核对的元数据。需要补全时再使用已配置的音乐元数据源，AI 辅助解释杂乱名称、识别冲突或提出候选，不直接凭文件名和模型自评决定归属。

专辑艺人与单曲艺人分别保留。合集不能因为歌曲演唱者不同就被拆成多个专辑；古典等类别还需适用的专门规则。[Picard 术语说明](https://picard-docs.musicbrainz.org/en/latest/about_picard/glossary.html)

专辑概念和具体发行版本也要区分：普通版、豪华版、不同地区或不同碟片组成可能属于同一专辑概念，但不能直接混进同一目录。MusicBrainz 的 Release 与 Release Group 提供了这种区分。[Release](https://musicbrainz.org/doc/Release)；[Release Group](https://musicbrainz.org/doc/Release_Group)

| 情况 | 整理规则 |
| --- | --- |
| 标签完整且能确认发行归属 | 按专辑艺人、专辑、发行版本、碟号与曲序形成确定性计划 |
| 同专辑多位单曲艺人 | 保留单曲艺人，使用正确专辑归属，不按每首歌的 artist 拆组 |
| 多碟专辑 | 保留一个发行组下的碟片层次，碟内曲序分别排序 |
| 同名专辑的不同版本 | 利用发行标识、版本说明、曲目组成和日期等区分；有歧义时待确认 |
| 标签缺失或互相矛盾 | 保留在待整理状态，展示候选与依据；不自动把猜测写回文件 |
| 缺曲或仅收藏部分曲目 | 可以标注不完整，不伪造完整专辑，也不因整理请求自动补下载 |
| 同曲不同格式/版本 | 不能仅凭曲名或音频相似就删除；是否去重另行处理 |

一个可选目录模板是“音乐库 / 专辑艺人 / 年份 - 专辑名 [版本] / Disc 01 / 01 - 曲名.flac”。这是示例，不是固定格式；单碟是否省略 Disc、未知日期怎样显示、多个编码版本怎样分开，都由库规则明确。缺少必要字段时保留待整理状态，而不是拼出误导目录。

不同文件格式的标签字段通过对应解析器映射到统一元数据，不能假定所有格式使用相同标签名称。[Picard 标签映射](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html)

封面、歌词、CUE、播放列表等关联内容一起识别和规划。改变文件路径可能影响其中的相对引用；需要改写关联文件时必须作为显式变更项。整轨音频加 CUE 不能未经请求就拆轨，归档也不自动转码或改变音质。

## 通用文件整理

照片、动漫图、表情包的大批量查重、优选、多标签分类和模型成本控制，另见 [图片资源库整理设计](image-library-curation-design.md)。先登记待整理状态，再生成分类与归档计划；不要求先搬动全部源文件。

同样的机制可以用于照片时间归档、文档分类、电子书/漫画元数据、模型包和项目资料整理。但目录和复合资产的完整性优先：不能只按扩展名把项目配置、模型权重、工作流和配套文件拆散。

AI 的输出是结构化候选，例如建议目标资源库、规则模板、识别出的字段、依据和不确定项。文件身份、真实路径、冲突判断与允许动作由 AssetLibrary 核心决定，模型不能用生成的文件名代替稳定资产身份。

只向所选分析模型提供完成任务所需的信息；在线匹配、内容分析和私有资料使用范围遵循库配置。清晰的文件标签和确定性规则优先，不为每个文件都调用一次大模型。

## 计划、执行与恢复

整理前展示源范围、目标目录、文件数量、改名/移动/标签变更、关联文件、冲突与需要复核的项目。用户确认的是一份具体计划；已经配置自动整理的入站目录，可按其允许的低风险确定性规则执行。

AssetLibrary 当前需求将正式库内移动、跨库移动、工程改名和 AI/OCR 推断命名作为需要明确确认的操作。本次只记录与这些规则一致的接入设计，不改变另一仓库的发布契约。[AssetLibrary 整理需求](C:/YOKI/Codex/AssetLibrary/docs/02_已确认需求基线.md)

执行由 AssetLibrary 核心完成范围、权限、当前版本、占用、冲突、空间和内容校验。计划建立后文件被修改，不能继续按旧计划盲目操作；同名目标不默认覆盖。跨文件系统移动要先完成复制和完整性验证，再按计划处理源文件。

批量操作记录逐项结果，允许部分完成、暂停、取消和重试；不能把跨目录的大批量整理宣称成一次天然原子事务。重试不重复生成副本，已执行的文件操作不会因为对话轮次重组而再次执行。

保留原位置、目标位置、内容版本、标签变更前状态和执行记录，支持在条件满足时生成恢复计划。目标后来被编辑、旧位置被占用或证据缺失时，恢复也要重新核对，不能承诺任意时候都能无损一键撤销。

整理结束要区分文件变更完成、AssetLibrary 索引更新完成和外部播放器/阅读库刷新完成。只收到任务受理回执，不表示音乐已经出现在正确的专辑视图。

## 下载器和资料库如何配合

下载器负责获取到其受管暂存区；发布到已由 AssetLibrary 管理的正式库时，明确由 AssetLibrary 的导入/整理用例负责最终文件操作，避免两个程序各搬一次。现有下载插件已经自行归档的路径，需要在整合时选择一个负责方并迁移规则。

Knowledge 可以引用 AssetLibrary 中已登记的文件与版本，再对选定文档解析、整理和索引。音乐、图片和模型文件的二进制内容不自动进入对话记忆；资料分析不授予额外的物理移动权限。

长任务由资产服务执行，天枢保存关联任务引用并提供进度入口，不占住两个陪伴处理槽等待所有文件搬完。扫描、哈希、音频识别和在线匹配都应有范围及并发限制，优先保障前台浏览与聊天。

## 接入接口的最小范围

| 能力 | 天枢需要的结果 |
| --- | --- |
| 资源库与资产查询 | 被允许的库、稳定资产编号、实际路径/版本、元数据及复合关系 |
| 元数据候选与规则 | 可用模板、候选字段、来源和匹配说明 |
| 准备整理计划 | 明确的源/目标、变更项、冲突、预检状态和计划版本 |
| 执行、取消、查看结果 | 与计划对应的真实任务状态、逐项结果和回执 |
| 索引与恢复 | 变更后的资产引用、索引状态，以及可用恢复信息 |

通过正式 AssetLink/业务 API 或其后续 MCP 适配调用。接口名和载荷应以 AssetLibrary 已发布契约为准；尚不存在的写入口不能仅靠天枢新增一个包装就视为已交付。

## 先验证哪些情况

第一阶段只读登记与整理建议；第二阶段在隔离样本目录验证实际计划、执行与恢复；能力就绪并获得明确文件范围后，再应用于真实资料库。不能用真实音乐库作为破坏性测试数据。

重点用例：合集不拆散、多碟曲序不冲突、同名不同发行不混合、歌词封面不丢、缺标签不乱猜、同曲不同格式不误删、计划后文件变化能阻止旧操作、空间不足与断线保留可恢复状态、重复执行不重复搬运、文件完成但索引失败不虚报全成功。

示例输入与预期见 [音乐归档设计示例](assetlibrary-nas-organization.examples.json)。它们仅是虚构案例，不是可直接执行的真实文件操作计划。
