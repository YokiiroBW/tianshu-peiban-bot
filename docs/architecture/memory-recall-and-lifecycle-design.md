# 天枢记忆的召回与整理链路

日期：2026-09-13。本文细化此前陪伴核心设计，仍是目标架构建议，尚未实现、压测或确定最终接口路径。

粒度约束进一步收紧：画像按字段和原子条目取用，禁止将完整人物简介或整张主题卡默认注入。以 [画像分层与最小充分召回](profile-memory-granularity-design.md) 为具体依据；本文的“小画像/快照”均指范围化的已选字段投影，允许为空。

## 先区分三件事

准备回应时，每轮都需要有限的当前情境。这个情境包括角色配置和当前状态，也包括关于对方的必要认识。它不等于每轮都重新向量化问题、搜索所有历史，再把一大段记忆塞进提示词。

建议分成“已有认识”“按需检索”“必要时追溯原文”。此前核心图中的“天枢记忆接口”把这些路径合在了一起；主线高亮只显示主要协作模块，不能据此判断每一轮实际执行了哪些检索。本次两张图将这部分展开。

| 处理 | 何时执行 | 主要内容 |
| --- | --- | --- |
| 身份、受众与版本核对 | 每个准备回应的轮次 | 确认当前人物、角色、会话、用途、允许范围，以及将复用的资料是否有效 |
| 有限基础情境 | 每个准备回应的轮次 | 当前发言者和相关人物确需的称呼/交流字段、话题与必要事项；画像条目按需取用且允许为空，人格及活动由核心提供 |
| 精确记录查询 | 当前事项、明确对象或具体约定需要核对时 | 按人物、事项/事件编号、时间等查当前结构化记录 |
| 关键词与语义检索 | 需要往事、话题知识或间接描述时 | 在允许范围内组合关键词、语义与时间/实体条件，取少量候选 |
| 原文追溯 | 摘要不够、需要准确原话或存在冲突时 | 回读 Chat Audit 的相关消息及少量相邻上下文 |

群里每条被观察到的消息，不都需要进入完整回应流程。是否插话由陪伴核心先判断；获准观察可以在后台积累。群成员很多时，只装配当前发言者、被明确提及者及本轮相关人物的有限信息，不把全群画像逐个放进提示词。

## 每轮已经带着什么

陪伴核心维护角色的人格配置、当前活动、心情、穿搭和话题窗口。天枢记忆按本轮需求提供人物/关系字段投影、必要事项及相关证据单元。快照保留已选条目与版本，不能每轮返回完整人物简介或全部未决事项。核心可以缓存这些资料，但它们不是第二套独立维护的长期记忆。

快照不是“把所有私人资料先放进去，输出时再脱敏”。私聊、群聊、不同角色和不同用途各取自己的允许视图；同一人物编号负责关联，不能充当跨场景公开许可。

一次正常的连续对话可以复用同一话题内仍然有效的已检索证据；换人、换群、换角色、话题切换、时间敏感信息过期或相关事实变化，都需要重新判断。记忆进入上下文后，也不意味着回复必须复述它。

## 谁决定是否继续检索

陪伴核心的情境装配模块判断本轮缺少什么；天枢记忆负责执行范围检查、精确查询、混合检索、证据选择及必要的原文回读。决策应产生可观察的类型和原因，例如“资料已够”“核对事项”“查相关往事”“查原话”，便于解释和评估。

规则先处理明显情况；剩下的复杂指代和不确定情境可用一次有限判断，或并入本轮模型的工具选择。不要单独为每条消息增加一个大模型，只用来问它“要不要查询记忆”。

小粒度存储应通过批量检索和装配取用，不能演变成每条原子记忆一次网络请求。范围和版本核对可与基础读取合并；入库时已经维护的语义依赖，线上先用程序检查，遇到新歧义再按需核验。对话与后台整理的等待边界见 [陪伴核心链路设计](companion-core-flow-design.md)。

| 触发情况 | 建议行为 |
| --- | --- |
| “早呀”“这张图真好看” | 有效基础情境足够时直接回应；无需为了使用记忆而搜索历史 |
| “你还记得上次说好的事情吗” | 必须核对相关证据；当前已有可用证据则可复用，否则检索，不得凭语气熟悉就编造 |
| “那件事办完了吗” | 先根据当前话题确定对象，精确查当前事项状态；指代不清时询问，不用最相似的一段旧聊天代替状态 |
| “昨天那个方案，我又想了想” | 按人物、时间和话题定位相关经历，必要时混合检索；这类间接回忆不能只靠“记得”关键词识别 |
| 切换新话题、人物或项目 | 检查原有证据是否仍适用，按需要补充新的资料 |
| 准备说出过去发生的具体细节，但上下文没有依据 | 在发送前补查一次；查不到就保留不确定性，不把生成内容当成记忆 |
| 主动提醒、关心或兑现约定 | 先查最新事项状态和联系条件；不能因为缓存里有旧计划就主动发送 |

这些规则是设计起点，不能宣称完全避免漏查。实现时应把“每轮轻量检索”保留为对照方案，在同一模型、范围和预算下比较；如果它在真实使用中更稳且成本可接受，可以对部分场景采用。门控的价值必须由少漏查、低延迟和适当成本共同证明。

## 真正的召回如何执行

先构造检索意图：本轮对象是谁、想核对哪件事、时间范围是什么、需要当前状态还是历史经过、证据要精确到什么程度。角色和受众范围从可信调用上下文继承，不能由聊天文本任意指定。

有明确人物、事项或事件编号时，先查结构化记录。描述模糊时再组合关键词和语义检索；候选查询本身受范围限制，不能先返回全库命中内容再让模型挑出可以看的部分。过时、撤回、被替代或不属于此角色所知范围的内容不进入可用证据。

候选按相关性、时间、来源和有效状态去重筛选，确有收益时再重排。时间并不是唯一权重：当前偏好应使用有效新版本，询问过去经历则需要当时版本。事实来源与用户自述、他人转述、推断、未完成计划分别保留性质。

摘要不足时，回读允许范围内的原消息及少量上下文。检索不充分时可做一次有上限的查询细化；仍有歧义则询问或明确记不准，不能不断扩展成全历史遍历。

交回核心的 MemoryContext 建议将最终选中内容与程序元数据分开：模型只接收必要字段、完整限定语和少量证据；完整来源列表、检索分数、候选全文与历史版本保留在服务端。条目数、最终渲染长度和补查累计预算共同约束输出，禁止截断条件来凑额度。具体字段与 API 名称仍待实现阶段确定。

“没有匹配”“当前不能使用该资料”“依赖服务故障”“资料版本无法确认”应在内部区分，但内部诊断不能向群成员暴露被过滤的私人记忆是否存在。最终表达可以自然说明需要本人补充或转到适合的场景。

## 缓存怎样保持连续，也不泄漏

缓存键至少绑定角色、人物集合、会话/允许视图、用途、话题或查询，以及对应的可见范围与数据版本。相同问题在私聊和群聊中不能因为文字相同就命中同一份私人结果。

身份合并、范围变化、撤回、纠正、事项完成/取消等应递增相应记录或范围的版本，使旧快照失效。时间敏感内容还需有效期；仅依赖固定 TTL 无法确保刚取消的提醒立即停止。

正式记录提交与版本更新应保持一致。每轮对将使用的快照做轻量版本核对，可与基础情境读取合并成一次接口调用；失效通知用于加速，不单独承担正确性。收不到通知或无法确认版本时，旧资料不能作为“最新状态”的依据，相关主动跟进延后。

向量或摘要更新可以稍后完成，但旧索引命中的条目要再按正式记录版本核对。新状态尚未进入向量索引时，先查结构化记录、增量变化或必要的受限原文。不能把“索引还没更新”表现成仍坚持旧事实。

记忆整理、向量化和按需重排可在统一模型配置中分别绑定。向量化按记忆集合固定空间、模型/版本与维度，更换时重建并验证新索引，不能随角色聊天模型切换或普通备用线路混用。详见 [多模型接入商与功能分工](model-providers-and-workloads-design.md)。

## 消息如何写成长期记忆

原聊天由 Chat Audit 保存，记忆摄取保存来源引用和需要整理的获准材料；任务结果、角色模拟活动、作品草稿等保留不同的事件类型与负责方。采集缺口、未缓存媒体和失效引用应有状态，不能假装原文永远完整。

接收时确认归属、范围和事件编号。重复投递应幂等。普通聊天按连续话题、参与者和事件边界积累素材，避免每句话独立提取、每轮重新总结全部历史。

模型辅助提取事实、经历、关系、事项和知识候选，程序及必要的有限校验再检查来源、人物归因、时间、冲突和范围。引述小说、转发别人消息或角色自己的创作，不能直接记成现实用户亲历。

明确且可确认的完成、取消和纠正走短路径：定位对象、检查身份和范围、校验并提交正式变更。指代不清或相互矛盾时先保留冲突，不将“最新一句话”无条件覆盖原记录。

正式记录保存来源、观察时间、适用时间、归属、允许范围、状态及修订关系。原事实被纠正后保留可追溯历史，召回默认使用当前有效版本；询问历史时再按问题时间回看。

画像、小摘要、关键词/向量索引等在后台增量派生，并携带对应版本。它们可以重建；用户明确修正的资料应形成正式修订，不只改缓存。底层可以先用一个关系库承载必要表与索引，不必为图中每个框部署独立服务。

## 模块边界与三个接口族

| 边界 | 负责内容 |
| --- | --- |
| 陪伴核心 | 当前话题、角色状态、回应必要性；明确本轮记忆需求，并组织最终表达 |
| 天枢记忆 | 人物/关系与长期资料、范围化读取、更新与纠正、证据选择、派生索引与快照 |
| Chat Audit | 原始聊天与媒体档案、消息邻域和归档状态 |

对核心可先提供三类能力：获取有限基础情境；按意图召回证据；摄取事件或提交明确修订。查询与摄取必须带可信身份和来源，但无需因此设计复杂的逐条人工授权流程。接口语义由天枢保持稳定，内部是否采用自有实现或成熟记忆引擎，可以继续比较。

相同的有界上下文能力也面向 Codex、Hermes 等编码体，但使用独立的项目视图和工作目录/版本范围。项目文档、当前任务与个人记忆保持各自负责方，不将完整文档自动注入每轮聊天。旧适配代码与新接入边界见 [项目上下文接入](project-context-codex-hermes-design.md)。

## 需要实际验证的用例

- 不进行新的历史检索时，仍能正确称呼用户并保持关系和角色语气。
- “昨天那个安排”能够触发必要检索；明确问往事时不因门控漏判而编造。
- 同一问题从私聊移到群聊，不命中私人缓存；他人的私密细节不被摘要带出。
- 取消事项后立即继续聊天，旧向量索引尚未更新，也不会继续提醒。
- 偏好更新后使用新版本；询问过去时仍可说明当时的偏好。
- A 的亲历不会自动成为 B 的亲历；虚构日常不会改写现实用户经历。
- 采集缺口、记忆故障、身份未确认和检索无结果能被区分处理。
- 对照每轮轻量检索与按需策略，检查漏查、答复依据、错误归因、隐私、延迟与 token 使用。

本文图示和接口语义尚未通过上述实际运行验收，不能视为已经完成的记忆系统。
