# 小屋环境、光照与交互联动

> V2 选型优先级见 [整体架构 V2](tianshu-system-architecture-v2.md)：优先验证固定视角轻量 3D，保留 2D 对照，样片验证后只选一条主渲染路线。下文环境行为约束继续有效。

日期：2026-09-13。用户明确重视小屋界面，要求按时间推进窗外光照与环境，同时考虑室内灯光、窗户开闭和窗帘风摆。本文将其纳入小屋基础体验要求；具体渲染技术、参数、素材和运行效果仍待验证，未实现环境模拟或角色动画。

## 体验目标

小屋应具有持续且可理解的环境状态。时间影响天空与日光，窗户影响开口、局部遮挡与气流，窗帘影响透光和风摆，室内灯具独立照亮附近对象。所有元素与角色当前活动保持相容。

| 对象 | 目标表现 | 必须保持的逻辑 |
| --- | --- | --- |
| 时间与天空 | 清晨、白天、黄昏、夜间连续过渡，窗外亮度与颜色随之变化 | 不把四个时段硬切成四张背景；示意时间不当作全年真实日出日落 |
| 窗外日光 | 入射方向、强度、色调与可见投影随时间变化 | 日光是否照进房间取决于设定的窗向、遮挡与天气，不能所有时间都保持相同直射光斑 |
| 室内灯具 | 台灯、床头灯等分别开关、调亮度与色调，柔和过渡 | 有局部照射范围、衰减与相应遮挡；关闭一盏不关闭其他灯或日光 |
| 窗户 | 关闭、部分开启、打开，以及连续开合过程 | 玻璃关闭通常仍透光，关窗不能等同于拉上遮光帘 |
| 窗帘 | 分别控制拉开程度、材质与轻微风摆 | 上端固定，摆动有惯性与衰减；半透明纱帘和遮光帘对光的影响不同 |
| 室内气流 | 受开窗程度、场景风向/风力及配置的室内送风影响 | 关窗后外来气流减弱，窗帘逐渐停稳，不瞬间冻结，也不永远保持大幅摆动 |
| 角色活动 | 阅读、写作、休息等可提出相应环境调整 | 由共享状态协调，不让角色台词、灯具、窗帘和小屋画面各自维护不同结论 |

环境是陪伴核心与小屋前端的内部能力，不新增一个必须单独部署的“天气/窗帘微服务”。角色的虚构窗灯与真实家庭智能设备是不同对象，不能因名称相同就控制用户的实体灯或窗户。

## 时间来源与预览

建议生活时间默认跟随平台配置时区，并以服务端时间为基准。当前用户环境为 Asia/Shanghai，但精确日出日落、太阳方向和季节变化还需要设定地点或虚构地点、日期与窗户朝向；不自动读取真实位置，也不在缺少这些信息时声称是准确天文模拟。

可先采用可配置的昼夜曲线：连续计算外部亮度、天空色、日光方向与环境光；若之后启用真实地点模式，再按相应日期和太阳位置驱动。昼夜曲线及实际地点模式必须有明确标识，效果图中的 08:00、14:00、18:30、23:00 仅是气氛对照时间。

天气与气流首先可以使用场景预设。今后若连接真实天气，应记录来源、新鲜度和失效后的替代状态；不能将预设晴天显示成实际天气。风和云可以持续缓慢变化，但不要求真实流体或气象模拟。

“预览时间”是本地视觉查看模式：拖动时间只改变预览环境，不改变核心生活时间，不触发新的日记、提醒、记忆记录或自动任务。退出预览后恢复当前共享状态；界面持续显示预览标识。

## 状态与计算如何衔接

基本链路：配置和服务端时间 + 房间窗/帘/灯状态 → 环境参数计算 → 小屋渲染与动作表现。

- 陪伴核心保存房间及物件的稳定编号、当前/目标状态、状态版本、变化原因与必要的开始时间。多个角色处在同一房间时，共享一套窗、帘和灯状态。
- 环境参数计算按时间、当前配置和物件状态求值，不逐帧调用大模型。角色可以因为活动提出开灯、关窗或拉帘动作，普通 UI 操作也调用同一状态入口。
- 前端负责平滑呈现、局部动画、材质和风摆。当前角度到新目标角度连续过渡，重复点击不能叠加出重复开合动作；新的有效目标应从当前表现状态衔接。
- 不把每一帧风摆写进长期记忆或数据库。可保存有意义的状态变化和必要的动画时序，渲染细节由前端求值。
- 房间状态由服务端版本确定。关闭网页后，生活时钟和自动规则继续按核心机制推进；重新打开或从后台恢复时读取当前状态，不补播离线期间所有帧，也不把浏览器的暂停计时器当作真实时间。

手动与自动不能争抢：建议手动控制后保持该物件的手动状态，界面提供“恢复自动”；用户恢复后才由角色/环境自动规则重新接管。具体是否支持“保持到某时刻”作为后续可选项，不默认不断覆盖用户刚调整的灯光和窗帘。命令尚未得到核心确认时，界面不能把它显示成已持久生效。

## 需要拆分的素材

房间基础色、窗外景、窗框/窗扇、玻璃、纱帘、外层遮光帘、灯体与发光部分、家具、角色和前景遮挡应具有可独立控制的素材或几何。高光、日光斑和阴影应与可变化的光源相匹配，不能在全天共用的底图里永久画死强烈午后阳光，再叠上一层蓝色当夜晚。

窗帘可以使用少量骨骼或低密度网格表现轻摆，顶部固定，位移受限；需要避开窗框、床和墙面。摆幅随气流平滑变化，加入轻微不完全同步的相位差，避免左右窗帘机械地同幅摇摆。无需一开始就做完整布料物理。

房间的光照与周围网页 UI 分开处理。夜晚可以让房间变暗，但日期、状态和操作面板必须保持可读；系统主题是否随昼夜变化另由界面偏好决定。

## 渲染路线需要按目标验证

前一轮将 Phaser 作为动态小屋的优先候选。现在用户进一步强调时间、局部灯光、窗扇、遮挡与窗帘联动，选择条件需要扩展；不能仅因为最初画的是等距插图就锁定纯 2D。

| 路线 | 适用优势 | 需要验证的代价或限制 |
| --- | --- | --- |
| Phaser 等距 2D / 分层素材 | 容易保留绘制风格，复用场景、输入和动画机制；可用二维受光、材质贴图与遮罩实现效果 | 法线辅助受光不等于恢复真实几何；移动日光、家具投影、窗扇与帘的遮挡需要额外设计，手绘阴影组合会随状态增加 |
| 固定等距视角的轻量 3D 场景，例如 Three.js | 视角仍可像当前 2.5D 小屋，但窗框、窗扇、家具和灯具使用几何来组织光照与阴影 | 需要房间与物件资产，控制模型、材质、透明物体和投影开销；角色动画与绘画风格也需验证，不能保证自动达到概念图品质 |

Phaser 官方文档提供二维灯光/环境光及法线相关机制，且 API 随版本变化；Three.js 的阴影文档提供灯光、投影对象与接收对象的配置及性能取舍。这些是可用机制，不证明当前素材已经完成动态光照。[Phaser Light](https://docs.phaser.io/phaser/concepts/gameobjects/light)、[Phaser 灯光管理](https://docs.phaser.io/api-documentation/4.0.0/class/gameobjects-lightsmanager)、[Three.js 阴影](https://threejs.org/manual/en/shadows.html)。来源核对于 2026-09-13。

首个环境样片应以同一小场景比较目标效果与成本：一扇可开合窗、纱帘和遮光帘、两盏可独立控制的灯、窗框/桌椅遮挡、一个角色姿态。确定一条主要场景渲染路径，不为“都支持”而同时叠加两套游戏引擎。选择引擎不改变 NoneBot、天枢记忆或陪伴核心的数据职责。

## 性能与表现

优先限制同时产生动态阴影的光源，把主要阴影预算留给日光和必要局部灯。角色呼吸、窗帘轻摆和微粒按终端能力降级；隐藏页面暂停高频渲染，恢复后重新与共享时间对齐。减少动态模式关闭非必要摆动与过渡，但窗户开闭、灯的开关和当前时间仍应正确显示。

普通光照和动画计算主要消耗浏览设备算力，不持续消耗聊天 token。绘制帧率、资产体积和不同设备上的性能尚未实测，不能以静态图或设置帧率上限作为运行成绩。

## 后续验收用例

1. 同房间从清晨连续预览到夜间，光照和投影变化连贯；正常模式不硬切时段，且不会写入预览产生的生活事件。
2. 正午只关窗，日光仍能穿过玻璃；保持其他条件不变时，外来气流减弱，帘摆逐渐衰减。
3. 拉上遮光帘后，进光和可见窗外范围相应减少；纱帘使用不同的透光表现。
4. 夜间分别关闭台灯和床头灯，剩余光源及环境光保留，不发生全房间统一跳亮/跳暗。
5. 太阳方向或灯位变化时，窗框、家具和角色的遮挡一致，不出现固定底图阴影与动态阴影互相冲突。
6. 连续改变窗户/窗帘目标，从当前状态衔接；顶部锚点不漂移，物件不穿过不允许的几何。
7. 多客户端看到相同房间状态；关闭页面或挂后台后回来，恢复当前时间和灯窗状态，不从旧时段继续累计。
8. 自动场景规则尊重手动保持；未确认的远端命令、过期状态和离线预览有明确区别。
9. 调整环境不让网页文字不可读，减少动态仍可理解状态；低性能设备有可用的简化效果。
