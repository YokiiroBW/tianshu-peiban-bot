# 陪伴核心内部链路设计

> V2 总体职责以 [整体架构 V2](tianshu-system-architecture-v2.md) 为准：人格、世界设定与当前世界/房间状态由陪伴核心维护；记忆索引历史及角色获知范围。本文的消息、上下文与表达细节仍供参考。

这是完整产品蓝图中陪伴核心的进一步展开，属于设计建议，尚未实现。模块名称帮助分配职责，不意味着每个框都是独立进程、模型代理或微服务。

## 三条持续运行的链

即时对话链负责当前互动；生活链推进角色自己的作息、活动、目标和兴趣；后台整理链从获准输入及真实结果中整理经历。三条链通过持久事件、角色状态和有限任务协作，可以先在一个核心程序及必要 worker 中实现。收件箱、待发送记录与任务表可先放在同一关系库，不必新增全局消息中间件。

角色并非每收到一句话就重新规划一整天。生活链维护“她此刻在做什么”，对话链读取这个状态。对话也可以产生生活调整，例如主要用户邀请她一起看电影：先形成邀请/安排变更，再更新活动；不能只在回复里说答应了，却让小屋继续显示另一套状态。

## 一条普通消息的运行过程

### 01 受理与定位

消息由 NoneBot 或陪伴客户端送入。核心按可信入口定位平台账号、人物编号、会话、角色及引用消息，处理必要的图片/语音描述，保存原始输入引用和轮次。平台消息编号与观察账号共同参与去重；同一消息重发不能再次加好感或重复执行工具。

当前话题窗口按角色与会话组织。世界共享、人物编号统一，不表示所有角色和群聊共享同一个上下文窗口。多角色在同一群中的普通主动回复应先仲裁；被明确提及的角色优先。自身回声及机器人互相触发要有限制。

2026-09-13 新增：受理后的普通用户发言先进入可配置的滑动静默窗口，同一收集键每次有效新活动都会重新计时；静默满窗口后形成保留原消息、顺序、引用与媒体的结构化消息组，再进入回应判断。详见 [连续短句防抖与消息组](message-debounce-and-bundling-design.md)。这不是将多条消息改写成一句话，也不在窗口内逐条生成回应。

后续轮次采用流水线：第一轮封存后继续处理，普通新消息进入独立的第二轮缓冲；第二轮就绪即可在资源和实际依赖允许时提前处理，默认按轮次发送。不能持有会话锁直到第一轮发送完，也不能仅因新消息出现而取消第一轮。

明确的完成、取消和纠正优先生效，例如“刚才的下载不用继续了”“那件事已经办好了”。没有明确证据的推断保留为候选；不要先等夜间总结，再停止已经过时的跟进。

### 02 判断是否回应

私聊、直接提及、正在进行的问答和任务回报通常进入后续处理。群聊中的普通消息先看相关性、最近发言、话题参与者、角色状态和冷却。确定能用规则判断时不调用模型；确实不清楚再使用一次有限判断。

“暂不参与”意味着不发送消息，仍可更新获准观察和群话题。它不意味着立即为每句话调用长期记忆模型。生活产生的主动候选，也要核对联系对象、当前场景、冷却、事项是否已完成，以及有没有值得分享的新信息。

任务结果是带关联编号的系统事件，不应被当成一条普通群消息重新猜意图。它恢复原目标并核对时效、授权及受众；不再次执行已经提交的同一动作。

### 03 装配本轮上下文

建议每轮得到一个有大小上限的 TurnContext，其中包含：

| 部分 | 来源与用途 |
| --- | --- |
| 稳定角色资料 | 人格版本、价值观、表达样例、世界设定引用，保证角色声音一致 |
| 此刻状态 | 当前活动、心情、日程、穿搭、正在做的作品，保证前后连续 |
| 与对方的关系 | 本轮确需的交流尺度与关系字段，按需取用；亲密表达与设备权限分开 |
| 当前对话 | 正在回复谁、引用、当前话题、未完成问答与必要最近消息 |
| 相关记忆 | 在人物、角色、会话和受众范围内召回的事实与经历，带来源与时间 |
| 可用能力 | 此角色可以使用的工具、已配置目标及本轮允许的操作范围 |

隐私范围在召回前确定；返回内容再按相关性和预算选择。不得把完整私聊历史放进群聊提示词，再要求模型自行隐藏。短期窗口、缓存、日记素材和工具返回也遵守同样边界。

2026-09-13 补充：每轮装配基础认识，不等于每轮重新检索全部历史。有效的小画像、关系、事项和已有证据可以复用；显式回忆、信息变化、话题切换或证据不足时再精确查询、混合检索或追溯原文。复用前仍要核对范围与版本。详见 [记忆召回与整理链路](memory-recall-and-lifecycle-design.md)。

粒度约束：上述“小画像/关系快照”只允许是本轮已选字段的投影，不是完整画像摘要。画像可以零条返回，命中一个主题不能展开整张画像；原子项必须保留条件、否定和时间。按 [画像分层与最小充分召回](profile-memory-granularity-design.md) 执行分层、完整语义与本轮共享预算。

情绪可以先基于本次事件形成临时评价，让当前回复体现刚发生的事。长期好感与稳定画像的变化要有证据、限幅、幂等更新，不能让一句模型生成的感想永久改写关系。

### 04 规划与表达

简单聊天可以在一次模型调用中确定回应意图并形成候选文本，保持人格、当前状态和上下文一致。需要搜索、自拍或设备操作时，返回结构化能力请求；需要写日记或创作时，选择对应 WritingRecipe。没有理由把所有闲聊拆成多轮规划、反思和工具调用。

模型请求通过模型网关发出。程序限定本轮工具次数、执行时间与输出预算，区分“建议动作”“已提交任务”“实际结果”。模型不能用自己生成的描述代替执行回报。

模型从天枢的统一接入商与功能绑定中解析：主对话可按角色覆盖，写作、识图和后台记忆整理可使用不同模型；已开始的轮次保留配置快照。分工不意味着每条消息调用所有模型。详见 [多模型接入商与功能分工](model-providers-and-workloads-design.md)。

### 05 发送前核对

检查接收对象、资料范围、事实与工具结果、角色一致性、重复表达和当前时效。发送前再次看是否收到更新的取消或纠正，避免把已经过时的回复发出去。

格式、目标、幂等和明显越界由程序检查；确有需要才进行有限语义检查。发现具体问题时，至多先安排一次定向修订；仍有问题则缩减到可确认内容、说明执行失败或放弃主动发送。具体默认预算后续实测决定，不用无限自我反思维持流程。

### 06 投递、回执与后续整理

合格内容进入待发送记录，由投递模块转成文本、图片、语音或客户端结果。已生成、已提交发送、已送达和对方已读分别保存。发送失败时不会把“她已经告诉用户了”写成既成经历。

输入、真实动作结果和发送回执分别进入观察日志；后台整理仅消费允许范围内的材料。核心准备事件与素材，天枢记忆的摄取和整理接口负责长期记录、索引、纠正与检索，不在核心复制另一套长期记忆系统。

## 对话等待与执行边界

2026-09-13 补充评估：目前是设计稿，尚无完整链路的实测延迟。模块数量不等于模型调用次数；若把判断、检索规划、语义重排、回应生成和审核各实现成一次串行模型调用，等待会明显累积。普通聊天应以一次主模型生成作为默认路径。

| 场景 | 建议的前台执行路径 | 哪些工作不应成为默认等待 |
| --- | --- | --- |
| 普通文字闲聊 | 受理与规则判断 → 批量读取必要状态/有效记忆投影 → 一次回应生成 → 必要核对与投递 | 独立画像总结、完整日程推演、第二个模型逐条审核、无目的历史检索 |
| 需要往事或约定 | 先精确查询或有限检索，再生成回应；生成中才发现缺口时允许有界补查与续答 | 每个原子项一次网络调用、对所有候选逐项模型审核、无限补查与重写 |
| 搜索、生图或业务操作 | 提交任务并记录关联；短任务在预算内等待，长任务完成后续接 | 占住整个会话等待生图/下载完成，或让无关新消息排在它后面 |

已确定角色与受众范围后，无依赖的状态和资料读取可以并行。天枢记忆的一次请求应在服务内部完成必要的范围、版本、候选选择与依赖组合，再批量返回小包；图上的逻辑节点不必各自变成一次网络跳转。用户明确取消等新变化要先处理，不可为了并行读取而破坏因果顺序。

语义完整性主要在入库和更新时维护：保存限定语、来源与必要依赖，后台检查派生资料。线上仍检查当前范围、版本与依赖是否齐全；发现新歧义或冲突时再回读和有限核验。不能通过跳过隐私、必要证据或状态校验来换速度，也不需要每轮重新审查所有历史块。

前台对话与日记、记忆提取、索引等后台任务分开限流，并为对话保留处理余量。异步任务仍会消耗模型额度、数据库、网络及本地 GPU，单纯放入后台不等于没有影响。工具占用 GPU 时，本地语音、embedding 等任务是否争抢同一资源需要实测和调度。

同一逻辑会话/线程内的陪伴处理上限已由用户确认为两个轮次，会话内多角色共享该上限。T2 的准备和独立生成不等待 T1 发送完成；候选生成顺序与发送顺序分开管理。对前轮答案、同一设备操作或状态写入存在真实依赖时，只有相关步骤等待；资源不足时真实记录排队，不能保证任意负载下无等待。

两个处理槽不限制全部功能任务。已注册的明确群管理或 GsCore 命令可由 NoneBot 直接分流给插件/桥接器，不等待陪伴模型；自然语言请求才先经过核心理解，再调用同一个执行者。详见 [功能路径与职责](functional-routing-and-ownership.md)。

私聊和群聊均支持用户配置的滑动静默窗口，启用后严格按窗口收集续句，例如最后一条有效发言后静默满 5 秒再处理；最长连续等待可单独设置或关闭。未启用时不增加这段收集等待。角色作息影响内容与参与时机，不默认叠加另一段不可取消的长时间等待。

Web 客户端可在允许范围内流式显示内容；QQ 等按完整消息投递的渠道，不能把模型首个 token 时间当成用户已经看到回应。分段发送也要保留完整意思，并对即将发送的内容完成必要检查；不能先发未经检查的敏感内容，再依赖后续修订撤回。

建议先将普通文字闲聊在消息组就绪后的自研处理开销以 p95 不超过 500 毫秒作为待验证目标，统计内部排队、状态/记忆读取、装配和投递前核对的实际等待。用户配置的防抖收集时间、受理耗时、外部模型生成、外部工具及渠道投递分别记录，全部纳入端到端结果，不能用处理目标掩盖实际等待。复杂检索、图片/语音输入及需要额外语义核验的轮次单列评估。

同时记录：收到消息到首条有实质内容的回复、完整回答完成、工具任务完成、实际模型调用次数、输入输出长度、检索和排队时间。进度提示单独统计，不能把“我去查一下”算成完成实质回答。对相同模型、输入规模和输出长度，对照直接调用与经核心调用的差异；在多角色群聊及后台任务运行时测尾部延迟。阶段 p95 不能直接相加当成端到端 p95。

500 毫秒是架构目标草案，不是当前成绩或保证。完整对话耗时最终还取决于模型线路、思考配置、输出长度、工具和实际负载；不能在未实现和压测前承诺每轮固定几秒。

## 工具、写作与长任务怎样回到主线

短任务在允许时间内完成，结果沿原调用链交回表达模块，再通过发送前核对。长任务保存原目标、角色、会话、受众、参数、任务编号、期限及当前状态，释放本轮会话执行位。完成、失败、取消或超时后，结果成为关联事件重入 01；用户在等待时仍能继续聊天。

必要时先发送一句有依据的进度说明，例如“我去拍一张”。这也是一次真实投递，需要自己的发送记录；不能提前回复“已经完成”。重入时只续接结果，不把工具动作从头再执行一遍。

日记配方读取当天可用素材，选少量有意义的片段，形成关注中心，再成稿和核对。创作中新写的情节不会自动变成现实用户的经历，也不会自动改写共享世界正典。

衣橱配方读取衣物、适用场景、当前活动和已选穿搭，形成结构化选装或自拍请求，再由生图适配器映射到 ComfyUI 工作流。仅说“给我看看今天穿搭”时应优先沿用当前穿搭；用户要求换装或生活安排变化时才更新，不每次随机改成另一件衣服。

查询资料、阅读和创作可由日程触发，也可由聊天触发。后台任务有结果后先更新活动/作品状态；只有新信息相关、时间合适且允许联系时，才产生主动分享候选。日记完成不等于自动公开日记。

## 数据与更新分别由谁负责

| 对象 | 主要负责方 | 更新原则 |
| --- | --- | --- |
| 人格配置与表达样例 | 陪伴核心配置 | 版本化，修改明确可见 |
| 当前活动、心情、穿搭和日程 | 陪伴核心 | 事件驱动、有限变化、状态版本；小屋读相同状态 |
| 话题窗口、轮次与待发送消息 | 陪伴核心 | 会话有序、有界窗口、去重和发送回执 |
| 人物、长期关系、画像、经历、事项 | 天枢记忆 | 核心通过接口读写，只缓存必要的当前快照 |
| 共享世界正典与各角色所知 | 核心持有世界设定与当前状态；记忆提供历史及获知范围检索 | V2：“世界发生了”与“谁知道了”分别记录；按参与者和传播更新 |
| 原始聊天与媒体引用 | Chat Audit Core | 保留来源，记忆与作品通过引用追溯 |
| 自拍、写作等任务 | 核心任务编排与对应后端 | 核心管理陪伴目标，后端报告实际执行状态 |
| 下载、设备、项目等外部业务任务 | 天枢平台及其执行器 | 一个动作只有一个实际执行负责方；核心保存关联引用 |

## 三个验收例子

“看看今天穿的什么”：识别私聊人物与角色 → 读取她当前活动、已选穿搭和关系 → 形成自拍请求 → 提交 ComfyUI → 长任务期间继续聊天 → 图片结果重入 → 核对图与目标 → 发图并记录实际送达。

群里有人继续讨论她关注的游戏：更新当前话题 → 判断是否相关且适合插话 → 不适合时安静观察；适合时取群内可用知识和认识 → 用角色语气接话 → 不带出其他人的私人聊天细节。

晚上写日记：生活链发现到期 → 配方读取当天获准事件和她自己的模拟活动 → 选择主题 → 写作及事实/视角检查 → 保存作品并更新书桌/日记本 → 是否向主要用户提及，再经过主动联系判断。

## 故障与边界验收

记忆暂不可用时可用近期窗口继续有限聊天，并说明无法确认的往事；依赖最新事项状态的主动联系延后。模型失败、图像失败和平台失败分别返回真实状态。服务重启后可恢复收件箱、任务与待发送记录，且不能重复加分、重复操作或重复发图。

需重点验证：同一消息重放；用户在生图期间取消；主要用户换了会话；两个角色同时想在群内接话；工具完成但发送失败；私聊取消使群内跟进过期；A 经历的事 B 尚不知道。上述结果比模块数量更能证明拟人连续性和可靠性。
