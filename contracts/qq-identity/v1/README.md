# QQ identity v1

Published locally on 2026-09-30 after fixed-diff review, three-service HTTPS observation tests and real Memory HTTPS browser read/grant/revoke tests. Accepted implementations: Platform `511b631e456297de9185132b9c17f126524766b2`, Companion `fc4d04caf4b0a376316f9acc2de55ea7030348b1`, Memory `5a635aa5292859a1527730bbf82577af47b1df95`. Production deployment is separate. See `docs/development/qq-identity-acceptance-2026-09-30.md` in the coordination repository.

Platform owns QQ administrative grants and the authenticated check endpoint. Companion consumes its scoped identity projection and rechecks the pinned version before generation and send. Memory owns each platform account's independent person mapping and source-bound display aliases. Runtime boundaries use exact-field validators; this schema describes the jointly accepted message shapes.

`POST /internal/v1/qq-admin/check` accepts `check_request`. Its `assertion_ref` is an opaque, persisted Platform origin reference, not a password or a model-visible grant token. Platform authenticates the Companion service and resolves the live reference; the verified account selects the QQ grant. Actor and conversation must match the source scope. The response includes the global grant version even when no grant applies. Only `identity.explain` is supported: it grants no tool, read, export, delete, device or administrative operation. Grants start empty and are written only through the authenticated operator web route with compare-and-swap versioning.

`POST /internal/v1/identity/qq-alias` accepts `alias_request` from the dedicated Platform writer. Its event reference is idempotent and conflicting event contents fail. This port does not create accounts. `POST /internal/v1/identity/qq-profiles` accepts `profiles_request` from a distinct Platform reader and is exposed by Platform only to its authenticated authorized web operator. Nickname and group card are display data, scoped by account/BOT/group, never identity or permission claims.

The ordinary bot text event v2 adds exactly `nickname` and `group_card` to the prior event v1; v1 remains accepted. Unhandled media, forwarded, quoted and third-party mention segments remain unsupported. Passive observation uses separate `observation_event_v3`, with both display fields present and nullable, even when neither name is available. Observation v2 remains archive-only.

The existing observation source envelope binds the entire v3 event through `source_digest = SHA-256(canonical(event))`. Platform verifies this against its durable accepted source, source revision and current read/archive authority. Memory independently calls the authenticated Platform observation verifier before creating or reusing the QQ account and writing aliases within the same transaction as archive intake. This narrow observation enrollment creates no dialogue origin, role, reply scope or administrator grant. A missing explicit QQ alias migration yields retryable failure before account/archive writes.

**Pause and revocation are distinct.** Pausing observation prevents new intake. Already accepted events may finish archive/profile/alias work while their current `read_enabled` and `archive_epoch` authority remains valid, including after a later observation revision pauses intake. Revoked source/read access or an invalidated archive epoch is rejected. This preserves the existing durable observation queue semantics; it does not allow new post-pause events or generate replies.

Deployment requires the Companion HTTPS QQ check reader, appropriate Platform operator/check actions, explicit Memory QQ alias migration, and distinct Memory read/write caller credentials when those features are enabled. Back up Platform's QQ sidecar together with its primary and existing role databases. New QQ reply compositions without the checker fail closed. Preserve existing role-runtime settings and sidecars.

Each platform account retains its own underlying profile and data ownership. This version exposes no cross-platform association/link write, account merge or automatic propagation of administrator status. Future same-person associations are reversible query/UI relationships, not merged storage identities.

Verification uses synthetic local accounts. Full AstrBot 4.27.3 host, real model behavior, production migration and actual QQ replies were not exercised. The browser fixture seeds synthetic data through Memory service methods; observation writes are independently covered by the three-service HTTPS test.
